## Two jobs, two primitives

Public-key cryptography solves two different problems:

- **Confidentiality:** anyone should be able to send a secret to the holder of a private key. A **key encapsulation mechanism (KEM)** does this by producing a fresh shared key plus a ciphertext that only the private key can open.
- **Authenticity:** the holder of a private key should be able to prove that a message came from them and was not altered. A **digital signature** does this.

They are not interchangeable. You cannot "sign" a session key and get confidentiality, and you cannot "encrypt" a public statement and get a signature.

## Why KEMs replaced ad-hoc encryption

Classic RSA encryption asks the sender to choose a random padding string and raise it to a public exponent. That is fragile: padding mistakes have broken real deployments. A KEM gives a cleaner contract:

1. **KeyGen** produces a public encapsulation key and a secret decapsulation key.
2. **Encaps** takes the public key and returns a ciphertext plus a 32-byte shared secret.
3. **Decaps** takes the secret key and ciphertext and returns the same shared secret.

The shared secret then keys a symmetric AEAD scheme. This is the hybrid encryption pattern used by TLS, HPKE and most modern protocols. <Cite id="rfc9180" locator="§4" />

## The attacker matters more than the algebra

A scheme is only meaningful relative to an attack model. For encryption, the strong target is **IND-CCA2**: the attacker can ask for decryptions of arbitrary ciphertexts, even after receiving a challenge ciphertext, but cannot decrypt that exact challenge. For signatures, the target is **EUF-CMA**: the attacker can request signatures on chosen messages but cannot forge one for a new message. <Cite id="fips203" locator="§3" /> <Cite id="fips186-5" locator="§4" />

<Callout variant="warning" title="Textbook RSA is not a KEM">
Raw RSA is malleable and deterministic. Real schemes need randomness, encoding and a CCA-secure transform. Post-quantum KEMs make the transform explicit with the Fujisaki–Okamoto construction.
</Callout>

## What a primitive is not

A common design mistake is to treat public-key encryption as a universal tool. Encryption does not authenticate the sender: anyone can encrypt under a public key. A signature does not hide the message: anyone can verify it. A hash does not prove who produced a file, and a key exchange does not by itself authenticate the peer.

Protocols compose primitives with identities, transcripts and policy. A KEM gives a shared key; the protocol must decide which identity is allowed to establish it and what happens on failure. A signature proves a private-key operation; the verifier must decide which key and certificate chain it trusts.
</Lens>

## What the interfaces look like

A KEM is deliberately minimal:

```text
(ek, dk) ← KeyGen()
(c, K)   ← Encaps(ek)
K'       ← Decaps(dk, c)
```

A signature scheme is:

```text
(pk, sk) ← KeyGen()
σ        ← Sign(sk, m)
0/1      ← Verify(pk, m, σ)
```

The simplicity is a feature. It keeps the attack surface small and makes it possible to swap algorithms behind a stable API — the essence of crypto agility.

## Where PQC schemes plug into protocols

- **TLS 1.3** negotiates a key-exchange group. A hybrid group combines X25519 and ML-KEM; authentication uses ML-DSA or SLH-DSA certificates.
- **HPKE** exposes a KEM interface directly, so ML-KEM can be used for sealed messages and hybrid public-key encryption. <Cite id="rfc9180" locator="§4–5" />
- **Firmware and code signing** need long-lived verification keys and offline signing; large SLH-DSA signatures may be acceptable, large McEliece public keys usually are not.
- **Constrained devices** care about RAM and code size more than bandwidth; the optimal family depends on the device.

<Callout variant="note" title="A KEM is not a drop-in replacement for every PKE">
If a protocol needs to encrypt to a static key without interaction, a KEM can still work, but the protocol must define how the ciphertext and shared secret are carried. Do not invent your own combiner.
</Callout>



## API contract in practice

The clean separation between KEMs and signatures is useful because it makes protocol integration explicit.

| Operation | Input | Output | Failure behaviour |
| --- | --- | --- | --- |
| KEM KeyGen | randomness | ek, dk | randomness failure |
| KEM Encaps | ek | c, K | malformed ek |
| KEM Decaps | dk, c | K or rejection key | implicit reject |
| Sig KeyGen | randomness | pk, sk | randomness failure |
| Sig Sign | sk, m | σ | randomness / rejection |
| Sig Verify | pk, m, σ | valid / invalid | invalid encoding |

The failure behaviour is part of the interface. A KEM that returns an error on a bad ciphertext creates an oracle; a signature verifier that leaks parsing detail can create a side channel. FIPS 203 and FIPS 204 specify these behaviours rather than leaving them to the implementer. <Cite id="fips203" locator="§3.3" /> <Cite id="fips204" locator="§3.6" />

## Key and ciphertext sizes

Sizes are not an afterthought. An ML-KEM-768 encapsulation key is 1,184 bytes and a ciphertext is 1,088 bytes; an ML-DSA-65 signature is 3,309 bytes. <Cite id="fips203" locator="Table 3" /> <Cite id="fips204" locator="§4" /> Protocol buffers, certificate chains, HSMs and firmware update formats must all accommodate those sizes before deployment.
</Lens>

<Lens level={3} title="Definitions, games and the FO theorem">

## Public-key encryption

A PKE scheme has algorithms $\mathsf{KeyGen}$, $\mathsf{Enc}$, $\mathsf{Dec}$ with correctness: for every $(pk, sk) \leftarrow \mathsf{KeyGen}()$ and message $m$,

$$
\Pr[\mathsf{Dec}(sk, \mathsf{Enc}(pk, m)) = m] \ge 1 - \delta.
$$

For lattice schemes, $\delta$ is not zero; it is a small decryption-failure probability that must be bounded and then eliminated at the KEM layer by the FO transform.

## IND-CCA2

The game gives the adversary a public key and a decryption oracle. The adversary submits $m_0, m_1$, receives $c^* = \mathsf{Enc}(pk, m_b)$ for a hidden bit $b$, and may continue to query decryption except on $c^*$. The scheme is IND-CCA2 if every polynomial-time adversary has advantage at most negligible in the security parameter.

The FO transform converts a CPA-secure PKE into a CCA-secure KEM by deriving the encryption randomness from the message and a hash of the public key, then re-encrypting during decapsulation. A mismatch triggers **implicit rejection**: the decapsulator outputs a pseudorandom key derived from a secret rejection value $z$ and the ciphertext, rather than an error. <Cite id="fujisaki-okamoto2013" locator="Vol. 26, pp. 80–101" /> <Cite id="hofheinz2017" locator="pp. 341–371" />

$$
r = G(m \,\|\, H(ek)), \qquad c = \mathsf{Enc}(ek, m; r).
$$

## Signatures

A signature scheme is EUF-CMA secure if an adversary with a signing oracle cannot produce $(m^*, \sigma^*)$ for a message $m^*$ it did not query, with non-negligible probability. Lattice signatures use Fiat–Shamir with aborts: sample a masking value, compute a challenge hash, form a candidate signature, and reject if it falls outside a norm bound. Rejection sampling ensures the output distribution is independent of the secret. <Cite id="lyubashevsky2012" locator="pp. 738–755" />

## The assumptions underneath

Lattice schemes reduce to variants of Learning With Errors and Short Integer Solutions. Regev's LWE reduction connects worst-case lattice problems to average-case LWE. <Cite id="regev2009" locator="Vol. 56, Article 34" /> Ring and module variants add algebraic structure for efficiency, with their own reductions and caveats. <Cite id="lpr2010" locator="pp. 1–23" /> <Cite id="peikert2016" locator="pp. 283–424" />

<Callout variant="lab" title="Proofs are conditional">
An IND-CCA2 proof says: if you can break the KEM, you can solve Module-LWE with a related advantage. It does not rule out a future algorithm for Module-LWE. Security is always relative to the best known cryptanalysis and the stated model (classical ROM, quantum ROM, standard model).
</Callout>



## The games in more detail

For IND-CCA2, the adversary receives $pk$ and a decryption oracle. It chooses $m_0,m_1$, receives $c^*$, and may continue to query decryption for any $c \ne c^*$. It wins if it guesses the challenge bit with non-negligible advantage. The oracle is what makes CCA much stronger than CPA: a scheme that reveals whether a ciphertext is valid can be attacked even if the underlying maths is hard.

For EUF-CMA, the adversary receives $pk$ and a signing oracle. It wins if it outputs a valid $(m^*,\sigma^*)$ where $m^*$ was never queried. Rejection sampling and transcript simulation are the tools that make lattice signatures simulatable without the secret.

<Callout variant="lab" title="Proofs are conditional">
The FO theorem and signature proofs are reductions: a successful attacker yields a solver for the underlying lattice problem, with some advantage loss. They assume hash functions behave like random oracles and that randomness is good. A proof does not protect against a broken RNG, a faulty decoder or a side channel.
</Callout>

## Hybrid combiners

A hybrid KEM concatenates two shared secrets and feeds them into a KDF. The combiner must be unambiguous and domain-separated; otherwise an attacker may be able to swap components or replay a secret across protocols. Use the combiner defined by the protocol (for example the TLS hybrid design) rather than inventing one. <Cite id="rfc9180" locator="§4" />
</Lens>

<Lens level={4} title="Interfaces, encoding and constant-time glue">

## The code around the maths is part of the primitive

A production KEM must define byte encodings for keys and ciphertexts, rejection behaviour for malformed inputs, and constant-time comparison. FIPS 203 makes these requirements explicit, including constant-time decapsulation and implicit rejection. <Cite id="fips203" locator="§3.3" />

Common implementation hazards:

- **Early-exit comparisons** on ciphertexts or tags leak how many bytes matched.
- **Secret-dependent branches** in decompression or decoding leak message or key bits.
- **Variable-time division** in modular reduction leaks coefficient values.
- **Memory reuse** without zeroisation leaves keys in heap or stack dumps.
- **Unchecked lengths** turn a decoder into an out-of-bounds read.

## Serialization is a protocol contract

ML-KEM encapsulation keys and ciphertexts have fixed sizes by parameter set. ML-DSA signatures include a hint encoding whose validity must be checked. SLH-DSA has a fixed structure but variable internal tree paths. If two implementations disagree on canonical encoding, one may accept ciphertexts the other rejects — a recipe for cross-protocol confusion. Use the standard test vectors.

## Libraries versus reference code

Reference implementations are written for clarity, not necessarily for side-channel resistance. Production deployments should use maintained, audited libraries and hardware where available. Open Quantum Safe's `liboqs` provides reference implementations and a test harness for experimentation, but the project itself warns that it is not a production-hardened library. <Cite id="liboqs" />

<Callout variant="warning" title="Do not roll your own KEM combiner">
Hybrid constructions need domain separation and a sound combiner. Follow RFC 9180 or the TLS hybrid design draft rather than concatenating secrets ad hoc. <Cite id="rfc9180" locator="§4" />
</Callout>

## A checklist before shipping

1. Which security notion does the protocol actually require: IND-CCA2, EUF-CMA, or both?
2. Are key and ciphertext sizes within every buffer on the path, including HSMs and firmware?
3. Is decapsulation constant-time, including the rejection path?
4. Are malformed inputs rejected deterministically and without an oracle?
5. Is there a tested migration path to a second algorithm?

## Interface and encoding checklist

1. Fix the byte encoding of keys, ciphertexts and signatures; reject non-canonical inputs.
2. Define failure as a single observable outcome, without distinguishing parsing errors.
3. Validate lengths before decoding; avoid out-of-bounds reads.
4. Keep secret-dependent branches out of decapsulation and signing.
5. Zeroise secret keys and intermediate values after use.
6. Test known-answer vectors, negative cases and cross-implementation interoperability.
7. Document the security level, parameter set and migration path for each key.

<Callout variant="warning" title="A KEM is not a drop-in RSA replacement">
Protocols must define how the ciphertext and shared secret are carried, how identities are bound and how failures are handled. A library swap is not a protocol migration.
</Callout>

## Key takeaways

- PKE, KEM and signatures solve different problems; APIs encode different failure modes.
- IND-CCA2 and EUF-CMA are the relevant attacker games for most deployments.
- FO converts CPA security into CCA security with re-encryption and implicit rejection.
- Hybrid combiners and serialization are protocol design, not library details.
- Post-quantum security is relative to assumptions and implementation quality.
