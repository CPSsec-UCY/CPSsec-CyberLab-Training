## What changes when infrastructure becomes an API

Cloud systems replace racks and physical access with programmable control planes. A storage policy, role assumption, container image, Kubernetes RoleBinding or service token can move an attacker from an internet-facing service to regulated data without touching a server room. The security unit is no longer just a host. It is a chain of identities, permissions, network routes and data services distributed across providers, accounts, clusters and organisations.

NIST defines cloud computing through five essential characteristics, three service models and four deployment models. Those categories matter because they allocate different control to the customer. Infrastructure as a service gives the customer more operating-system responsibility; platform and software services move more of the stack to the provider but do not remove the customer's responsibility for identity, configuration and data. <Cite id="nist-sp800-145" locator="§3 (service and deployment models)" />

The practical consequence is that a cloud review must answer three questions for every asset: **who can change it, who can read it, and which identity can reach the next asset?** A hardened virtual machine is not secure if a storage administrator can replace its boot image. A private subnet is not private if a workload token can call the metadata service. A signed container is not trusted if an attacker can create a privileged pod that mounts it.

<Callout variant="warning" title="The control plane is a production workload">
Kubernetes API servers, cloud IAM services, secret managers and image registries deserve the same or stronger protection as business applications. Compromise there can invalidate controls applied inside the workload.
</Callout>

## Shared responsibility is a matrix, not a slogan

“The cloud provider secures the cloud” is incomplete. Responsibilities vary by service and by operation. Physical facilities and the provider's managed service internals may be provider responsibilities, while account structure, IAM policies, data classification, application code and logging configuration are customer responsibilities. Even managed databases still need customer decisions about authentication, network exposure, encryption context, backup access and audit review.

A responsibility matrix prevents two dangerous assumptions. The first is that a compliance attestation proves the customer's configuration is safe. The second is that a provider-side incident makes customer-side controls irrelevant. A compromised customer credential can abuse a correctly operated service. Conversely, a provider availability failure can strand a customer whose recovery depends on one region or one identity plane.

## Assets, adversaries and incentives

Start with the asset inventory. Cloud assets include human administrators, service principals, federated identities, access keys, sessions, virtual networks, storage buckets, databases, queues, container images, Kubernetes namespaces, secrets, logs and backup vaults. Record the account, region, owner, data classification, internet exposure and dependencies. An inventory that lists only running instances misses the identities that can create, delete or impersonate them.

The adversary may be an external attacker with a leaked token, a compromised software supplier, a malicious insider or a tenant exploiting a misconfiguration. Their goal might be data theft, cryptomining, persistence, credential harvesting or disruption. Their incentive is to use legitimate APIs and avoid controls that require rare signatures. The defender's incentive is to reduce the number of standing privileges and make abuse visible without creating an alert queue that cannot be investigated.

Consider a payments platform with a public checkout service, an internal ledger and a batch-reporting job. The checkout can accept internet traffic but should not read ledger secrets. The reporting job needs batch access but should not be reachable from the internet. A developer role may deploy code but should not silently grant itself production data access. If all three share a broad administrator role, one compromised checkout container can reach the platform's objective. Separating duties is both a security control and an outage-containment mechanism.

### Common misconceptions

A private IP address is not an authorisation boundary. A running container is not automatically isolated from the host or the cluster. Encryption in transit does not prevent an authorised workload from reading plaintext after decryption. Multi-factor authentication protects some human sign-ins but does not constrain a stolen machine credential. A vulnerability scan finds software weaknesses but does not reveal that a bucket policy grants anonymous object reads.

Treat every claim as testable. Instead of “the database is private”, ask which principals and networks can connect, whether the policy has exceptions, and what event is emitted when a new principal connects. Instead of “containers are immutable”, ask who can push an image, whether admission verifies signatures, and whether runtime mounts can overlay trusted files. Security architecture becomes useful when it can be expressed as reachability and evidence.

## Encryption and identity are complementary

Transport Layer Security version 1.3 authenticates the server through its certificate and establishes encrypted application records; network observers cannot rely on reading HTTP payloads to detect cloud abuse. <Cite id="rfc9846" locator="§2 and §4.1–4.5" /> A passive sensor may still see endpoints, timing and connection metadata, but those observations must be correlated with identity, API audit and workload telemetry.

TLS does not decide whether a workload should read a secret. That is an authorisation question. A stolen token sent over TLS remains a stolen token. A malicious process inside a legitimate pod can make perfectly valid TLS connections to the data service. This is why zero-trust architecture emphasises explicit authorisation per session, least privilege and policy enforcement close to resources rather than trusting network location alone. <Cite id="sp800-207" locator="§2–3 (tenets and architecture)" />

## Design the boundary before choosing the service

A useful cloud design begins with trust zones: public ingress, application workloads, control plane, data services, administrative access and evidence storage. For each zone, define allowed identities, protocols, direction, data classification and response owner. Then select services whose controls can enforce that contract. Managed services can reduce operational burden, but they can also concentrate permissions and hide operational detail.

Draw the attack path backwards from the crown-jewel dataset. Identify every identity that can read it, every service that can issue those identities, every principal that can change the relevant policies and every network route that can reach the service. Ask what happens if one workload token is stolen, one image is replaced or one administrator account is phished. If every answer ends at “full production access”, the architecture has not yet separated security domains.

## Reason about paths with evidence, conditions and time

An attack graph is a set of claims about possible transitions, not a picture of confirmed compromise. Give each edge an actor, an action, a target resource, required conditions and an evidence reference. Separate a policy that permits an action from a log showing the action occurred. A missing audit event is not proof that the path is closed; it may mean the event was never enabled, was filtered or arrived late.

Suppose the objective is an encrypted customer export. One candidate path starts with a public archive, reaches a build credential, creates a workload and reads the export. The first edge may be confirmed by storage access logs. The credential's usability may be inferred from its type and expiry. Role passing may be allowed by policy but unobserved. Final data access may remain unknown because object-level logging is disabled. Those four statements have very different confidence and require different follow-up.

| Edge state | Example | What to do next |
| --- | --- | --- |
| Observed | Anonymous object download with object version and timestamp | Preserve the raw event and retrieve that exact version |
| Permitted but unobserved | Build role policy allows creating compute with a data-reader role | Test safely from the build identity and review policy history |
| Unknown | No record shows whether the export was opened | Check data-service audit coverage and bound the uncertainty explicitly |

Prioritise a path by reachable asset value, the number of independent controls that must fail and evidence confidence. Do not multiply invented probabilities to create false precision. A control is valuable when it removes an edge under the attacker's actual conditions and the removal can be tested. Record dependencies on stale tags, optional conditions or provider-specific overrides rather than treating a path as universally open or closed.

The remaining lenses build this model in three layers. First, follow IAM, storage and container identity across cloud APIs. Second, map Kubernetes identities and admission boundaries. Third, connect those technical paths to telemetry, containment and recovery. The interactive lab is deliberately small, but its method scales: nodes are assets, edges are permitted actions, and a control is valuable when it removes an edge rather than merely making it harder to notice.

## Identity is the primary cloud authorisation surface

Cloud IAM combines principals, permissions, resources and conditions. A principal may be a human user, a federated role, a workload identity or a service account. A policy states which actions are allowed or denied on which resources under which conditions. Effective access is the result of identity policies, resource policies, permission boundaries, organisation controls and session conditions. Reviewing only one policy document produces false confidence.

Separate authentication from authorisation. Authentication establishes who is making a request; authorisation decides what that request may do. A valid access token can be replayed from an unexpected host unless token lifetime, audience, sender constraints and conditional access reduce the opportunity. Workload identity improves on long-lived keys by exchanging a platform-verifiable identity for short-lived credentials, but it does not fix an over-broad role attached to that identity.

A least-privilege review should begin with observed actions, not guessed intentions. Collect API activity over a representative period, identify unused permissions, and build a narrow role. Keep administrative actions separate from runtime actions. A deployment role may create a new workload version; the workload role should read only its own configuration and data. Emergency access must be time-bound, approved, alerted and reviewed after use.

<Callout variant="note" title="Deny is not a substitute for least privilege">
An explicit deny can block a known-bad action, but a broad allow still creates future risk when services add actions or resources. Prefer narrow allows, then use denies for organisation-wide guardrails and exceptional cases.
</Callout>

## Storage exposure is often a data path without a vulnerability

Object storage security combines account-level public-access blocks, bucket policies, object ownership, access-point policies, encryption and logging. Public-read access may be intentional for static website assets, but it is dangerous for deployment archives, backups, exports or forensic captures. Review anonymous access separately from authenticated access; a service can be private to the internet yet readable by every identity in an account.

The most important storage question is not “is encryption enabled?” It is “which principal can obtain plaintext, under what conditions, and how will we know?” Encryption protects storage media and may satisfy compliance requirements without preventing a legitimate application role from downloading the entire dataset. Key policies can create a second authorisation boundary, but a role that can decrypt and read remains inside that boundary.

Continuous configuration monitoring should detect policy drift, but prevention is stronger. Apply guardrails at account and organisation level, limit who can change public-access settings and require infrastructure changes through reviewed code. Alert on anonymous requests, unusual download volume and changes to bucket policy, key policy or replication destinations. Preserve the raw change event, actor identity, source network and before-and-after policy.

## Containers add supply-chain and runtime edges

NIST's container security guidance treats risks across the container image, registry, orchestrator, container runtime and host. <Cite id="nist-sp800-190" locator="§3–5 (container risks and mitigations)" /> Vulnerabilities may enter through base images, dependencies, build tooling or registry credentials. A vulnerable image is only one problem: an attacker may exploit excessive runtime privileges, writable host mounts, exposed Docker-compatible sockets or a permissive orchestrator policy.

Secure the lifecycle rather than only scanning the final artefact. Pin base images by digest, generate a software bill of materials, scan dependencies, build in a controlled environment, sign the resulting image and verify the signature at admission. Runtime controls should drop unnecessary capabilities, run as a non-root user, use a read-only root filesystem where possible and restrict host namespaces, mounts and device access.

A signed image proves origin and integrity under the signing policy; it does not prove the code is safe. A clean scan proves only that the configured scanner did not find known issues at that time. Admission policy should combine signature verification, allowed registries, provenance and runtime restrictions. Exceptions need an owner, rationale, compensating controls and expiry.

## Microservices turn identity into an application architecture problem

Service-to-service calls need identity, authorisation and transport protection. NIST's microservices security strategies describe patterns such as service authentication, access control and secure communication within a microservice-based system. <Cite id="nist-sp800-204" locator="§3–5 (microservice security patterns)" /> The architectural choice matters: a single shared database credential bypasses service-level authorisation, while per-service identities and database roles can constrain what a compromised service reads.

Use a service mesh or application-level mutual TLS where appropriate, but do not assume the mesh solves authorisation. Encryption protects the channel; policy decides which service may call which operation. Apply request-level authorisation, bounded retries and rate limits. Keep asynchronous consumers idempotent so replaying a message cannot duplicate a financial action. Separate control messages from bulk data movement to make anomalous traffic easier to detect.

## Evaluate policy semantics, not policy names

Policy names such as “read-only” and “developer” are not security boundaries. Review the action list, resource scope, condition keys and implicit deny behavior. A read-only role that can read secrets is powerful. A deployment role that can pass any service role to a new compute resource can escalate through the compute service even if it cannot directly assume that role.

Check cross-account trust, federated role mappings and service-linked roles. External principals may obtain access through resource policies rather than identity policies. Conditions can reduce exposure, but only when the condition keys cannot be freely supplied by the requesting principal. Use organisation guardrails to prevent public storage, restrict allowed regions and protect audit configuration independently of workload administrators.

## Evaluate the complete permission chain

A role document is not the effective permission. The result depends on the principal's attached policies, policies on the target resource, organisational guardrails, permission ceilings and the context of the current session. Provider-specific precedence rules differ, so do not assume that one platform's evaluation order transfers to another. Use the provider's policy simulator for exploration, but confirm important decisions with an authorised runtime test and the audit result.

| Policy layer | Question it contributes | Common review mistake |
| --- | --- | --- |
| Identity policy | Which actions may this principal request? | Treating every attached role as equally appropriate for runtime work |
| Resource policy | Which principals may access this specific resource? | Reviewing only the caller and missing a cross-account grant |
| Organisation guardrail | Which actions are prohibited or region-restricted across accounts? | Assuming an application administrator can override it |
| Permission boundary | What is the maximum scope of an identity's grants? | Counting a broad attached allow without evaluating the ceiling |
| Session and request context | Which source, tag, time or federation conditions apply? | Trusting a condition value the caller can set arbitrarily |

Workload identity removes a standing key but adds a chain that must be reviewed. A pod presents a platform-verifiable identity; the provider validates its source and audience; a token service issues short-lived credentials; the target evaluates role and conditions. If every pod in a node pool receives the same role, compromising one inherits the pool's authority. If a namespace editor can change the service account mapped to a cloud role, they can select a more privileged identity. An overly broad exchange audience can also let a token intended for one service reach another.

NIST's microservices guidance treats service authentication and access control as architectural concerns rather than incidental transport settings. <Cite id="nist-sp800-204" locator="§3–5 (microservice security patterns) — service authentication and access control" /> A safe workload-identity design therefore names the issuing platform, the allowed workload identities, the token audience, the role attached at exchange time and the resource policy applied at use. It also disables static-key fallback, because a convenient fallback often survives long after the primary path is hardened.

Work through a concrete denial. A reporting workload can read its configuration object but receives `AccessDenied` on the report bucket. Check the resource policy's expected access point, organisation conditions, permission boundary, exchanged role and session context. Fixing only the identity policy may change nothing. Record the evaluated chain so the next operator does not repeat a partial diagnosis.

## Validate with adversarial tests

Use safe, authorised tests to confirm that policy behaves as intended. Try an anonymous object request, a request from a disallowed network, a role assumption without the required tag, a pod mounting a host path and a service account reading an unrelated secret. Capture the denial and the corresponding audit event. If the request succeeds unexpectedly, stop and correct the control before continuing.

Do not test only from an administrator workstation. Test from the workload's actual identity and network context. Policies can behave differently for federated users, assumed roles and service principals. Test both allow and deny paths, including a resource that does not exist. Error messages should not reveal sensitive policy details, but audit records should contain enough context to explain the decision.

## Separate the cluster, node, workload and network planes

Kubernetes security spans several planes. The **cluster control plane** includes the API server, scheduler, controller manager and etcd. The **node plane** includes the kubelet, container runtime, host operating system and host mounts. The **workload plane** includes pods, containers, service accounts and application credentials. The **network plane** includes services, ingress controllers, pod-to-pod traffic and egress to external APIs.

An attacker can enter through any plane. An exposed API server or dashboard may permit unauthenticated or weakly authorised administration. A vulnerable kubelet may allow commands to run on a node. A compromised pod may steal its mounted service-account token. A permissive network policy may let that pod scan and reach unrelated services. Controls must cover all four planes rather than treating the cluster as one object.

The OWASP Kubernetes Top 10 organises common cluster risks, including control-plane exposure, workload privilege, insecure RBAC, vulnerable components, secret exposure, network segmentation and supply-chain concerns. <Cite id="owasp-k8s-top-10" locator="Current Kubernetes risk categories" /> Use the categories to structure review questions, not as a claim that ten checks make a cluster secure.

## Authentication gets you to the API; RBAC decides what you can do

Kubernetes supports human users, groups, service accounts and federated identities. Authentication may come from certificates, bearer tokens, an external identity provider or cloud IAM integration. Authorisation is commonly handled through role-based access control. A Role is namespace-scoped; a ClusterRole can define reusable permissions across namespaces; RoleBindings and ClusterRoleBindings attach those permissions to subjects.

Avoid wildcard verbs and wildcard resources. A role that can list secrets may expose every credential in a namespace even if the application only needs one configuration value. A role that can create pods is indirectly powerful because the creator controls the pod specification, including service account, mounts, host namespaces and security context. Treat workload creation as a privileged capability.

Service accounts are identities, not just names. Every pod runs under one. By default, a token may be projected into the pod, so a process can call the Kubernetes API. Disable token automounting for workloads that do not need API access. Where access is required, use short-lived projected tokens, bind the audience and issue only the permissions needed for that service.

<Callout variant="danger" title="Pod creation can be privilege escalation">
If a principal may create a pod, it may choose a more privileged service account, mount a secret or request host access unless admission policy prevents it. Review creation rights independently of read-only appearance.
</Callout>

## Find RBAC escalation paths beyond pod creation

RBAC permissions compose with controllers. A principal that cannot create pods directly may still update a Deployment or Job whose pod template selects a powerful service account, requests host namespaces or mounts a sensitive volume. The controller then creates the pod, which runs under the service account named in the template. Reviewing only the API verb named `pods` misses that path.

| Permission | Hidden capability | Independent control | Verification |
| --- | --- | --- | --- |
| Create pods | Choose service account, mounts, host namespaces and security context | Restricted admission and a small set of assignable service accounts | Attempt a privileged synthetic pod and confirm admission denial |
| Create or update workloads | Cause a controller to create pods from a chosen template | Admission on resulting pods plus protected service-account assignment | Patch a Deployment template and inspect both admission and created pod identity |
| Bind a role or cluster role | Attach a more privileged role to a controlled subject | Restrict `bind` and review referenced permissions | Attempt to bind a privileged role from the limited identity |
| Escalate a role | Create a role containing permissions the principal does not hold | Restrict `escalate` and monitor role changes | Try a role with a forbidden verb and verify denial |
| List or read Secrets | Obtain reusable application credentials | Narrow resource names, separate secret delivery and rotation | Test that only the required secret is readable |

Kubernetes documentation treats RBAC, pod security and secret access as connected controls. <Cite id="kubernetes-security" locator="Pod security, RBAC, network policy and secrets" /> The connection is operational: admission must validate the pod that the controller actually creates, and RBAC must limit who can change the template or the service-account mapping. A policy that checks the human request but not the resulting workload leaves the controller as a confused deputy.

Follow one namespace-editor scenario. The editor can patch a Deployment but cannot create pods or read Secrets directly. They select a service account that can read the database secret and add a hostPath mount. Admission may reject the hostPath while still allowing the service-account change. The new pod can then read the secret without touching the host. Break both edges: constrain service-account assignment and enforce the restricted pod profile on controller-created pods.

Protect namespace enforcement labels from application administrators who could downgrade their own policy. Test with the controller identity, not only a direct pod-create request, and preserve the admission decision in audit evidence.

## Admission and runtime controls are complementary

Pod Security Standards provide baseline, restricted and privileged profiles for common workload settings. The Kubernetes security documentation describes pod security, RBAC, network policy and secrets as connected controls. <Cite id="kubernetes-security" locator="Pod security, RBAC, network policy and secrets" /> Admission policy can reject privileged containers, host networking, unsafe mounts, root execution and unapproved images before a pod starts. Runtime controls observe what happens after admission.

Use the restricted profile as a target for ordinary applications. Require non-root execution, drop all capabilities and add back only documented ones, disallow privilege escalation, use seccomp and prevent unsafe hostPath or host namespace access. A workload that genuinely needs special privileges should run in an isolated namespace or node pool with explicit approval and stronger monitoring.

Admission is not a one-time gate. Policies need tests, version control, staged rollout and an audit trail. Emergency exceptions should expire. Namespace labels must be protected from application teams that could otherwise downgrade their own enforcement level. Cluster administrators also need separation: the ability to change admission policy should not silently include the ability to exfiltrate application secrets.

## Secrets need lifecycle controls

Kubernetes Secrets are objects whose values are encoded, not necessarily encrypted at rest by default. Enable encryption at rest with controlled key access, restrict who can read Secret objects and avoid putting secrets into container images, source control or ordinary logs. External secret managers can centralise rotation and auditing, but the workload identity that reads them becomes a sensitive credential.

A secret has a lifecycle: create, distribute, use, rotate, revoke and delete. Rotation without revoking the old value may leave a usable backdoor. Deleting a Kubernetes Secret does not remove copies from memory, process environments, backups or host mounts. Incident response must identify where a credential was used and revoke the underlying provider credential, not merely delete the cluster object.

Limit secret propagation. Prefer just-in-time delivery to a workload that needs one value over mounting every namespace secret into every pod. Protect the secret-delivery controller and its identity. Monitor reads, especially bulk list operations, and alert when a service account that normally performs no API calls begins retrieving secrets.

## Network policy is a distributed firewall with sharp edges

Network policies select pods and define allowed ingress and egress. Their effect depends on the cluster network plugin; a policy object that the plugin does not enforce provides false assurance. Default-deny policies establish a baseline, then explicit allows permit required traffic. Include DNS resolution, health checks, identity-provider calls, telemetry export and external APIs in the design so security changes do not create mysterious outages.

Separate ingress from service-to-service traffic. An ingress controller terminates public traffic and routes requests, but that does not authorise one internal service to call another. Apply workload identity and application authorisation in addition to network policy. For east-west traffic, deny by namespace or label and allow only required destinations and ports. For egress, restrict external destinations where practical and route traffic through controlled proxies or gateways.

TLS protects pod-to-pod traffic in transit, but certificate issuance, trust roots and rotation are part of the design. RFC 9846 describes the TLS 1.3 handshake and encrypted-record model. <Cite id="rfc9846" locator="§4.1–4.5" /> A service mesh can automate mutual TLS, but the trust domain, authorisation policy and certificate lifecycle still require ownership. A valid mesh certificate proves membership in a trust domain, not permission to invoke every operation.

## Node security and escape resistance

A container compromise becomes more serious when the container shares sensitive host resources. Keep nodes patched, reduce the agent and daemon surface, protect the kubelet and restrict host access. Use separate node pools for workloads with different privilege requirements. Treat nodes running privileged system components as high-value assets and limit administrative access to them.

Runtime detection should look for unexpected process execution, host mounts, namespace changes, kernel module loading, container escape attempts and access to node credentials. These signals need context: some are expected for node agents or debug pods. Record the workload, namespace, node and admission decision so analysts can distinguish authorised platform activity from an application container reaching the host.

## Test the cluster as an attacker would traverse it

Build a controlled red-team scenario that begins with a compromised application pod. Attempt to read its service-account token, call the API, list namespace secrets, reach a peer service and access the node filesystem. Compare observed behaviour with the intended trust-zone diagram. Repeat the scenario after policy changes. Verify that admission rejects an unsafe pod, that the API denies an unauthorised secret list and that network policy blocks a disallowed peer. Confirm the corresponding events arrive in central logging. A control that works but produces no usable evidence is difficult to operate; an alert without an enforced control merely records an avoidable compromise.

## Collect evidence from every plane

Cloud detection requires control-plane, identity, workload and network evidence. Cloud audit logs show API calls and policy changes. Kubernetes audit logs show requests to the API server, including actor, verb, resource, namespace and response status. Container runtime and endpoint telemetry show process execution, mounts and network connections. Network logs show flows even when payloads are encrypted.

Preserve event time and ingestion time. Cloud services, nodes and applications may have different clocks or delays. Use stable identifiers such as request IDs, principal ARNs, service-account UIDs, pod UIDs and trace IDs. Enrich events with asset owner, environment, data classification and expected deployment pipeline, but record enrichment freshness so stale context is not mistaken for current truth.

Protect the evidence plane. Central logging accounts, audit buckets and SIEM ingestion roles should be separate from workload administration. An attacker who can delete audit logs or change log sinks can blind the response. Alert on logging configuration changes, retention reductions and sudden gaps in expected event volume.

## Give every detection a telemetry acceptance test

A detection is a claim that a particular sequence should produce a usable alert from named evidence. Test the evidence path before tuning the rule. If Kubernetes audit omits response status, a rule cannot reliably distinguish a denied secret-list attempt from a successful read. If storage data events are disabled, an anonymous-read alert may detect only policy changes, not access.

| Detection hypothesis | Required evidence and joins | Benign fixture | Blind-spot test |
| --- | --- | --- | --- |
| An application service account begins listing Secrets | Kubernetes audit subject UID, verb, resource, namespace, response and workload baseline | A controller reconciling its own namespace | Disable a required audit field and confirm the rule reports degraded coverage |
| A deployment identity assumes a broader role | Cloud identity audit, assumed-role chain, pipeline identity and workload UID | Approved deployment using the expected role | Delay cloud events and verify correlation still respects the accepted time window |
| Pod enforcement is downgraded | Namespace label change, admission decision, resulting pod spec and pipeline record | Approved migration to a stronger profile | Remove the webhook log and confirm the missing-evidence condition is visible |

NIST's log-management guidance covers infrastructure, retention and review; incident-response guidance connects detection and analysis to tested playbooks. <Cite id="sp800-92" locator="§3–5 (log infrastructure, retention, review)" /> <Cite id="sp800-61r3" locator="§2–5 (incident response lifecycle and playbooks)" /> Retain raw events, track enrichment freshness and measure ingestion lag. Enriched summaries alone can hide the field loss that invalidates a detection.

Run each rule against a true-positive fixture, a realistic benign fixture, duplicates, late events and records missing optional fields. Validate the alert and analyst context: principal, resource, time window, evidence source and severity reason. A rule with a missing join key has failed its acceptance test even when its threat label is correct.

Measure coverage separately from alert volume. Track the percentage of relevant workloads emitting required events, resources with protected audit export and time from source event to queryable evidence. A quiet queue may mean low attack activity or a broken pipeline. Measure precision in the deployed account context, and assign an owner to every detection and its telemetry dependencies.

## Detect behaviour, not only known indicators

Useful detections express a hypothesis and name the evidence required. Examples include a service account that normally performs no API calls suddenly listing secrets; a deployment role creating an administrator policy; anonymous access to a bucket that normally has none; a pod mounting the host filesystem; and a workload contacting an unapproved external destination immediately after starting.

ATT&CK-style technique labels help communicate and organise coverage, but a tag alone does not prove a detection works. Test each rule with benign and malicious fixtures, including late events, duplicates and missing fields. Measure precision in the deployed environment. A public-bucket alert may be routine in a development account and critical in a regulated production account; severity should reflect asset context and data classification.

Zero-trust principles support detection and response as well as access control: make authorisation explicit, minimise privilege and continuously evaluate the context of access. <Cite id="sp800-207" locator="§2–3 (tenets and architecture)" /> In practice, that means alerting when a workload identity appears from a new network, when a session's permissions expand unexpectedly or when a resource policy changes outside the approved pipeline.

## Contain the identity, the workload and the route

Containment is not one button. Depending on the incident, responders may need to disable a compromised identity, revoke active sessions and tokens, quarantine a workload, block egress, remove a malicious admission exception, rotate a secret or restore a trusted policy. Each action has a different blast radius and evidence consequence.

Preserve volatile and durable evidence before destructive actions when active harm allows. Capture relevant audit records, pod specifications, container metadata, process and network state, image digests and configuration history. Record the collector, tool version, time zone, hash and storage location. If ransomware or active data theft demands immediate containment, contain first and document the evidence that could not be preserved.

Revoking a token does not necessarily invalidate every derived credential. Follow the credential chain: who assumed which role, which short-lived session was issued, which Kubernetes service account was used and which external secret was obtained. Rotate underlying secrets and remove persistence such as new IAM users, access keys, RoleBindings, admission exceptions, scheduled workloads or compromised image tags.

<Callout variant="lab" title="Containment changes the evidence">
Scaling a deployment to zero may remove malicious processes and their memory. Deleting a pod removes some runtime artefacts, though audit evidence remains. Define what must be captured first, who can authorise the trade-off and how the decision will be recorded.
</Callout>

## Recover trust, not just availability

A restarted service is not a recovered service. Recovery requires rebuilding from a known-good image, restoring reviewed policy, validating data integrity, rotating exposed credentials and confirming that the attacker cannot regain the same path. Compare the recovered configuration with the pre-incident baseline and the approved change history.

Use staged recovery for critical systems. Restore in an isolated environment, verify application behaviour and security controls, then gradually restore traffic. Keep heightened monitoring on the affected identities and resources. Confirm that backups are usable and that their restore process does not reintroduce the vulnerable policy or stale credential.

Post-incident review should turn findings into owned changes. If the attacker entered through a public bucket, fix the organisation guardrail and detection for anonymous reads. If a pod escalated through RBAC, review all principals with similar creation rights. If evidence was missing, improve audit export and retention. Closing the ticket without changing a control leaves the path open for the next attacker.

## Build an incident-ready control-plane runbook

A cloud runbook needs contacts as well as commands. Identify the incident commander, cloud account owner, Kubernetes platform owner, application owner, data owner, legal or privacy contact and communications lead. Define who can disable an identity, change a network policy, revoke a key or restore a backup. Record approval requirements for high-impact actions and a tested rollback for each.

Run tabletop exercises with realistic constraints: the identity provider is slow, audit export is delayed, the attacker is actively copying data and a proposed isolation would interrupt a critical service. The goal is not to memorise commands. It is to expose unclear authority, missing telemetry and recovery dependencies before a real incident.

Measure readiness with evidence: percentage of production workloads using short-lived identity, percentage of clusters enforcing restricted pod security, time to export a complete audit trail, number of standing administrator grants and success rate of recovery exercises. Track policy drift and expired exceptions. Metrics should reward removal of attack paths, not only deployment speed.

## Make the design review evidence-based

A design review should inspect real policies and real audit output. Ask the platform team to demonstrate an anonymous storage denial, an over-privileged role denial, an admission rejection and a network-policy block. Review the events produced by each test. Ask what happens when logging fails and who is alerted. This converts a checklist conversation into a repeatable engineering exercise.

Prioritise by attack path and asset value. A public development bucket may deserve a quick fix; a production deployment role that can attach administrator permissions may deserve emergency action. Avoid ranking every finding by a generic severity alone. Consider exploitability, reachable assets, data sensitivity, existing controls and business impact. Document residual risk with an owner and review date.

## Common failure modes

| Failure mode | Observable symptom | Root cause | Guardrail |
| --- | --- | --- | --- |
| Shared responsibility gap | Team assumes provider secures customer policy | No responsibility matrix or owner | Assign every layer and control to a named owner |
| Wildcard workload role | One pod can reach unrelated services and secrets | Convenience-based IAM grants | Derive narrow roles from observed actions |
| Public storage drift | Anonymous reads appear after a deployment | Bucket policy changed outside guardrails | Account-level public block and drift alerts |
| Long-lived credentials | Token reuse continues after pod deletion | Keys embedded in images or bundles | Short-lived workload identity and rotation |
| Unverified image provenance | New image digest appears without approval | Registry or pipeline access too broad | Signed artefacts, digest pinning and admission checks |
| Over-broad Kubernetes RBAC | Service account lists every namespace secret | ClusterRoleBinding to view or edit | Custom least-privilege Roles and token minimisation |
| Unenforced network policy | Blocked connection still succeeds | Plugin unsupported or selectors wrong | Verify enforcement and test positive and negative paths |
| Control-plane blind spot | Logs stop during an incident | Log sink editable by workload admins | Separate evidence account and protected retention |
| Token-only containment | Access resumes through another credential | Derived sessions and secrets not revoked | Trace and revoke the full identity chain |
| Availability-only recovery | Service returns but attack path remains | Restart treated as eradication | Rebuild, rotate, review policy and negative-test |

## Design review checklist

- [ ] Every cloud account, cluster, namespace and data service has an owner and data classification.
- [ ] Shared responsibility is documented for each managed service and operational task.
- [ ] Human, pipeline, workload and administrator identities are separated.
- [ ] Runtime roles are scoped to exact resources and derived from observed actions.
- [ ] Public storage is blocked by account or organisation guardrails, with reviewed exceptions.
- [ ] Workloads use short-lived identity; long-lived keys have owners, rotation and alerts.
- [ ] Images are pinned, signed, scanned and verified by admission policy.
- [ ] Ordinary pods meet restricted security requirements and avoid host access.
- [ ] Kubernetes RBAC uses narrow verbs and resources; pod creation is treated as privileged.
- [ ] Network policy is default-deny, enforced by the plugin and tested in both directions.
- [ ] Secrets have protected delivery, rotation, revocation and access auditing.
- [ ] Cloud, Kubernetes, runtime and network evidence reaches a protected central store.
- [ ] Containment follows the full identity chain and has an approved rollback path.
- [ ] Recovery verifies trusted artefacts, clean policy, data integrity and closed attack edges.
- [ ] Tabletop exercises include delayed logs, unavailable services and critical-business constraints.

## Key takeaways

- Cloud security is an attack-path problem across identities, APIs, workloads, networks and data.
- Shared responsibility varies by service; customer configuration and data remain customer concerns.
- IAM least privilege and short-lived workload identity reduce the edges available after compromise.
- Container security spans image provenance, registry access, admission, runtime privileges and the host.
- Kubernetes has cluster, node, workload and network planes; RBAC and pod creation require special scrutiny.
- Network policy and TLS complement, but do not replace, workload identity and application authorisation.
- Detection must correlate control-plane, identity, workload, network and data-access evidence.
- Containment revokes the full credential chain; recovery proves the original path is closed.
