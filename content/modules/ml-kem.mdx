## The shape of the problem

Alice publishes a public **encapsulation key**. Bob wants to agree on a fresh 32-byte secret. He runs an encapsulation routine that produces:

- a **ciphertext** that he sends to Alice, and
- a **shared secret** that he keeps.

Alice runs decapsulation on the ciphertext with her secret key. If everything is honest, she derives the same 32 bytes. An eavesdropper sees only the public key and the ciphertext.

## Why noise is the feature

ML-KEM's security rests on **Module-LWE**: recovering a secret from noisy linear equations over a polynomial ring is believed to be hard, even for quantum computers. The noise is not an implementation defect; it is the hardness.

The engineering challenge is that Alice's reconstructed value is slightly noisy. ML-KEM solves this with rounding and a reconciliation step: the message is encoded far apart in the coefficient space, so small errors still decode correctly. <Cite id="fips203" locator="§4.2.1" />

<Callout variant="note" title="One byte of intuition">
Imagine encoding a single bit as “near 0” or “near half the modulus”. Add a little noise: the point wobbles, but it stays in the correct half. Only if the noise crosses the midpoint does the bit flip. ML-KEM keeps that probability astronomically small.
</Callout>

## Why the re-encryption check matters

A naive noisy KEM is only secure against passive attackers. An active attacker can submit malformed ciphertexts and watch how the victim responds. The **Fujisaki–Okamoto transform** closes that hole: decapsulation re-encrypts the recovered message and compares the result with the received ciphertext. If they differ, it returns a pseudorandom rejection key rather than an error. <Cite id="fujisaki-okamoto2013" locator="Vol. 26, pp. 80–101" />

## A real session

A browser opens a TLS 1.3 connection to a server that supports X25519MLKEM768. The client sends an X25519 share and an ML-KEM-768 encapsulation key; the server returns its X25519 share and an ML-KEM ciphertext. Both derive a hybrid secret and use it to key the record layer.

The attacker records the ciphertext. Today, deriving the key requires solving Module-LWE. After a cryptographically relevant quantum computer exists, Shor's algorithm does not apply to Module-LWE; the recorded ciphertext remains hard under the best known attacks. That is the migration argument in one paragraph.

## Threat model and deployment scenario

ML-KEM targets an IND-CCA-secure key encapsulation mechanism. The adversary sees the public key, may obtain many encapsulations, and may submit chosen ciphertexts to a decapsulation oracle. It must not distinguish the shared secret from random or recover information about the decapsulation key. The defender must return the same key on honest ciphertexts and make every rejected ciphertext produce an output that looks like an independent secret to the attacker.

A TLS terminator is a realistic implementation boundary. It receives an ML-KEM-768 encapsulation key in a client hello, encapsulates with fresh randomness, and later decapsulates a ciphertext under its long-lived key. The network attacker can truncate, duplicate and modify handshake messages. A local tenant may be able to trigger repeated decapsulations and observe response time. The endpoint must authenticate the peer through the surrounding protocol, but the KEM itself must not become a ciphertext-validity oracle before that authentication completes.

Defender goals include canonical parsing, strict length checks, constant-time re-encryption and secret-key protection. A 1,088-byte ciphertext is not valid merely because a buffer is that long; every component must decode according to its compression depth. The decapsulation key contains a cached hash of the encapsulation key and a secret rejection value. Either value must remain bound to the correct key during import, backup and rollback.

Misconceptions obscure the security boundary. Compression is not encryption and does not add security; it reduces bandwidth while consuming correctness margin. The FO transform does not repair a broken random-number generator, a leaked secret key or a ciphertext comparison that exits early. Hybrid deployment does not make an unsafe ML-KEM implementation safe; both components must be implemented correctly. Finally, the tabulated decapsulation failure rate is a correctness bound, not an estimate of an attacker's success probability.

Availability is also worth stating. A decapsulation call should always produce a 32-byte value for a ciphertext of the expected length under the standard interface. The surrounding protocol may later fail authentication, but that is different from exposing a KEM error. Buffer allocation failure or an internal key-format error can stop the process; ordinary ciphertext rejection cannot. This distinction prevents a chosen-ciphertext oracle and gives the protocol a clean interface.

## The parameter set

ML-KEM uses $n = 256$, $q = 3329$, and a module rank $k \in \{2,3,4\}$. The public key contains a matrix $\hat{A}$ in NTT form and the vector $\hat{t}$; the secret key contains $\hat{s}$. Key generation, encapsulation and decapsulation are specified in FIPS 203 Sections 7.1–7.3. <Cite id="fips203" locator="§7.1–7.3" />

| Parameter set | $k$ | $\eta_1$ | $\eta_2$ | $d_u$ | $d_v$ | failure rate |
| --- | --- | --- | --- | --- | --- | --- |
| ML-KEM-512 | 2 | 3 | 2 | 10 | 4 | $2^{-138.8}$ |
| ML-KEM-768 | 3 | 2 | 2 | 10 | 4 | $2^{-164.8}$ |
| ML-KEM-1024 | 4 | 2 | 2 | 11 | 5 | $2^{-174.8}$ |

The round-3 CRYSTALS-Kyber specification documents the same design, NTT representation and reference pseudocode. <Cite id="kyber-spec" locator="§2.3–2.4" />

## Encapsulation

1. Sample a 32-byte message $m$.
2. Derive $(K, r) = G(m \,\|\, H(ek))$ using SHA3-256 and SHAKE256. <Cite id="fips202" locator="§6" />
3. Run K-PKE.Encrypt with randomness $r$ to obtain $c$.
4. Output $(c, K)$.

## Decapsulation

1. Decrypt $c$ to recover $m'$ (with possible noise).
2. Recompute $(K', r') = G(m' \,\|\, H(ek))$.
3. Re-encrypt $m'$ under $r'$ to obtain $c''$.
4. Compare $c''$ with $c$ in constant time.
5. Return $K'$ on equality; otherwise return $J(z \,\|\, c)$ for a secret rejection value $z$.

The re-encryption step is the FO transform. The comparison must not exit early, and the rejection path must not be distinguishable by timing. <Cite id="fips203" locator="§7.3" />

## Compression

The ciphertext components are rounded to fewer bits:

$$
c_1 = \mathsf{Compress}_{d_u}(u), \qquad c_2 = \mathsf{Compress}_{d_v}(v).
$$

Decompression reconstructs an approximation. The parameters choose $d_u, d_v$ so the rounding error plus the LWE noise stays inside the decoding regions. Coarser compression saves bytes and consumes correctness margin.

## Decapsulation step by step

Given a well-formed ciphertext $c$:

1. Decrypt to $m'$, accepting that the result may be noisy.
2. Compute $H(ek)$ and derive $(K', r') = G(m' \| H(ek))$.
3. Re-encrypt $m'$ with randomness $r'$ to obtain $c''$.
4. Compare $c''$ and $c$ in constant time.
5. If equal, return $K'$; otherwise return $J(z \| c)$.

The comparison is over the entire ciphertext, not just a tag. The rejection key is derived from a secret $z$ stored in the decapsulation key, so an attacker cannot distinguish a tampered ciphertext from a valid one by observing the output.

## Compression worked example

For a coefficient $v$, compression computes

$$
\mathsf{Compress}_d(v) = \mathsf{round}\left(\frac{2^d}{q}v\right) \bmod 2^d,
$$

and decompression reverses the rounding. With $q=3329$ and $d=10$, the compressed value has 10 bits and the reconstruction error is at most about $q/2^{11} \approx 1.6$. ML-KEM uses $d=10$ for the vector component and $d=4$ for the message polynomial in the smaller parameter sets; the larger set uses different values to preserve correctness. <Cite id="fips203" locator="Table 2" />

<Callout variant="warning" title="Compression is part of correctness">
Coarser compression saves bytes but increases the chance that noise crosses a reconciliation boundary. Parameter choice is a joint optimisation of size, failure probability and security.
</Callout>

## Byte layout and an implementation walkthrough

For rank $k$, the encapsulation key is $384k+32$ bytes, the ciphertext is $32kd_u+32d_v$ bytes, and the expanded decapsulation key is $768k+96$ bytes. The extra 32 bytes in the public key encode the matrix seed; the decapsulation key includes the encoded private key, public key, public-key hash and rejection seed. These sizes explain why a seemingly simple KEM interface still needs careful buffer ownership.

Key generation samples a 32-byte seed $d$ and derives $\rho$ and $\sigma$ through the specified hash. Matrix entries are sampled and rejected until canonical coefficients in $[0,q)$ are obtained. The secret and error vectors are sampled from centered binomial distributions, transformed to the NTT domain, and combined as $\hat t=\hat A\hat s+\hat e$. The expanded key must be checked for internal consistency on import rather than trusting an arbitrary byte string of the correct length.

Encapsulation uses a fresh 32-byte message, not a caller-chosen nonce. The hash $G(m\|H(ek))$ binds the random message to the public key. K-PKE then samples short $r,e_1,e_2$, computes $u$ and $v$, compresses both vectors, and packs the coefficients into the exact ciphertext layout. The returned shared secret is the $K$ value from $G$. There is no separate authentication tag: integrity checking during decapsulation comes from deterministic re-encryption under the FO transform.

Decapsulation first decompresses the received components. It computes $m'=\mathsf{Decode}_1(v-s^Tu)$, hashes $m'$ with the cached public-key hash, re-encrypts deterministically with the derived $r'$, and compares the entire result with $c$. Only after the comparison mask is known should the caller select between $K'$ and $J(z\|c)$. Implementations commonly compute both candidates before selection so that failure does not shorten the observable path.

## The underlying problem

Let $R_q = \mathbb{Z}_q[X]/(X^{256}+1)$. Module-LWE with rank $k$ gives samples

$$
(\mathbf{a}_i, \langle \mathbf{a}_i, \mathbf{s} \rangle + e_i) \in R_q^k \times R_q,
$$

where $\mathbf{s}$ is a secret module vector and $e_i$ is small. The decisional problem is to distinguish these samples from uniform. Worst-case-to-average-case reductions connect module lattices to hard lattice problems. <Cite id="regev2009" locator="Vol. 56, Article 34" /> <Cite id="lpr2010" locator="pp. 1–23" /> <Cite id="langlois-stehle2015" locator="Vol. 75, pp. 565–599" />

## K-PKE in three equations

Key generation samples $\hat{A}$, secret $\hat{s}$, and error $\hat{e}$, and sets

$$
\hat{t} = \hat{A}\hat{s} + \hat{e}.
$$

Encryption samples short $r, e_1, e_2$ and computes

$$
u = \mathsf{NTT}^{-1}(\hat{A}^T \hat{r}) + e_1, \qquad
v = \mathsf{NTT}^{-1}(\hat{t}^T \hat{r}) + e_2 + \mathsf{Decompress}_1(m).
$$

Decryption computes $v - s^T u$ and decodes the message. The noise term is small with overwhelming probability; the parameters are chosen so that it stays below the decoding threshold.

## Correctness

The decryption error is a sum of products of small coefficients. A standard bound shows that, for the standardized parameters,

$$
\Pr[\text{decapsulation failure}] \le 2^{-138.8}\ \text{(ML-KEM-512)}, \quad 2^{-164.8}\ \text{(ML-KEM-768)}, \quad 2^{-174.8}\ \text{(ML-KEM-1024)}.
$$

These are the values tabulated in FIPS 203 Table 1. <Cite id="fips203" locator="Table 1" /> The bound assumes hash functions behave like random functions and that randomness generation succeeds.

## The FO transform

Let $\mathsf{PKE} = (\mathsf{KeyGen}, \mathsf{Enc}, \mathsf{Dec})$ be CPA-secure. Define

$$
\begin{aligned}
\mathsf{Encaps}(ek):&\quad m \leftarrow \{0,1\}^{256},\quad (K,r) = G(m \,\|\, H(ek)),\\
&\quad c = \mathsf{Enc}(ek, m; r),\quad \text{output } (c,K),\\
\mathsf{Decaps}(dk,c):&\quad m' = \mathsf{Dec}(dk,c),\quad (K',r') = G(m' \,\|\, H(ek)),\\
&\quad c'' = \mathsf{Enc}(ek,m';r'),\quad \text{return } K' \text{ if } c''=c \text{ else } J(z,c).
\end{aligned}
$$

The modular analysis of Hofheinz, Hövelmanns and Kiltz explains which properties of $G$, $H$, $J$ and the PKE are needed for IND-CCA2 in the random oracle model. <Cite id="hofheinz2017" locator="pp. 341–371" /> The important engineering consequence is that the rejection path must be indistinguishable from success.

## Correctness and failure probability

Decryption succeeds if the accumulated noise stays inside the correct reconciliation region. A standard analysis bounds the noise as a sum of products of small coefficients; the failure rates in FIPS 203 are $2^{-138.8}$ for ML-KEM-512, $2^{-164.8}$ for ML-KEM-768 and $2^{-174.8}$ for ML-KEM-1024. <Cite id="fips203" locator="Table 1" />

These are not cryptographic security levels; they are correctness probabilities. The FO transform handles a failure by returning a rejection key, so a rare correctness failure does not become a decryption oracle.

## The FO argument in detail

The re-encryption check binds the ciphertext to the message and randomness. If an attacker modifies $c$, decryption produces an unrelated $m'$, re-encryption produces $c'' \ne c$, and the output is the rejection key. The attacker cannot tell whether the ciphertext was valid without solving the underlying problem or breaking the hash/KDF assumptions. <Cite id="hofheinz2017" locator="pp. 341–371" />

The proof is in the random-oracle model and requires domain separation between $G$, $H$ and $J$. Using the same hash inputs for different purposes can break the argument.

## Correctness as a norm inequality

Write the uncompressed K-PKE equations in the coefficient domain as

$$
u=A^Tr+e_1,\qquad v=t^Tr+e_2+\mathsf{Decompress}_1(m),\qquad t=As+e.
$$

An honest decryption therefore forms

$$
v-s^Tu=e_2+s^Te_1-e^Tr+\mathsf{Decompress}_1(m).
$$

This identity exposes every source of disturbance: encryption error, secret times ephemeral error, public-key error times ephemeral secret, and the encoded message. If decompression reconstructs $u+\delta_u$ and $v+\delta_v$, the decoded value contains the additional term $\delta_v-s^T\delta_u$. The subtraction is exact in the field; the error analysis is over centered integer representatives before reduction.

For each coefficient, decoding succeeds when the total disturbance stays inside the region closer to the intended codeword than to the competing codeword. A sufficient per-coefficient condition is an absolute error below $q/4$. The proof must bound the maximum over all message coefficients, not merely an average. It uses componentwise bounds for binomial samples, products and sums, then combines them with compression-error bounds and a union argument over the coefficient positions. <Cite id="fips203" locator="Table 1" />

Compression error is bounded by $q/2^{d_u+1}$ per coefficient of $\delta_u$ and $q/2^{d_v+1}$ for $\delta_v$. Multiplying $\delta_u$ by the secret amplifies it by secret coefficients, which is why reducing $d_u$ is not a free bandwidth optimisation. The standard's failure bounds already account for the selected parameter sets. Changing a noise distribution, root representation, rounding rule or compression depth invalidates that bound even if a small sample of keys still decapsulates.

The reduction to Module-LWE is an average-case argument. Public samples $(A,t)$ hide short secret and error vectors; the error distribution is what makes the noiseless linear system unhelpful. A reduction must transform a Module-LWE distinguisher into an IND-CPA attacker against K-PKE, with a loss determined by the error bounds and number of samples. Module-SIS hardness and lattice reductions support the surrounding parameter analysis. <Cite id="regev2009" locator="Vol. 56, Article 34" /> <Cite id="langlois-stehle2015" locator="Vol. 75, pp. 565–599" />

The FO transform upgrades the passive setting to chosen-ciphertext security. In the random-oracle reduction, $G$ is programmed to derive coins consistently, $H$ binds the public key, and $J$ provides an independent rejection key. A decapsulation query either re-encrypts exactly, in which case it can be simulated, or yields an implicit rejection value. Domain separation is essential so that a hash query from encapsulation cannot silently answer a re-encryption query. <Cite id="hofheinz2017" locator="pp. 341–371" />

Implicit rejection also handles the tiny correctness event where the recovered message is wrong. If a noisy decode changes $m$, the derived randomness changes, so the re-encrypted ciphertext almost certainly differs. Returning $J(z\|c)$ avoids revealing that correctness failure. An implementation that returned a distinct error, skipped re-encryption, or compared only a prefix would destroy this argument.

Edge cases sharpen the model. The input must have exactly the expected length; allocation or internal key corruption may be fatal, but an ordinary wrong ciphertext must not be. Public-key coefficients must be canonical before use. The comparison must cover every ciphertext byte, including unused padding bits if the encoding defines them. Secret-key rollback must restore the matching rejection seed. If two operations share an output buffer, wipe or overwrite the previous key so a protocol layer cannot mistake a rejection key for an earlier success.
</Lens>

## The hot loops

ML-KEM's performance is dominated by:

1. **Keccak** for SHA3-256, SHA3-512 and SHAKE128/256. The XOF calls in matrix sampling and key derivation are substantial. <Cite id="fips202" locator="§3" />
2. **NTT and inverse NTT** for polynomial multiplication. <Cite id="longa2016" locator="pp. 124–139" />
3. **Sampling** from centered binomial distributions without secret-dependent branches.
4. **Compression/decompression** and constant-time encoding.

## Constant-time rules

FIPS 203 Section 3.3 imposes implementation requirements. In practice that means:

- no secret-dependent branches in decapsulation,
- no secret-indexed table lookups,
- constant-time comparison of the re-encrypted ciphertext,
- deterministic handling of malformed inputs,
- no floating-point arithmetic in the reference data path.

The rejection key must be computed and selected without leaking whether rejection occurred.

<Callout variant="danger" title="The compiler is not your friend">
A branch that looks constant-time in C can be turned into a conditional move or a jump by the optimiser. Validate the generated code or use established constant-time primitives. Test with tools such as `dudect`, `valgrind`/ctgrind and hardware side-channel evaluation.
</Callout>

## Performance engineering

- **AVX2** packs 16-bit coefficients and vectorises butterflies across independent blocks.
- **Arm NEON/SVE** uses a different lane layout; twiddle handling is often the bottleneck.
- **Montgomery/Barrett** reductions replace division in the inner loop. <Cite id="montgomery1985" locator="Vol. 44, pp. 519–521" />
- **Keccak accelerators** (SHA-3 extensions, dedicated blocks) can change the performance balance entirely.
- **In-place buffers** reduce RAM pressure on embedded targets.

## Memory and protocol reality

A decapsulation key is 2,400 bytes for ML-KEM-768; an encapsulation key is 1,184 bytes. Hybrid TLS adds these to a handshake that previously carried a 32-byte X25519 share. Firmware and HSMs need larger command buffers. Embedded devices need stack budgets measured in kilobytes, not megabytes.

## Testing strategy

3. **Fuzzing** of decoders and length checks.
4. **Constant-time verification** and leakage assessment.
5. **Interoperability tests** across libraries and protocol stacks.

## Implementation detail: where the cycles go

ML-KEM spends time in Keccak (matrix sampling, key derivation), NTT/inverse NTT, sampling from centered binomial distributions, and compression/encoding. Optimising only the NTT may leave most of the cost untouched. Measure the whole operation.

- **Keccak:** SHA3-256, SHA3-512 and SHAKE128/256; hardware acceleration changes the balance.
- **NTT:** 7 layers with 128 butterflies each, plus base-case multiplication.
- **Sampling:** rejection sampling for matrix entries; must be constant-time or use a fixed number of attempts.
- **Encoding:** bit packing and compression must reject malformed input.

<Callout variant="danger" title="The comparison must be constant-time">
An early-exit comparison leaks how many bytes matched. The rejection key must be computed and selected without a branch on the comparison result.
</Callout>

## From reference code to a hardened service

Use a clear ownership model for buffers. The caller owns the encapsulation or decapsulation key; the implementation owns only bounded temporary workspaces. Allocate enough space for the largest parameter set if a library supports all three, or compile the rank into the API so a caller cannot pass a 1,088-byte ciphertext to a 768-byte decoder. Never infer the parameter set from untrusted length alone.

Compute $H(ek)$ once when importing a key and store it in protected key state. During decapsulation, decompress, decode, derive, re-encrypt and compute $J(z\|c)$ without branching on recovered coefficients. A useful implementation pattern accumulates byte differences with bitwise OR and converts the final zero/nonzero value to a selection mask. Both candidate keys exist before the select. The surrounding protocol may perform ordinary branching after the KEM returns, because by then the observable choice no longer distinguishes acceptance from rejection.

Sampling deserves the same scrutiny as multiplication. Rejection sampling of matrix entries has a public target range, but loop control must be fixed-work or otherwise independent of secret values. Centered binomial sampling should use byte loads and bit arithmetic rather than a table indexed by random or secret data. The random message and nonce expansion come from an approved random source; an HSM should attest to that capability rather than silently falling back to a deterministic counter.

For performance, maintain separate counters for key generation, encapsulation, decapsulation, hashing, NTT, sampling and encoding. Decapsulation is usually more expensive because it repeats encryption. Benchmark with the exact compiler, CPU features and Keccak backend used in deployment. Disassembly review should cover modular reduction, ciphertext comparison and rejection selection. Static taint analysis should mark the secret key and rejection seed as tainted and flag any branch or address derived from them.

Hardware brings buffer and lifecycle constraints. An HSM command that accepted a 32-byte classical public key may now truncate a 1,184-byte ML-KEM key. Firmware stacks need measured headroom for the expanded decapsulation key, ciphertext, public key, hash state and two candidate outputs. Import and export operations should be authenticated, and key deletion should wipe both the secret vector and rejection seed.

Build a negative test corpus before deployment. Include every wrong length, non-canonical public coefficients, truncated final bytes, all-zero and all-one ciphertexts, and single-bit flips near both ends. Compare decapsulation against an independent implementation. Then inject internal failures, such as a corrupted recovered message, to confirm that the service returns only the rejection key and never an error observable to the remote party.

Monitor aggregate decapsulation time and failure-related handshake outcomes without logging ciphertexts or keys. A latency change after a library update can indicate an early-exit regression even when functional tests pass. Re-run the full leakage assessment after changing compilers, CPU features, crypto providers or HSM firmware. Keep the constant-time reference result available for differential debugging, but do not ship a scalar fallback selected by secret data.
</Lens>

## Common failure modes

| Failure | Cause | Impact | Prevention |
| --- | --- | --- | --- |
| Rejection returns an error | Wrapper translates the KEM result | Chosen-ciphertext oracle | Keep the standard 32-byte interface |
| Comparison exits early | `memcmp` or a manual early break | Timing reveals matching prefix | Compare every byte with bitwise accumulation |
| Rejection key skipped | Rejection selected before $J$ is computed | Success path does more work | Compute both candidates unconditionally |
| Wrong key hash or rejection seed | Imported key components are mismatched | Incorrect keys and broken rejection privacy | Validate expanded-key consistency on import |
| Non-canonical coefficients accepted | Decoder reduces values instead of rejecting | Ambiguous public-key encoding | Check every coefficient is below 3329 |
| Randomness failure is hidden | Fallback repeats a counter or message | Loss of encapsulation security | Fail closed and attest to the random source |
| Ciphertext buffer is truncated | HSM or firmware still uses classical key sizes | Interoperability failure or memory fault | Measure and test maximum parameter-set buffers |
| Compression depth is changed | Custom bandwidth optimisation | Correctness bound no longer applies | Use standard parameters and re-run KATs |

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Valid peer ciphertext always rejects | Wrong public-key hash, key pair or parameter set | Compare imported key hashes and test a known vector |
| Rejection is measurably faster | Early comparison or skipped re-encryption | Compute both paths and select by mask |
| Only certain bit patterns fail | Rounding, NTT root or compression implementation differs | Compare stage outputs with an independent implementation |
| Crashes occur only on short input | Length is checked after buffer access | Validate exact length before decoding |
| HSM reports a command error | Public key or ciphertext exceeds its legacy buffer | Update command schema and test maximum sizes |
| Handshake fails after KEM success | Hybrid secret ordering or transcript binding differs | Check protocol combinator and key-schedule inputs |

## Design review checklist

- [ ] The parameter set is fixed and exact key and ciphertext lengths are enforced.
- [ ] Public-key coefficients are canonical and malformed encodings fail deterministically.
- [ ] Encapsulation uses a fresh random message and the specified key-bound hash derivation.
- [ ] Decapsulation computes re-encryption and the rejection key without early exits.
- [ ] The comparison covers the complete ciphertext and selection is branch-free.
- [ ] Secret key, public-key hash and rejection seed stay bound during import and rollback.
- [ ] Centered-binomial and rejection sampling have bounded, reviewed control flow.
- [ ] Compression, decompression and rounding match the standard at boundaries.
- [ ] Known-answer, differential, malformed-length and bit-flip tests pass.
- [ ] Exact binaries pass taint, assembly and statistical timing review.
- [ ] Hybrid handshake sizes, HSM buffers and firmware memory have measured headroom.

## Key takeaways

- ML-KEM is a Module-LWE KEM wrapped by the FO transform.
- Encapsulation returns a ciphertext and a 32-byte shared secret.
- Decapsulation re-encrypts and compares in constant time; on mismatch it returns an implicit rejection key.
- Correctness relies on bounded noise and compression parameters.
- Real performance is dominated by Keccak, NTT and sampling, not by a single loop.
