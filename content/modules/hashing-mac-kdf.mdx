## Three jobs, three tools

Hash functions, message authentication codes and key derivation functions look similar at the API level, but they answer different questions:

- **Hash:** "Is this data the same as that data?" A fingerprint.
- **MAC:** "Did someone with the secret key produce or approve this data?" A seal.
- **KDF:** "How do I turn one secret or password into several strong keys?" A key factory.

Confusing them is a classic source of vulnerabilities. A plain hash is not a MAC, and a fast hash is not a password-storage function.

## Why hashes look random

A cryptographic hash compresses arbitrary input into a fixed-size output. Good hashes are preimage-resistant, second-preimage-resistant and collision-resistant. A one-character change should flip about half the output bits.

## Three properties, three different attacker tasks

The properties are easiest to remember by what the attacker is given. In a **preimage** attack, the attacker receives a target digest $y$ and must find any $x$ with $H(x)=y$. In a **second-preimage** attack, the attacker receives a particular message $x$ and must find a different $x'$ with the same digest. In a **collision** attack, the attacker chooses both messages and must find any distinct pair $x,x'$ with $H(x)=H(x')$.

The distinction changes both the defence and the application. A file-integrity check against a trusted digest mainly needs second-preimage resistance: the attacker should not be able to substitute different content for that specific file. A commitment or hash tree needs collision resistance: the defender may eventually publish or authenticate either member of a pair. A password verifier is not protected merely by collision resistance, because the attacker is not trying to collide with a stored digest; they are guessing the low-entropy password directly.

| Task | Attacker starts with | Must produce | Generic classical work for an $n$-bit ideal hash | Typical use |
| --- | --- | --- | --- | --- |
| Preimage | A target digest | One matching input | About $2^n$ | Recovering input from a committed digest |
| Second preimage | A chosen input and its digest | A different matching input | About $2^n$ | Substituting content under a trusted fingerprint |
| Collision | Freedom to choose both inputs | Any equal-digest pair | About $2^{n/2}$ | Commitments, hash trees and signature preprocessing |
| MAC forgery | A verification key and chosen message/tag pairs | A fresh valid tag | Depends on tag and key, not hash collision work alone | Authenticating protocol messages |

These are generic attack models, not proofs that a particular hash reaches the bound. Structure-specific cryptanalysis can do better, which is why algorithm selection and migration matter. The random-looking appearance of one digest says nothing about resistance to a chosen-prefix collision.

Entropy explains why a KDF cannot repair every weak input. A password with $h$ bits of min-entropy has at most $2^h$ plausible values from the defender’s perspective, even if its textual representation is long. HKDF can concentrate existing entropy into a uniform-looking key; it cannot create more of it. A password-hashing function instead makes each guess expensive, while a salt prevents one computation from being reused across many accounts. <Cite id="rfc5869" locator="§3.4, §4" />

## Passwords are not hashes

Passwords are low-entropy, reused and often breached. Storing a fast hash such as SHA-256 lets an attacker test guesses at very high rates. Password storage needs a salted, memory-hard function with a tunable work factor — Argon2id is the modern default. <Cite id="owasp-password-storage" locator="Password Hashing Algorithms → Argon2id; Using Work Factors" />

<Callout variant="danger" title="Never invent password storage">
`SHA256(password + salt)` is not password hashing. Use Argon2id, scrypt or bcrypt through a vetted library, with a unique salt per password and appropriate memory/time parameters. <Cite id="rfc9106" locator="§3–4" />
</Callout>

## The questions these tools answer

- **Integrity:** “Did this file change after the publisher signed the hash?” A hash detects accidental or unsophisticated modification, but an attacker who can replace both the file and the published hash defeats it. Signatures or a trusted channel are needed for adversarial integrity.
- **Authentication:** “Did someone holding the shared key produce this message?” A MAC answers this; a plain hash does not.
- **Password verification:** “Does this password match the stored verifier?” This needs a salted, slow, memory-hard function, not a general-purpose hash.

<Callout variant="danger" title="A hash is not a password vault">
A SHA-256 digest of a password can be computed at very high rates on a GPU. Salting prevents precomputation but does not make a fast hash suitable. Use Argon2id, scrypt or bcrypt with tuned parameters. <Cite id="rfc9106" locator="§3–4" />
</Callout>

## Model two different adversaries

A software publisher distributes an update and publishes its digest separately. A network attacker controls a mirror and wants to replace the binary; a compromised mirror wants the replacement to look legitimate. A plain digest detects accidental corruption, but if the attacker replaces both file and digest, it proves no origin. The defender needs an authenticated channel or signature. The publisher wants cheap distribution; the attacker wants downstream code execution.

A password database is different. After a breach, the attacker works offline with GPUs and dictionaries. The defender cannot observe guesses and must verify many legitimate users concurrently. A unique salt defeats one precomputed table; a costly function raises per-guess work. Defender availability and attacker hardware therefore shape the work factor. OWASP treats algorithm, salt and tuning as one decision. <Cite id="owasp-password-storage" locator="Password Hashing Algorithms → Argon2id; Using Work Factors" />

The two adversaries also imply different failure criteria. For software distribution, the defender must preserve an authentic reference across time and compromise; hashing alone is only an accidental-corruption check. For passwords, the defender assumes the verifier database will eventually be read and asks how much work each guess will cost after that event. This is why “we use SHA-256” answers neither question completely: it names a fast primitive without specifying who authenticates the digest, how the password is stretched or how the system responds when the stored verifiers leak.

The prerequisites are bitstrings, XOR, fixed-size outputs and computational work. Collision work scales with the square root of output size; preimage work scales with output size. Keep three boundaries clear: a hash does not authenticate without a trusted reference; a MAC authenticates within a shared-key domain, not a person; a password hash slows guessing without adding entropy.

## Hash families

- **SHA-2** (SHA-256, SHA-512) is standardised, widely deployed and hardware-accelerated on many CPUs.
- **SHA-3 / Keccak** uses a sponge construction and provides SHAKE extendable-output functions. <Cite id="fips202" locator="§3, §6" />
- **BLAKE2/3** are fast modern alternatives common in file integrity and password hashing contexts.

## Padding, sponge rates and domain separation

SHA-256 pads to a 512-bit boundary: append one `1` bit, then the smallest non-negative number of zero bits that makes the length congruent to 448 modulo 512, then the original message length as a 64-bit big-endian integer. SHA-256 accepts messages shorter than $2^{64}$ bits. For the three-byte message `abc`, the length is 24 bits, so padding is one `1` bit, 423 zero bits and the 64-bit encoding of 24. The length field is security-relevant metadata, not decorative framing. <Cite id="fips180-4" locator="§5.1.1, §6.2" />

SHA-3 instead absorbs input into a 1,600-bit sponge state at a specified rate and squeezes output from that state. SHA3-256 uses a 512-bit capacity; SHAKE128 and SHAKE256 use capacities of 256 and 512 bits. SHAKE is an extendable-output function: the caller must specify the output length. “SHAKE128” names a security-strength parameter, not a 128-bit digest, and its collision resistance depends on the requested output length. The `01` suffix for SHA-3 and `1111` suffix for SHAKE provide domain separation inside the standardized functions. <Cite id="fips202" locator="§5.2, §6.1–6.3" />

That internal separation does not replace application-level separation. Two protocols can still feed the same bytes into SHAKE and ask for the same output length. If the resulting value is used as a key, the protocol must bind its own name, version, direction and purpose before hashing. A hash function only separates domains that its input encoding distinguishes.

| Interface | Fixed or caller-selected output | Critical encoding detail | Common misuse |
| --- | --- | --- | --- |
| SHA-256 | 256 bits | 512-bit blocks; 64-bit big-endian message length | Treating it as a password verifier |
| SHA-512 | 512 bits | 1,024-bit blocks; 128-bit big-endian message length | Assuming a longer digest fixes low-entropy passwords |
| SHA3-256 | 256 bits | Sponge suffix `01`; rate 1,088 bits | Confusing SHA3-256 with raw Keccak-256 |
| SHAKE256 | Caller-selected | Output length in bits; sponge suffix `1111` | Omitting the length from the protocol contract |
| HMAC-SHA-256 | 256 bits before optional truncation | Hash block size is 64 bytes | Prefixing the secret without the nested construction |
| HKDF-SHA-256 | Up to $255\times32=8{,}160$ bytes | Previous block plus `info` plus one-byte counter | Omitting the previous block or allowing ambiguous `info` |
| Argon2id | Caller-selected tag | Algorithm version, salt, memory, passes and lanes all affect output | Trusting attacker-controlled cost parameters |

## MACs

<Figure caption="HMAC authenticates with an inner and outer pad; HKDF extracts and expands key material into purpose-specific keys.">
  <HmacHkdfFlow />
</Figure>

A MAC authenticates a message under a secret key. HMAC is the standard construction built from a hash:

$$
\mathrm{HMAC}_K(M) = H\big((K \oplus \mathrm{opad}) \,\|\, H((K \oplus \mathrm{ipad}) \,\|\, M)\big).
$$

HMAC remains secure even when the underlying hash has some weaknesses, as long as it is a reasonable hash. <Cite id="rfc2104" locator="§2–3, §6" /> Never replace HMAC with `H(K || M)`; length-extension attacks apply to many Merkle–Damgård hashes.

The block size belongs to the hash, not to the output size. HMAC-SHA-256 and HMAC-SHA-512 use 64-byte and 128-byte blocks respectively. A key longer than the block is hashed; a shorter key is zero-padded. An implementation may precompute the compression states after the inner and outer pads, but those states are key-equivalent secrets and need the same protection as the key. <Cite id="rfc2104" locator="§2, §4" />

## KDFs

HKDF extracts a uniform key from input keying material and expands it into purpose-specific keys:

$$
\mathrm{PRK} = \mathrm{HMAC}_{\mathrm{salt}}(\mathrm{IKM}), \qquad
\mathrm{OKM} = \mathrm{HKDF\text{-}Expand}(\mathrm{PRK}, \mathrm{info}, L).
$$

The `info` field is your domain separation: protocol, direction, algorithm, version. <Cite id="rfc5869" locator="§2.3, §3.2" /> It is public context, not secret key material, and RFC 5869 requires it to be independent of the IKM value. An omitted salt is defined as HashLen zero bytes, but a random or protocol-derived salt can strengthen extraction and separate uses. If a salt comes from handshake nonces, those nonces need authentication before they can serve as trusted context. <Cite id="rfc5869" locator="§2.2, §3.1, §3.4" />

## Password hashing

Argon2id combines data-independent and data-dependent memory access, making it resistant to some side-channel and GPU attacks. Parameters should be chosen so one verification is expensive for the defender but acceptable for the service. <Cite id="rfc9106" locator="§3–4" />

| Use | Recommended primitive |
| --- | --- |
| File integrity | SHA-256 / SHA-512 / BLAKE3 |
| Message authentication | HMAC-SHA-256 |
| Key derivation | HKDF |
| Password storage | Argon2id / scrypt / bcrypt |
| Random tokens | CSPRNG, not a hash |



## HMAC and HKDF step by step

HMAC is defined by two nested hash evaluations:

$$
\mathrm{HMAC}_K(m) = H\big((K \oplus \mathrm{opad}) \,\|\, H((K \oplus \mathrm{ipad}) \,\|\, m)\big).
$$

The inner hash processes the keyed message; the outer hash protects the result from length extension. Verification must compare the full tag in constant time.

HKDF has two phases:

1. **Extract:** $\mathrm{PRK} = \mathrm{HMAC}_{\mathrm{salt}}(\mathrm{IKM})$. This concentrates non-uniform input into a pseudorandom key.
2. **Expand:** derive output blocks with $T(0)=\epsilon$ and $T(i)=\mathrm{HMAC}(PRK,T(i-1)\|info\|i)$, where $i$ is a one-byte counter. The `info` string should include protocol, version, direction and purpose.

<Cite id="rfc5869" locator="§2" />

## Argon2id parameters in practice

A password hash stores the algorithm, parameters and salt alongside the digest. A typical deployment chooses memory and iterations so one verification takes a deliberate fraction of a second, then benchmarks under peak login load. Parameters must fit the server memory budget; a configuration that causes memory exhaustion under a login flood is a denial-of-service vulnerability. <Cite id="rfc9106" locator="§4" />

| Field | Why it matters |
| --- | --- |
| Salt | unique per password; prevents precomputation |
| Memory cost | raises GPU/ASIC cost |
| Iterations | raises CPU cost |
| Parallelism | uses cores without changing the security target |
| Pepper | optional server-side secret; not a substitute for a salt |

## Migrating an old password store

1. Keep the old verifier and mark its algorithm/parameters.
2. On successful login, verify with the old scheme, then rehash with the new one.
3. For dormant accounts, force a reset or a risk-based migration.
4. Never log plaintext passwords or raw verifier material.
5. Rate-limit authentication even after migration.

## Derive purpose-specific keys step by step

HMAC-SHA-256 uses 64-byte blocks. Hash keys longer than 64 bytes to 32 bytes; pad shorter keys with zeros. XOR with `0x36` repeated 64 times for the inner hash, then with `0x5c` repeated 64 times for the outer hash. This nesting blocks the simple length-extension attack on a keyed prefix. <Cite id="rfc2104" locator="§2–3" />

HKDF Extract turns IKM into PRK with salted HMAC. Expand computes $T(0)=\epsilon$ and $T(i)=\mathrm{HMAC}_{PRK}(T(i-1)\|\mathrm{info}\|i)$ using a one-byte counter, for at most 255 blocks. The previous block prevents repetition; `info` separates contexts. <Cite id="rfc5869" locator="§2.2–2.3" />

## Hash properties and quantum caveats

For an ideal $n$-bit hash, generic classical preimage and second-preimage search cost about $2^n$ work, while finding a collision costs about $2^{n/2}$ because the attacker stores candidates and looks for a repeated digest. Grover’s algorithm gives a quadratic speedup for unstructured search, so a generic quantum preimage search is often described as $2^{n/2}$ work. <Cite id="grover1996" locator="pp. 212–219" />

That does not justify multiplying every classical bound by the same factor. Quantum collision search, parallel hardware, memory costs and structure-specific attacks have different models. A parameter decision should cite analysis for the actual hash and security goal, not infer a universal “quantum hash strength” from the digest length. SHA-256’s 128-bit generic classical collision target is a useful design heuristic, but it is not itself a theorem stated by FIPS 180-4. <Cite id="fips180-4" locator="§1, §6.2" />

## HMAC as a PRF

HMAC is a PRF if the compression function is a PRF under the relevant key. The nested construction prevents length extension and provides a clean keyed interface. A MAC must be verified in constant time over the full tag; early-exit comparison leaks the number of matching bytes.

## HKDF

HKDF-Extract compresses possibly non-uniform input into a pseudorandom key; HKDF-Expand stretches it into multiple outputs. Security requires a salt (which may be public) and context binding through `info`. Outputs for different `info` values should be independent.

<Callout variant="lab" title="Domain separation is a security boundary">
If two protocols derive keys with the same KDF input and no context separation, a key from one protocol may be valid in another. Bind algorithm, version, direction, identity and purpose into the derivation.
</Callout>

## Password hashing cost

Password hashing is an arms race between defenders and attackers. Memory-hard functions raise the cost of parallel GPU/ASIC guessing. The right parameters depend on hardware budgets and latency requirements; they are not a universal constant. Argon2id's hybrid memory access pattern is designed to balance side-channel and GPU resistance. <Cite id="rfc9106" locator="§3–4" />



## Length extension in one example

For a Merkle–Damgård hash, the digest is the internal state after processing the message. An attacker who knows `H(secret || message)` can often compute `H(secret || message || padding || suffix)` without knowing the secret. HMAC avoids this by using the secret in both an inner and an outer hash. This is why “hash the secret as a prefix” is not a MAC.

A KDF does not create entropy. HKDF assumes the input has enough min-entropy; a password has little, so password hashing must add cost. <Cite id="rfc5869" locator="§3.4, §4" />

## Define the properties as attacker advantages

Preimage resistance means finding any input for a given digest; second-preimage resistance means finding a different input for a given input; collision resistance means finding any distinct equal-hash pair. These games have generic classical costs $2^n$, $2^n$ and $2^{n/2}$. Finding a pair from scratch is easier than inverting a chosen digest.

For a MAC, the adversary queries chosen messages and wins by verifying a fresh candidate. Constant-time full-tag comparison prevents a prefix oracle. HMAC’s proof treats the compression function as a PRF: distinguishing HMAC would require distinguishing a keyed inner or outer evaluation. Its nesting blocks simple length extension. <Cite id="rfc2104" locator="§2–3, §6" />

Formally, if $\mathcal A$ outputs a pair $(m^*,\tau^*)$ not among its tagging queries, its forgery advantage is $\Pr[\mathsf{Verify}(K,m^*,\tau^*)=1]$. Truncating to $t$ bits changes the per-attempt guessing term to roughly $2^{-t}$; making $v$ attempts changes the union bound to about $v2^{-t}$ when that product is small. Verification must still process the full expected tag, because a fast inequality exit reveals how many leading bytes matched.

HKDF correctness requires agreement on hash, `info`, counter encoding and length. With sufficient input min-entropy, Extract should produce a computationally uniform PRK; Expand should then act as a PRF for distinct contexts within query and length bounds. The salt should be independent of the IKM, and `info` must not be derived from the secret IKM value. HKDF never turns a dictionary password into high entropy. <Cite id="rfc5869" locator="§2.2–2.3, §3.1–3.4" />

The ceiling is a correctness and interoperability rule as well as a security boundary. Check the requested length and the implementation’s protocol-specific ceiling before allocating output buffers or entering the expansion loop. <Cite id="rfc5869" locator="§2.3" />

If a password has about 10 bits of entropy and each guess costs $C$, budget $B$ permits roughly $B/C$ candidates. Memory and iteration costs reduce guesses until online limits, reuse or pepper compromise dominates. Verification recomputes Argon2id with the stored salt and parameters and compares without early exit. <Cite id="rfc9106" locator="§3–4" />

Given `H(secret || amount=10)` and its length, an attacker may append Merkle–Damgård padding and a suffix, then continue compression from the digest. HMAC’s outer keyed hash prevents this. SHA-3’s sponge construction does not expose the same extendable chaining-state interface, but it still should not be used as an ad-hoc prefix-MAC. <Cite id="fips202" locator="§3.4–3.5" />

Finally, handle empty inputs deliberately. Hashing the empty string is well-defined. HMAC accepts an empty key and normalises it through the pad construction. HKDF accepts an omitted salt and omitted `info`, both of which have specified empty encodings, but protocol use should make the context explicit. None of these edge cases permits ambiguous concatenation or an unchecked output length.

<Lens level={4} title="Acceleration, constant-time verification and operational storage">

## Hardware acceleration

- **SHA-NI** accelerates SHA-1/SHA-256 on x86; Arm has crypto extensions for SHA-2 and SHA-3.
- **Keccak** is efficient in software and increasingly accelerated; SHA-3 is common in PQC code.
- **GPU/ASIC attackers** make fast hashes unsuitable for passwords; memory-hard functions change the economics.

## Implementation rules

1. Use a vetted library; do not implement HMAC, HKDF or Argon2 from scratch.
2. Compare MACs and tags in constant time.
3. Use a CSPRNG for salts and tokens, not timestamps or counters.
4. Store algorithm and parameters with the hash so they can be upgraded.
5. Rehash on successful login when parameters change.
6. Rate-limit and monitor authentication endpoints; hashing does not stop online guessing.
7. Never put secrets in logs, URLs or error messages.

<Callout variant="warning" title="Length extension">
Merkle–Damgård hashes such as SHA-256 are vulnerable to length extension when used naively as `H(secret || message)`. HMAC avoids this by construction. If you need a hash-based MAC, use HMAC or a keyed mode designed for it.
</Callout>

## Key derivation in protocols

TLS 1.3 uses HKDF to derive handshake and application traffic keys from the key schedule. Each direction and epoch gets independent keys. Getting the context or transcript binding wrong can enable cross-protocol or downgrade attacks even when the primitives are strong.

## Constant-time verification and storage

- Compare MACs and tags with a constant-time routine over the full length.
- Use a CSPRNG for salts and reset tokens; never a timestamp or counter.
- Store algorithm and parameters with the verifier so you can upgrade later.
- Rehash on successful login when parameters change.
- Protect the password database like a crown jewel: encryption at rest, least privilege, audit.
- Avoid putting secrets in URLs, logs, crash reports or analytics.

## Hardware economics

GPU and ASIC attackers excel at fast, low-memory hashes. Memory-hard functions change the cost curve, but they also consume server memory. Benchmark the real deployment, choose a target verification time, and monitor authentication latency and error rates. The goal is not “unbreakable”; it is to make guessing expensive enough relative to the value of the account and the lifetime of the password.

## Make parameters, capacity and failure behaviour explicit

Store a versioned verifier with algorithm, Argon2 version, memory, iterations, parallelism, output length, salt and digest. Reject unsupported versions rather than falling back to a fast hash. Validate parameter ceilings before allocation, verify with stored values, and rehash below the policy floor. Argon2id is preferred by the RFC and OWASP guidance. <Cite id="rfc9106" locator="§3–4" /> <Cite id="owasp-password-storage" locator="Password Hashing Algorithms → Argon2id; Using Work Factors" />

Estimate concurrency as arrival rate times mean service time, then add burst headroom. Cap simultaneous expensive operations and return retryable overload rather than spawning unbounded work. Run a comparable dummy verification for inactive usernames to resist enumeration.

## Treat the verifier record as untrusted input

A breached or modified database is not a trusted configuration file. Before allocating memory, validate the algorithm identifier, Argon2 version, tag length, salt length, memory cost, passes and lane count against policy ceilings. In Argon2, memory is expressed in KiB and rounded down to a multiple of $4p$; the specified minimum is $8p$. The RFC fixes version `0x13` and defines broad parameter ranges, but those ranges are not a safe deployment policy. A record claiming an enormous memory cost must be rejected before the library call. <Cite id="rfc9106" locator="§3.1–3.2" />

Store enough information to reproduce the verifier exactly, normally in a standard encoded string: algorithm and version, $m$, $t$, $p$, salt, output length and digest. Salts and parameters are public; passwords, peppers, IKM and derived keys are not. When a successful login finds a verifier below the current policy floor, recompute it with a fresh salt and approved parameters, then atomically replace the old record. Concurrent logins need compare-and-swap or an equivalent guard so two upgrades cannot race.

| Threat | Primary control | Residual risk |
| --- | --- | --- |
| Offline dictionary attack on database only | Unique salt plus tuned Argon2id | Passwords already exposed before migration remain compromised |
| Precomputed rainbow tables | Fresh CSPRNG salt per verifier | A reused or predictable salt restores cross-account amortisation |
| Database and application compromise | Separately stored pepper or HSM-backed keyed step | Pepper rotation may require every user to reset their password |
| Online credential stuffing | Per-account and per-source limits, MFA, monitoring | Distributed attempts can evade coarse source limits |
| Username enumeration | Comparable dummy verification and one generic failure | Traffic analysis and response-time noise can still leak clues |
| Login-flood denial of service | Bounded worker pool, queue limits, overload response | Legitimate users may experience delay during an attack |
| Malformed verifier record | Strict grammar and parameter ceilings | Legacy records may need a bounded compatibility reader |
| Secret leakage through telemetry | Structured logging that excludes passwords and key material | Crash dumps and debug builds need separate review |

A pepper changes the threat boundary rather than making a weak password strong. If an attacker steals only the database, a separately protected pepper can prevent offline guessing. If the attacker also compromises the pepper or the application process that uses it, that advantage disappears. OWASP therefore treats peppering as defence in depth and requires the pepper to be stored separately from the password database. <Cite id="owasp-password-storage" locator="Methods for Enhancing Password Storage → Peppering" />

Password policy and password hashing solve different problems. NIST’s current verifier guidance emphasizes length, blocklists of compromised or common values, rate limiting and avoiding arbitrary composition rules or periodic changes absent evidence of compromise. A slow hash does not make a known-breached password safe again. <Cite id="nist-sp800-63b-4" locator="§3.1.1.2, §3.2.2" />

Argon2id’s first half of the first pass uses data-independent addressing and the remainder uses data-dependent addressing. This hybrid is intended to trade side-channel exposure against time–memory trade-off resistance; it is not a promise that every implementation is safe against a co-resident attacker. RFC 9106 recommends enabling memory wiping when side channels are a viable threat. <Cite id="rfc9106" locator="§1, §3.4.1.3, §4" /> Benchmark the complete service under burst load, because a configuration that is safe for one verification can still be weaponised into memory exhaustion by concurrency.

Memory is the configured Argon2 cost per verification; concurrency assumes stable benchmarked latency. Monitor p99 latency, queue depth and memory pressure on the real host. A single-user test cannot predict login-flood behaviour. <Cite id="rfc9106" locator="§4" />

Benchmark fast hashes, HMAC, HKDF and Argon2id separately. SHA acceleration does not help a memory-hard password verifier. Compare full tags in constant time and collapse malformed-record and wrong-password errors. Protect salts and verifiers in transit and storage; never log passwords or IKM.

Test published SHA and HKDF vectors, HMAC vectors, empty and long keys, maximum HKDF lengths, truncated tags and malformed parameter records. Fuzz the verifier grammar with strict bounds. Prove legacy upgrades happen once and load-test peak rate, oversized parameters and inactive usernames.

Review parameters as hardware improves and retain versions needed for old records. Rehash on successful login when the floor rises; after suspected breach, run a reset campaign without locking everyone out. Offline cost does not stop online guesses, so rate limiting and monitoring remain necessary.

## Common failure modes

| Failure mode | Root cause | Consequence |
| --- | --- | --- |
| Plain hash used as a MAC | Secret is prepended without a keyed construction | Length extension or forgery |
| Published digest treated as proof of origin | Digest and artifact share an untrusted channel | Attacker replaces both without detection |
| Fast hash used for passwords | Team optimises verification speed instead of guessing cost | Offline cracking is cheap |
| Salt reused or omitted | Password records were copied without per-user randomness | Precomputation and equal-password correlation |
| Same KDF context everywhere | `info` is empty or copied between protocols and directions | Cross-protocol key reuse |
| MAC comparison exits early | Generic equality routine is used | Matching-prefix timing oracle |
| Argon2 parameters have no upper bound | Encoded user record controls allocation directly | Memory-exhaustion denial of service |
| Verifier format has no version | Parameters and encoding are implicit | No safe upgrade or migration path |

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Peers derive different HKDF outputs | Hash, `info`, counter byte or length differs | Compare non-secret derivation metadata and run RFC 5869 vectors |
| A valid MAC fails intermittently | Message encoding or tag length changed | Canonicalise the message and pin the full tag length |
| Login latency collapses under a burst | Too many Argon2 instances run concurrently | Bound the worker pool, queue excess work and load-test peak arrivals |
| One malformed record consumes huge memory | Parameters are trusted before validation | Enforce algorithm and parameter ceilings before allocation |
| Equal passwords have equal verifiers | Salt is constant, empty or derived from the username | Generate a fresh CSPRNG salt for every verifier |
| Legacy users never migrate | Rehash occurs only on password reset | Rehash after successful legacy verification and report remaining coverage |
| Timing varies with matching tag prefix | Verification exits on the first mismatch | Use a vetted constant-time comparison over the complete tag |

## Design review checklist

- [ ] Each use is classified as hash, MAC, KDF or password-hashing duty.
- [ ] Adversarial integrity uses a MAC or signature, not an unauthenticated digest.
- [ ] HMAC is used instead of an ad-hoc keyed prefix or suffix hash.
- [ ] MAC and password comparisons are constant time over the full value.
- [ ] HKDF context binds protocol, version, algorithm, direction and identity.
- [ ] HKDF output length, hash and counter encoding are fixed and validated.
- [ ] Password records contain a unique CSPRNG salt and versioned parameters.
- [ ] Argon2 memory and concurrency are bounded and load-tested.
- [ ] Legacy verification upgrades safely without logging secrets.
- [ ] Published vectors and malformed-parameter tests run in CI.
- [ ] Salt, verifier and key material are protected in storage and telemetry.
- [ ] Parameter review and rehash policy have an owner and schedule.

## Key takeaways

- Hashes detect change; MACs authenticate; KDFs derive keys; password hashes resist guessing.
- HMAC is not `H(secret || message)`; use the standard construction.
- HKDF binds context through `info` and can derive many independent keys.
- Argon2id parameters are a deployment decision with availability consequences.
- Constant-time tag comparison and secret hygiene are part of the primitive.
