## Name the layer before naming the threat

A rootkit is not simply a hidden process. It is a collection of mechanisms that establishes privileged or early influence and then distorts the evidence available to ordinary consumers. A bootkit participates in the boot path so that its influence can be restored before normal endpoint security starts. A firmware implant operates in platform firmware or an early firmware service. The labels overlap in practice, but the layer determines which evidence can observe the compromise and which recovery action can remove it.

Matrosov, Rodionov and Bratus move from rootkit case studies into bootkit background, operating-system boot essentials, boot process security and infection techniques. <Cite id="book-matrosov-rootkits-bootkits" locator="Chs. 1–7 (rootkit cases, observation, bootkit history, boot process, security and infection concepts)" /> Their central defensive lesson is architectural: an analyst who begins only after the session starts may be looking through the compromised layer. Investigation must include the trust path that produced the running system.

Start a rootkit assessment with four questions. Where does the influence enter? When does it execute relative to security software? How is it restored after reboot or service restart? Which vantage point remains independent enough to challenge it? These questions are more useful than immediately asking which product will remove the infection.

## Draw the boot chain as a chain of claims

A simplified chain begins with platform reset and firmware initialisation. Firmware establishes basic hardware services and chooses a boot path. On UEFI systems, firmware drivers and boot applications participate before the operating-system loader. The bootloader transfers control toward the kernel. The kernel initialises drivers and security components. Session services then start user applications and endpoint agents. Real platforms vary, but the trust transitions are what matter.

Each transition makes a claim: this component is authorised to run, its handoff is intact and the next stage receives the expected state. Secure Boot can authenticate selected boot components under a platform trust policy. Measurements can report what executed to a verifier. Neither mechanism by itself proves that the operating system, every driver or every user process is benign. A clean boot decision is one claim in a larger evidence chain. NIST treats authenticated firmware update, boot-time integrity verification and verified recovery as distinct resiliency controls. <Cite id="nist-sp800-193" locator="§4.2.1, §4.3.1 and §4.4.1" />

## Treat each handoff as a non-transitive claim

Trust does not accumulate because previous stages completed. An authentic component can contain harmful logic. A measured component can be faithfully reported while behaving badly. A successful handoff can discard evidence needed by the next stage. Each transition therefore has its own verification scope and limits.

<div className="not-prose overflow-x-auto" role="region" aria-label="Boot-chain handoff claims" tabIndex={0}>

| Transition | State passed forward | What successful verification does not imply | Investigation question |
| --- | --- | --- | --- |
| Reset to firmware initialisation | Hardware configuration, reset reason and early execution context | That firmware code, option ROMs or management components are all benign | Which reset path ran, and what inventory or measurement is available before normal services? |
| Firmware to boot application | Boot services, handles, memory map and selected device path | That every dispatched driver was verified or that the selected loader behaves correctly | Which drivers were dispatched, which policy covered them and what changed from the baseline? |
| Boot application to operating-system loader | Loaded image, configuration and handoff protocol | That the loader will preserve every security property of the earlier stage | What was measured, what was merely loaded and where did the verification log come from? |
| Loader to kernel | Kernel image, boot parameters and early hardware state | That runtime drivers, callbacks or applications are trustworthy | Which kernel and parameters were accepted, and what independent runtime view can challenge them? |
| Kernel to session | Process service, identity context and endpoint telemetry | That earlier compromise stopped influencing the session | Can external identity, network or management records corroborate the session view? |

</div>

This table separates prevention from investigation. Secure Boot rejection can prevent an unauthenticated component from continuing along the configured path, even if the analyst never learns why it was present. Acceptance is bounded by key trust, policy coverage and verification-path integrity. Matrosov and colleagues place Secure Boot inside a wider boot-process-security model. <Cite id="book-matrosov-rootkits-bootkits" locator="Ch. 6 (boot process security) and Ch. 17 (how Secure Boot works)" />

For assessment, annotate the platform's chain with the owner of each reference and the independence of each observer. If firmware inventory and session records are collected by the same endpoint agent, their apparent agreement is weaker than it looks.

## Model persistence as a lifecycle

Persistence has at least four parts: an entry mechanism, an execution point, a restoration mechanism and a concealment or influence mechanism. A user-mode hook may be restored by an ordinary launcher at session start. A kernel callback may be re-established by a component that loads with the kernel. A bootloader implant participates on each boot before the operating system. A UEFI driver is dispatched during firmware initialisation.

Do not assume that a lower-layer implant always hides perfectly or that a higher-layer hook is easy to remove. Detection depends on implementation, tooling and the independence of the observer. Similarly, do not assume that reboot clears every compromise. Reboot may remove volatile user-mode state while faithfully restoring a persistent boot component. It may also trigger delayed behaviour or destroy the memory evidence needed to understand the incident.

The adversary's incentive is to make one view look normal while another reveals the truth. The defender's incentive is to collect evidence through multiple trust boundaries and to avoid letting the suspect system be the sole authority on its own integrity. This is why a rootkit case often combines endpoint telemetry, independent kernel acquisition, firmware evidence, boot logs and network or identity records.

## Keep the investigation safe

Suspected rootkit activity changes the risk of live response. A process listing, kernel structure or firmware query may be filtered, and an acquisition tool may share the same compromised operating-system path. Do not experiment on production. Use an approved forensic method, preserve evidence before destructive action when the risk allows and document which views may be unreliable. NIST's malware guidance integrates analysis with incident prevention and response. <Cite id="nist-sp800-83r1" locator="§3–5 (prevention, detection and response)" />

Record platform model, firmware version, boot mode, disk-encryption state, Secure Boot policy state, management-controller involvement and available acquisition support. These facts determine which evidence can be collected and which recovery path is realistic. A generic instruction to “reinstall Windows” is not a firmware recovery plan, and a firmware image is not automatically safe to flash back without a trusted reference.

## Threat-model the platform, not only the process

Identify the assets an attacker could reach after early influence: disk-encryption keys, credentials, management interfaces, boot policy, hypervisor state, cluster nodes and recovery media. Consider insiders, compromised suppliers, stolen administrative credentials and remote exploitation of exposed firmware-management services. The objective may be concealment, data theft, disruption, cryptomining or long-term access rather than a visible ransom note.

Document the expected trust baseline. Which firmware version is approved? Which bootloader and kernel are signed? Which measurements are recorded? Which management components can change boot policy? Which teams can reflash firmware? A baseline is not a screenshot from one day; it is a versioned set of platform references, change records and verification procedures.

## Understand what each vantage can actually see

User-mode tools consume operating-system interfaces and may receive filtered results. Kernel evidence has greater privilege but can still be obtained through a compromised kernel, an incorrect acquisition method or incomplete symbols. Firmware evidence can address pre-boot state, but only if acquisition is supported and interpreted against the correct platform reference. No vantage is automatically trustworthy.

The useful question is not “which tool says clean?” but “what evidence would each layer be expected to produce, and do independent observations agree?” A user-mode service that omits a process, a kernel view that shows unexpected state and an identity log that confirms activity form a contradiction worth investigating. Three tools sharing the same agent, parser or source may simply repeat the same blind spot.

Matrosov and colleagues emphasise observing rootkit infections and analysing boot process security rather than trusting a single hidden view. <Cite id="book-matrosov-rootkits-bootkits" locator="Ch. 3 (observing rootkit infections) and Ch. 6 (boot process security)" /> Treat apparent absence as a result with provenance. Record which interface produced it, what filters may apply and whether an independent source can test it.

## User-mode hooks influence the session view

A user-mode hook can alter what an application or service reports without changing firmware or the bootloader. It may depend on a launcher, scheduled task, service configuration or another persistence mechanism to return after restart. The visible symptom might be an incomplete process list, inconsistent network ownership or a service that disagrees with endpoint telemetry.

Detection should combine cross-view disagreement with durable evidence. Process creation logs, object-access events, network flows and identity records can survive the hooked component or arrive through separate infrastructure. Do not assume that every mismatch is malicious: software compatibility layers, security products and instrumentation failures can also create disagreement. The hypothesis strengthens when the mismatch follows one process, account or asset and when raw records support the hidden activity.

## Kernel callbacks require independent state evidence

A kernel-mode mechanism can influence events before many user-space consumers receive them. A callback or notification path may suppress information, alter state or create inconsistency. The defensive description is intentionally conceptual: understanding the trust boundary is more important than reproducing an implementation. The analyst needs an independent kernel view and a clear account of how that view was acquired.

Compare expected and observed state using approved forensic methods. Preserve memory, loaded-module information, object references and relevant logs before stopping a suspicious component when active harm allows. Check acquisition completeness and symbol or platform compatibility. If the tool relies on the same possibly compromised kernel, document the dependency rather than presenting its output as ground truth.

## Acquisition is a measurement system with failure modes

An independent view is not automatically accurate. Memory acquisition runs through the target operating system or a supported out-of-band mechanism; firmware acquisition interprets platform-specific layouts; log collection can drop, delay or rewrite records. Each method introduces dependencies that can imitate or conceal the condition under investigation.

A memory capture is not an instantaneous, perfectly consistent copy. CPUs, page tables, locks and object lists change during collection. The tool needs correct operating-system symbols and must distinguish unsupported fields from genuine absence. Live acquisition can alter the target. Out-of-band acquisition may avoid the suspect kernel but still needs documented timing and coverage. Memory forensics treats acquisition as a method with prerequisites, not a neutral copy operation. <Cite id="book-ligh-memory-forensics" locator="Volatile memory acquisition, process analysis and hidden-artefact analysis" /> Volatility's documentation separates acquisition requirements from plugin analysis. <Cite id="volatility-docs" locator="Memory acquisition requirements and plugin analysis" />

| Vantage | Blind spot or failure mode | Validation before trusting a mismatch |
| --- | --- | --- |
| Kernel memory snapshot | Inconsistent CPU state, wrong symbols, incomplete ranges or live-acquisition perturbation | Verify platform build, capture flags, layer completeness and parser warnings; compare with an approved second method when feasible |
| Firmware volume inventory | Tool may normalise away unknown regions or misparse a compressed update container | Retain the original image hash, raw regions and parser version; compare against the exact platform reference |

Suppose two kernel acquisitions disagree about a callback. Before alleging concealment, check whether both tools used the same symbol file, whether one reported a parsing warning and whether either capture covered every CPU. A callback present in an out-of-band image but absent from the live list supports a visibility hypothesis; the same discrepancy in two parsers using an incorrect symbol set supports a tooling hypothesis. Preserve both results and the validation records.

Firmware analysis has an analogous trap: a parser reporting “no unknown volumes” may have skipped an unsupported region. Report what was parsed, what was skipped and how the reference was produced. Matrosov and colleagues's firmware-forensics discussion reinforces platform-specific interpretation and preservation of low-level evidence. <Cite id="book-matrosov-rootkits-bootkits" locator="Chs. 18–19 (packers and CHIPsec firmware forensics)" />

## Bootloader implants sit between firmware and kernel

A bootloader implant can influence the handoff before normal operating-system controls run. It may affect the next stage, evade session-level observation or persist across ordinary reinstalls that do not restore boot media. The strongest evidence often combines firmware-side trust decisions, bootloader measurements and independent analysis of trusted recovery media.

Matrosov and colleagues trace the evolution of MBR, VBR and initial-program-loader bootkits before moving to UEFI boot processes and contemporary UEFI bootkits. <Cite id="book-matrosov-rootkits-bootkits" locator="Chs. 10–12 (MBR, VBR and IPL bootkit evolution) and Chs. 14–15 (UEFI boot process and contemporary UEFI bootkits)" /> For this course, the takeaway is the shift in evidence. A process-centric investigation cannot independently establish that the pre-kernel handoff was authentic.

## UEFI drivers expand the pre-boot surface

UEFI firmware uses drivers and boot services before the operating system. An untrusted early component can influence later stages or their visibility. Firmware inventory and measured boot paths become central evidence, while ordinary endpoint process telemetry is downstream of the event. Platform-specific acquisition and vendor documentation matter because firmware layouts, update mechanisms and recovery options differ.

The UEFI discussion also changes recovery. Restoring a partition, reinstalling the operating system or resetting an application may leave the firmware path untouched. Recovery may require a vendor-supported firmware update, a trusted platform replacement, restoration of provisioning keys and verification that the expected components are again authorised and measured. NIST requires recovery to restore an authentic firmware image and verify its integrity and authenticity before restoration. <Cite id="nist-sp800-193" locator="§4.4.1" /> Always preserve evidence before applying a trusted update when feasible.

## Secure Boot is a boundary, not an immunity claim

Secure Boot authenticates selected boot components under a platform trust policy and can reject an untrusted component before it controls the handoff. Matrosov and colleagues explain how Secure Boot works and place it within broader boot process security. <Cite id="book-matrosov-rootkits-bootkits" locator="Ch. 17 (how Secure Boot works)" /> The exact guarantee depends on platform implementation, policy keys, update integrity and the components covered by the policy.

Secure Boot does not directly validate every user-mode hook, kernel callback or application. It also does not make a compromised trust store or signing key harmless. Treat enforcement as a preventive control with a defined scope, and treat policy changes, key enrolment and recovery events as high-value audit records. A successful boot is evidence that the configured verification path accepted the components it checked, not a universal integrity proof.

## Attestation reports claims; it does not repair them

Attestation can send measurements or state claims to a verifier that compares them with a reference. A trusted verifier may detect a mismatch and restrict access. It cannot reflash firmware, remove a kernel callback or revoke every credential by itself. A measurement also needs freshness, scope and a trustworthy reporting path. Otherwise a valid old measurement could be replayed or a compromised component could misreport its own state. The TCG PC Client Reference Integrity Manifest specification defines reference information for validating TPM Quotes and boot-cycle event logs, including expected PCR coverage; it does not by itself decide remediation policy. <Cite id="tcg-pc-client-rim-1-1-r11" locator="§2–3.2.2" />

Design attestation as a decision system. Specify what is measured, when it is measured, how freshness is established, which reference is authoritative, what happens when evidence is missing and which access decision follows a mismatch. Avoid collecting unnecessary platform identifiers. Test fail-open and fail-closed behaviour, clock issues, offline operation and recovery-mode exceptions.

## Record the limits of every observation

A negative finding should say what was searched, with which tool and against which reference. “No firmware mismatch detected” is different from “firmware is intact”. The first is a bounded result; the second is an unsupported universal claim. Use confidence statements that identify evidence quality, source independence, contradictions and unknowns. This discipline protects both the investigation and the eventual recovery decision.

## Attestation needs a policy and a verifier

A measurement without a reference is only a number. Build a reference from supported platform baselines and approved changes. Bind the report to a specific device and a fresh challenge when replay is a concern. Decide which components are critical, which deviations are expected and which require access denial. Protect the verifier and its reference data independently of the endpoint being assessed.

The verifier should output an interpretable decision: trusted under policy, untrusted, unknown because evidence is missing or unsupported. “Unknown” should not silently become trusted. At the same time, a rigid fail-closed policy can lock out legitimate recovery or offline systems. Define an authorised exception with expiry, audit and compensating controls rather than creating a permanent bypass.

Treat attestation as one signal in a larger access decision. Combine it with device ownership, patch posture, identity, network context and recent behaviour. A correctly measured boot can still run a compromised application. A measurement mismatch can also result from an approved firmware update that has not reached the reference system. Both cases require context and change management.

## Separate prevention, measurement and access enforcement

Secure Boot, measured boot, attestation and access policy solve different problems. Conflating them produces brittle decisions. A signature check asks whether a component is authorised under a configured key policy. A measurement records a value for later comparison. Attestation transports a claim, ideally with freshness, to a verifier. Access policy decides what to do with the result.

<div className="not-prose overflow-x-auto" role="region" aria-label="Boot trust mechanism scopes" tabIndex={0}>

| Mechanism | Useful outcome | Characteristic failure | Required companion control |
| --- | --- | --- | --- |
| Boot authentication | An unapproved component is refused before it controls the configured path | A trusted key signs harmful code, or policy omits a relevant component | Protected key management, policy audit and a reference for expected components |
| Measurement | A verifier can compare observed values with an approved baseline | The reference is stale, incomplete or itself untrusted | Provenance-controlled baseline updates and component-level interpretation |
| Fresh attestation | A verifier receives a current claim tied to a device | Reports are replayed, missing or collected through a compromised path | Challenge or freshness validation, protected transport and unknown-state handling |
| Access enforcement | A mismatch or missing report leads to a bounded decision | The service fails open, or an exception becomes permanent | Tested fail-closed paths, time-limited exceptions and recovery procedures |

</div>

Consider a laptop whose bootloader measurement changed while Secure Boot still accepts the boot. Benign explanations include an approved update outside the reference's scope or a stale reference entry. An adversarial explanation is a component accepted under an enrolled key or a measurement path that misses the changed region. Mark the device **unknown pending evidence**, restrict privileged access and request the vendor package identity, policy history and supported firmware acquisition. Do not update the reference merely to silence the alert.

This decision sequence preserves the distinction between detecting a difference and proving an implant. Matrosov and colleagues describe Secure Boot's verification mechanism, while the broader investigation still depends on independent evidence about keys, components and handoffs. <Cite id="book-matrosov-rootkits-bootkits" locator="Ch. 17 (how Secure Boot works) and Chs. 14–15 (UEFI boot process and contemporary UEFI bootkits)" /> A clean verifier result is meaningful only while its reference, freshness and reporting path remain trustworthy.

## Container nodes inherit lower-layer trust

Containers isolate workloads, but they do not remove the host kernel, boot path or firmware beneath the node. NIST's container security guidance treats risks across images, registries, orchestrators, runtimes and hosts. <Cite id="nist-sp800-190" locator="§3–5 (container risks and mitigations across the container ecosystem)" /> A compromised node kernel or early boot component can undermine isolation assumptions for every workload on that node.

Kubernetes security documentation places pod security, RBAC, network policy and secrets within a broader platform-security model. <Cite id="kubernetes-security" locator="Pod security, RBAC, network policy and secrets" /> Those controls remain necessary, but they do not establish firmware integrity. If a node fails trusted-boot verification, containment may include cordoning or draining the node under the platform's operating policy, preserving supported evidence and preventing new workloads from landing there. Recovery may require node replacement rather than restarting containers.

This connection matters for blast radius. A user-mode endpoint hook may affect one session. A kernel callback may affect all telemetry from a node. A bootloader or UEFI implant may survive container replacement and node reboot. Map the persistence layer to the fleet unit that must be contained: session, host, node, rack or platform family.

## Build a fleet view of trust transitions

Track device model, firmware version, boot mode, Secure Boot state, measurement status, attestation freshness, last approved change and recovery status. Group exceptions by platform family rather than treating thousands of endpoints as unrelated alerts. A new firmware release can create a coordinated measurement change, while a targeted implant may affect a small asset group with privileged access.

Protect telemetry integrity. Central measurement logs, boot-policy audit and device inventory should not be writable by the same identity that administers the endpoint. Alert on missing reports, sudden policy changes, enrolment of unknown keys and recovery activity outside approved windows. Preserve raw reports so a later investigation can distinguish a true mismatch from a reference-data problem.

## Contain before the platform can expand the incident

Containment depends on active harm and asset role. Network isolation may stop command-and-control, credential theft or lateral movement. Disabling a user or service identity may be necessary if the suspicious layer could observe authentication. Restricting management interfaces may prevent boot-policy changes. A critical system may need a controlled maintenance path rather than abrupt disconnection.

NIST's malware incident guidance connects detection and analysis to containment, eradication and recovery. <Cite id="nist-sp800-83r1" locator="§3–5 (prevention, detection and response)" /> Preserve volatile and durable evidence before destructive action when feasible. If active encryption, data theft or safety impact demands immediate containment, contain first and document what could not be saved. Do not let a generic evidence-first rule create a second incident.

Acquisition must be approved and platform-aware. Firmware images, boot logs, measurement reports, memory captures, disk state and management-controller logs may have different tools, formats and legal constraints. Record tool version, source device, time, hash, operator and storage location. Keep originals immutable and analyse verified working copies.

## Eradication follows the earliest affected layer

Removing a file, service or container is not eradication if a lower-layer component can restore it. The recovery plan must identify every affected trust boundary. A user-mode case may require launcher removal and host rebuild. A kernel case may require trusted boot media and kernel-state validation. A bootloader case must restore the pre-kernel handoff. A UEFI case may require vendor-supported firmware recovery, key reset or platform replacement.

Credential exposure is a parallel workstream. Early influence may precede endpoint controls and may observe login, disk-unlock or management activity. Revoke sessions, rotate secrets and review authentication logs based on the exposure window. Restoring firmware without addressing stolen credentials leaves the incident open.

Matrosov and colleagues close the technical arc with Secure Boot, hidden file-system analysis and firmware forensics. <Cite id="book-matrosov-rootkits-bootkits" locator="Chs. 17–19 (Secure Boot, hidden file systems and CHIPsec firmware forensics)" /> The practical recovery lesson is to verify the restored trust path with independent evidence, not to rely on a successful reboot or a single vendor utility reporting success.

## Make eradication a falsifiable chain

“Reimaged” and “reflashed” are actions, not outcomes. Eradication is supported only when the original persistence path is closed and independent evidence shows it cannot return. That requires provenance for the recovery material, restoration of the earliest affected boundary and verification that does not reuse the suspect view.

A worked recovery illustrates the separation. After a supported firmware restore, the measured bootloader matches the approved reference and Secure Boot accepts it. An external identity log still shows the old administrator session connecting from the recovery network. The firmware claim has evidence; eradication does not. Revoke the session, rotate exposed secrets and review the exposure window before restoring privileged access. Conversely, if firmware matches but an independent kernel acquisition shows the original unexpected callback, the earliest supported persistence layer may be runtime rather than firmware.

Containment and recovery decisions also need owners and reversibility. NIST's incident-response guidance connects playbooks to the response lifecycle and its containment, eradication and recovery handoffs. <Cite id="sp800-61r3" locator="§2–5 (incident response lifecycle and playbooks)" /> Record what was preserved before repair, what urgent containment destroyed, which trusted artefacts were used and who accepted residual risk. A device returns to service only when the original failure condition is absent from independent views and recurrence can be detected.

## Validate recovery against the original hypothesis

If the hypothesis was a filtered process feed, test that independent process, network and identity sources agree after recovery. If it was a kernel callback mismatch, compare independent kernel state and alert delivery. If it was a bootloader measurement mismatch, verify the boot path and policy. If it was a UEFI driver, verify the supported firmware inventory and measurements. Each test should fail visibly when the original condition returns.

Do not validate only with the tool that may have been compromised. Use a trusted recovery environment, independent acquisition path and external telemetry. Record the baseline version and the evidence generated by each test. Recovery is complete when the original path is closed and the organisation can detect its return, not when the device merely starts.

## Build detections around observable disagreements

MITRE ATT&CK provides a shared vocabulary for adversary behaviour, including persistence and defence-evasion concepts. <Cite id="mitre-attack" locator="Enterprise tactics, techniques and procedures" /> Use technique labels to organise hypotheses, but build detections from evidence. Examples include an unapproved firmware measurement, a boot-policy change outside a maintenance window, disagreement between endpoint and network telemetry, or a fleet-wide gap in attestation reports.

Each detection needs a data source, reference, logic, expected benign cases, severity rule, owner and test. A measurement alert must account for approved updates. A missing-agent alert must account for offline devices and planned maintenance. A kernel-state comparison must use a supported acquisition method. A technique tag without telemetry is not a working detection.

Measure precision and recall in the deployed platform population. Firmware mismatches may be rare, so precision can collapse when a reference baseline is stale. Missing-report alerts may be noisy during travel or maintenance. Track analyst dispositions and update benign references through controlled change management rather than suppressing whole device classes indefinitely.

## Learn from the trust failure

Post-incident review should ask how the early component entered, which trust policy accepted or failed to reject it, why detection occurred at the current layer and which fleet assets share the exposure. Convert findings into owned changes: protected key-management procedures, baseline automation, faster firmware inventory, independent telemetry and tested recovery runbooks.

## Common failure modes

| Failure mode | Observable symptom | Root cause | Guardrail |
| --- | --- | --- | --- |
| Session-only investigation | Endpoint looks clean despite external activity | Lower-layer influence ignored | Collect independent kernel, firmware and external evidence |
| Reboot-as-recovery | Compromise returns after restart | Boot path restores persistence | Restore the earliest affected trust boundary |
| Secure Boot overclaim | Accepted boot treated as full integrity | Control scope misunderstood | State exactly what policy verified |
| Attestation-as-repair | Mismatch reported but access continues | No policy or remediation link | Bind fresh evidence to access decisions |
| Single-tool trust | Several tools repeat the same clean view | Shared agent or acquisition path | Use independent evidence sources |
| Reference silencing | Alerts disappear after baseline edit | Unverified component accepted as normal | Require provenance and controlled baseline changes |
| Destructive first response | Firmware or memory evidence lost | Update or rebuild before acquisition | Preserve approved evidence when risk allows |
| Partition-only cleanup | Firmware implant survives | Operating-system scope mistaken for platform scope | Include firmware and bootloader recovery |
| Credential omission | Access continues after device recovery | Early layer may observe authentication | Rotate sessions and secrets by exposure window |

## Design review checklist

- [ ] The boot chain and earliest plausible persistence layer are documented for each platform family.
- [ ] Secure Boot scope, key management, recovery mode and policy-change auditing are explicit.
- [ ] Attestation defines freshness, trusted verifier, reference ownership, missing-evidence behaviour and access policy.
- [ ] User, kernel, firmware and external evidence sources are assessed for shared dependencies.
- [ ] Acquisition methods are supported, authorised, versioned and safe for the target platform.
- [ ] Containment covers sessions, credentials, management interfaces and fleet scope, not only files.
- [ ] Recovery restores the earliest affected trust boundary using trusted or vendor-supported procedures.
- [ ] Verification uses evidence independent of the suspect layer and tests for recurrence.
- [ ] Container-node containment and workload redeployment respect shared kernel and boot trust.
- [ ] Detection logic has benign update fixtures, mismatch tests, owners and measured precision.
- [ ] Evidence preservation includes hashes, custody, timestamps and documented losses.
- [ ] Recovery exercises test offline, maintenance, lost-device and compromised-management scenarios.

## Key takeaways

1. A rootkit or bootkit is defined by influence and persistence across a trust layer, not merely by a hidden process.
2. The boot chain determines which evidence can observe the compromise and which recovery action can remove it.
3. User-mode, kernel, bootloader and UEFI hypotheses require different vantage points and containment scope.
4. Secure Boot authenticates a defined boot-policy scope; it is not a guarantee of runtime integrity.
5. Attestation supplies evidence to a trusted verifier; it does not repair the endpoint automatically.
6. Cross-view disagreement is valuable when sources are independent and their limitations are recorded.
7. Container isolation does not remove shared kernel, boot-path or firmware trust.
8. Recovery restores the earliest affected layer, rotates exposed credentials and verifies that the path cannot return.

### Trust-chain mapping

Choose a managed laptop, a container node and a virtual machine from a fictional inventory. Draw reset, firmware, bootloader, hypervisor or kernel, and session transitions. Mark which evidence source could observe each stage and which team owns recovery. Do not inspect or modify real firmware.

**Deliverable:** three diagrams with evidence and ownership annotations. **Success criterion:** every claimed visibility source has a stated independence assumption.

### Control-scope memo

Use the boot-chain explorer to compare all four layers with Secure Boot and attestation on and off. Write a one-page memo explaining what each control can prevent, what it can reveal and what remains outside its scope. Include at least two benign explanations for a mismatch.

**Deliverable:** a scope matrix and mismatch triage rule. **Success criterion:** no control is described as a universal integrity guarantee.

### Recovery tabletop

Run the guided workshop as a tabletop with roles for incident commander, firmware engineer, identity lead, Kubernetes owner and legal contact. Introduce a constraint that the administrator laptop must remain available for a critical business process. Decide how to preserve evidence and restrict access without creating an unsafe permanent exception.

**Deliverable:** a timed action log, decision rationale and recovery acceptance criteria. **Success criterion:** every disruptive action has an owner, rollback and evidence consequence.

### Detection test plan

Design three safe tests: an approved firmware update fixture, a stale-reference fixture and a simulated mismatch fixture. Specify data sources, expected alerts, benign cases, severity, owner and closure criteria. Add one test for a node that stops reporting while containers remain healthy.

**Deliverable:** a test table with positive, negative and missing-evidence cases. **Success criterion:** each test distinguishes trust mismatch, reference error and telemetry failure without deploying malicious code.
