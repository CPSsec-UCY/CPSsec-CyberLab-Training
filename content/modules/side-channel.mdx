## The uncomfortable truth

Cryptographers prove statements about algorithms. Attackers target implementations. The two are not the same object.

A secret-dependent branch changes how long code runs. A table lookup indexed by a secret changes which cache lines are touched. A multiplier consumes different power depending on the bits of its operands. A glitch can skip a signature check. None of these are visible in the mathematical security proof.

<Callout variant="danger" title="Real-world consequence">
Timing attacks have recovered RSA keys from network measurements. Differential power analysis has recovered AES keys from smart cards. Fault attacks have broken RSA signatures with a single corrupted computation. The algorithm was not broken; the implementation leaked. <Cite id="kocher1996" locator="pp. 104–113" /> <Cite id="kocher1999" locator="pp. 388–397" />
</Callout>

## The attacker's question

For every operation, ask: **does the observable behaviour depend on a secret?**

- If yes, you have a side channel.
- If the dependency is measurable and the attacker can repeat it, you have a practical attack.
- If the secret is long-lived and the leak is stable, you have a serious one.

## "Constant-time" is a discipline, not a compiler flag

Constant-time code means the sequence of instructions and memory addresses does not depend on secret data. It does not mean "takes the same number of nanoseconds" — caches, interrupts and frequency scaling make exact timing impossible. It means no secret-dependent control flow and no secret-dependent memory indexing.

<Callout variant="note" title="Not sufficient, but necessary">
Constant-time code is designed to remove timing and cache-index leaks caused by secret-dependent control flow and addressing. It does not defeat power analysis, electromagnetic leakage or fault injection. Those need masking, hiding, redundancy and physical protections on top.
</Callout>

## Three ways a correct algorithm fails

- **Timing:** a secret-dependent branch or variable-time division changes how long an operation takes. An attacker with many observations can recover the branch pattern.
- **Power:** a multiplier or memory access consumes different power depending on the data. Differential power analysis correlates many traces with a guessed intermediate value.
- **Faults:** a glitch skips a check or corrupts a computation. The attacker compares the faulty output with a correct one to recover a key.

The algorithm can be provably secure and still lose to any of these. Security engineering must include the implementation, the compiler, the hardware and the operational environment.

## Threat model: a device under observation

Consider an ML-KEM decapsulation key inside a payment terminal. The attacker can submit chosen ciphertexts through the payment protocol, measure response time, share a CPU cache, and place a power probe near the secure element. In a stronger lab setting, the attacker can control voltage or clock glitches. The terminal's owner wants the key to remain secret and every decapsulation to return a normal 32-byte value regardless of ciphertext validity.

The attacker's goal is to connect an observable to a secret-dependent intermediate. A timing trace may reveal the matching prefix of the re-encryption comparison. A cache trace may reveal a secret-indexed sampling table. A power trace may reveal Hamming weight in a multiplication. A fault may corrupt one computation so that comparing it with a correct result exposes key material. The defender's goal is to reduce each observable's dependence on secrets, bound the number of useful observations, and detect or contain faults before they affect an output.

State the capabilities precisely. Remote timing requires many queries and low noise; a co-resident cache attacker has a different observation channel; power and electromagnetic probes require physical access; fault injection may require specialised equipment. The number of traces, chosen inputs, probe locations and fault types determines the assurance claim. A countermeasure useful against one model may be irrelevant against another.

Defender goals also include reproducibility. The exact source, compiler, optimisation flags, CPU features and hardware revision must be pinned for evaluation. A constant-time audit of an x86 build says nothing about an Arm backend or a later HSM firmware release. Operations must detect when a provider or toolchain changes and trigger revalidation.

Misconceptions weaken this model. Constant-time does not mean equal wall-clock nanoseconds, because interrupts, caches and frequency scaling create noise. It means that secret values do not choose instructions or memory addresses. It also does not mean power-independent. Masking does not make arbitrary code safe, and hiding a secret with noise does not help if the attacker can average unlimited traces. A single clean benchmark is not evidence against a statistical attack.

Security and availability must be reviewed together. Redundant computation can double latency; full-table scans can increase cache pressure; fault detection can abort a payment. Define acceptable failure behaviour and recovery rather than silently removing countermeasures under load. The result should degrade into a documented safe state, not into a secret-dependent shortcut.

### Translate capabilities into an observation budget

“The attacker can measure timing” is too vague to design a test. A remote attacker may control ciphertexts and collect thousands of requests, but cannot pin the victim process to one CPU or remove network jitter. A co-resident attacker can manipulate cache state but may observe only coarse eviction patterns. A power attacker can align traces to a hardware trigger but usually changes the physical environment. Fault capability is different again: the attacker may corrupt one byte, skip an instruction or repeat a computation, but may not know whether the fault landed.

| Channel | Observable and attacker control | Main confounders | Assurance question |
| --- | --- | --- | --- |
| Remote timing | Chosen inputs and response duration | Network jitter, scheduling, frequency changes | Does duration distribution depend on a secret at the stated sensitivity? |
| Cache | Shared-cache eviction or hit pattern | Other tenants, prefetch, replacement policy | Can secret-selected addresses be distinguished across repeated probes? |
| Power or EM | Aligned trace samples at chosen probe points | Probe placement, board variation, clock noise | Is an intermediate value recoverable under a stated leakage model? |
| Fault | Output after controlled disturbance | Unknown fault location and repeatability | Does the device detect, contain or leak the fault before releasing output? |

Consider chosen ciphertexts sent to an ML-KEM decapsulation interface. A prefix comparison can make rejection time depend on how many leading bytes match, so repeated queries may expose structure even when each individual measurement is noisy. <Cite id="fips203" locator="§7.2–7.3 (ML-KEM encapsulation and decapsulation)" /> The test plan must therefore fix the input distribution, estimate the number of observations available to the attacker and record what noise the countermeasure must tolerate. A one-off benchmark with one ciphertext cannot answer that question.

The observation budget also determines what “secure” can mean. A design may resist an attacker limited to 500 traces but not one allowed 500,000. Write the bound into the assurance claim, together with chosen-input freedom, probe count, fault set and hardware revision. Kocher's timing work shows why repeated measurements amplify small execution differences; the DPA work shows why many aligned traces can reveal data dependence. <Cite id="kocher1996" locator="pp. 104–113" /> <Cite id="kocher1999" locator="pp. 388–397" /> Without a budget, a pass label has no defensible scope.
</Lens>

## Timing attacks

Kocher's 1996 attack on RSA and Diffie–Hellman exploited secret-dependent execution time, including the square-and-multiply pattern and conditional reductions. Remote timing attacks are practical when the leak is amplified by many queries. <Cite id="kocher1996" locator="pp. 104–113" />

Common sources:

- branches on secret bits,
- variable-time division or modulo,
- early-exit comparisons,
- secret-dependent loop bounds,
- table lookups that miss the cache.

## Cache attacks

A cache line is loaded or evicted depending on the address accessed. If that address depends on a secret index, an attacker sharing a cache can infer the index with Flush+Reload or Prime+Probe.

## Power analysis

Simple power analysis reads a trace directly; differential power analysis correlates many traces with a hypothetical intermediate value. A common leakage model is Hamming weight, but real devices are messier.

## Fault attacks

A fault during a computation can produce an incorrect result that reveals the secret. The Bellcore attack on RSA signatures used one faulty signature to factor the modulus. Countermeasures include recomputation, verification before release, and redundancy. <Cite id="boneh1997" locator="pp. 37–51" />

## The countermeasure toolbox

| Threat | Countermeasure | Limit |
| --- | --- | --- |
| Timing branches | Branch-free selection, constant-time comparison | Does not hide power |
| Cache indexing | Full-table scan, register selection | Can be slower and use more power |
| Power analysis | Masking, hiding, fresh randomness | Cost, verification difficulty |
| Faults | Redundant computation, verify-before-release | Area, latency |
| All of the above | Hardware isolation, secure elements | Trust and availability |

## PQC-specific hotspots

- **ML-KEM decapsulation:** re-encryption comparison, decompression, rejection selection.
- **ML-DSA signing:** masking vector generation, norm checks, rejection loop, hint construction.
- **SLH-DSA signing:** address-dependent hashing and secret seed handling.
- **NTT:** any secret-dependent indexing or branch in the butterfly network.
- **Compression:** rounding must not branch on secret coefficients.

<Callout variant="warning" title="The rejection path is part of the attack surface">
In ML-KEM and ML-DSA, the path taken on rejection or failure must not be distinguishable from the success path. Implicit rejection exists for exactly this reason. <Cite id="fips203" locator="§7.3" /> <Cite id="fips204" locator="§3.6" />
</Callout>


## Worked oracle: compare completely, then select

An ML-KEM-768 ciphertext is 1,088 bytes. A vulnerable implementation decompresses and decodes enough input to derive a candidate key, re-encrypts it, and compares the result with the submitted ciphertext using a routine that returns at the first mismatch. The returned shared secret may be correct, but rejection time reveals the matching prefix. An attacker does not need to recover the long-term key in one query; repeated chosen ciphertexts can build a distinguishing statistic.

The repair is not “compare faster.” Parse and validate the public length, perform the prescribed decoding and derivation, compute both the accepted key and the implicit-rejection key, and accumulate differences across the complete ciphertext without early exit. Convert the final accumulation to a mask and select the output with bitwise operations. FIPS 203 specifies the decapsulation interface and its rejection behavior. <Cite id="fips203" locator="§7.3 (decapsulation and implicit rejection)" />

| Implementation choice | Instruction and address trace | Remaining concern | Test that discriminates |
| --- | --- | --- | --- |
| Prefix comparison with early return | Secret-dependent branch and loop length | Network timing and local cache effects | Compare distributions for ciphertexts with controlled matching prefixes |
| Full comparison followed by branch on result | Comparison work is fixed; output branch remains | Success and rejection paths may differ in latency or power | Include both output classes in statistical tests |
| Full comparison, both outputs derived, masked selection | No secret-dependent branch or index in source | Compiler may reintroduce a branch; power remains data-dependent | Inspect release assembly and run power evaluation |
| Faulted comparison or selection | May skip the check or corrupt the mask | Unchecked key output or distinguishable error | Inject faults and require a safe abort or the specified rejection output |

Constant-time repair removes one observable, not every observable. A library `memcmp` can hide an early exit behind an audited interface, but a compiler or provider update can change the generated code. A fault that skips comparison can also defeat a superficially correct path. Test the complete operation boundary, including cleanup and output serialization, because a secret-dependent error code can recreate the oracle even when the arithmetic is constant-time.

## A measurement and correlation walkthrough

Begin with a leakage hypothesis. Mark a secret byte, predict a candidate intermediate value under each key guess, and choose a time point or power window where that value should be processed. Fix message generation, clocking, warm-up and trigger alignment. Otherwise the experiment may measure workload variation rather than secret dependence.

For correlation power analysis, collect traces $T_i$ and predicted leakage $P_i(k)$ for every guess $k$. Compute Pearson correlation over the same trace window. The correct guess should correlate if the leakage model is accurate. Wrong guesses will also show random peaks, so evaluate enough traces, control multiple comparisons and confirm that the peak persists on held-out measurements.

Masking changes the distribution rather than merely obscuring a trace. A first-order arithmetic mask splits $x$ into two shares modulo a field or ring. If one share is uniform and independent, observing only that share reveals nothing about $x$. Nonlinear operations require secure multiplication gadgets; naively multiplying unmasked reconstructed values recreates the leak.

## A leakage model

A side-channel attack assumes a leakage function $L$ applied to intermediate values. A simple model is Hamming weight:

$$
L(x) = \mathrm{HW}(x) + \eta,
$$

where $\eta$ is noise. More realistic models include Hamming distance, bit transitions and device-specific power profiles.

## Correlation power analysis

For a guess $k$ of a secret-dependent byte, predict an intermediate value $v(k)$ and compute the correlation between the predicted leakage $L(v(k))$ and the observed traces. The correct key should produce a higher correlation than wrong guesses.

$$
\rho(k) = \frac{\mathrm{Cov}(L(v(k)), T)}{\sigma_{L(v(k))}\,\sigma_T}.
$$

With enough traces and a good model, the correct key emerges. Masking aims to make the joint distribution of shares independent of the secret.

## Masking

<Figure caption="Masking splits a secret into shares. Any single share is uniform, but the combination reconstructs the secret; masking must be combined with constant-time code and fresh randomness.">
  <MaskingDiagram />
</Figure>

Split a secret $x$ into $d+1$ shares:

$$
x = x_0 \oplus x_1 \oplus \cdots \oplus x_d.
$$

Any $d$ shares are uniformly random and reveal nothing in the probing model. Boolean masking suits bitwise operations; arithmetic masking suits modular addition and multiplication. Converting between them is a common source of bugs.

<Callout variant="lab" title="Proof sketch">
In the $d$-probing model, the adversary sees at most $d$ intermediate wires. A $d$-th-order masking scheme guarantees that any $d$ shares are independent of the secret. Real proofs also need composability and strong non-interference; a flawed refresh or a leaky conversion can break the guarantee. <Cite id="nikova-rechberger-rijmen2006" locator="§3.2–3.3" /> <Cite id="faust2018" locator="§1 and §4–4.1" />
</Callout>

## Fault models

A fault model specifies where and how an attacker can disturb computation: a bit flip in a register, a skipped instruction, a corrupted memory word. Security definitions such as fault-invariant security or combined fault-and-side-channel models are research-grade; engineering practice relies on redundancy, verification and physical countermeasures.

## Constant-time is not a proof of no leakage

Constant-time code prevents a specific class of observable, the instruction/address trace. It does not prevent power or EM leakage. Conversely, a masked implementation can still have timing leaks. Real assurance combines code review, formal tools, leakage assessment and hardware evaluation.

## What to formalise

- the leakage model,
- the adversary's number of traces and probes,
- the allowed fault set,
- the composition of countermeasures,
- the assumptions about randomness.

Without those, "side-channel resistant" is a marketing phrase.


## When masking passes a unit test but fails a campaign

A first-order masked multiplier passes its arithmetic test vectors: reconstructing the output shares always gives the correct product. During hardware evaluation, however, a correlation peak appears when the implementation converts Boolean shares to an arithmetic representation. The multiplication gadget is not the only secret-dependent operation; the conversion performs nonlinear work, and a refresh step reuses a mask from the previous invocation.

| Test or observation | What it establishes | What it does not establish |
| --- | --- | --- |
| Functional reconstruction | The shares encode the correct mathematical result | That intermediate shares are independent of the secret |
| Single-probe simulation | No tested wire leaks under the stated model | Security against two probes, glitches or a different placement |
| Static Hamming-weight correlation | Linear leakage under that model and time window | Absence of nonlinear or transition-based leakage |
| Fixed-mask versus fresh-mask comparison | Whether refresh and randomness affect the measured distribution | Higher-order security if only first-order combinations are tested |
| Held-out traces and second board | Whether the effect reproduces beyond the tuning set | A universal guarantee across future hardware revisions |

DPA predicts an intermediate value under each key guess and correlates that prediction with many traces; the correct guess should stand out when the leakage model and alignment are appropriate. <Cite id="kocher1999" locator="pp. 388–397" /> In a masked design, the evaluation must also vary masks and test joint observations, not merely compare average power. A stale mask can correlate shares across executions, while a leaky conversion can expose a combination even when each input share looks uniform in isolation.

A useful campaign first validates sensitivity with a deliberately weakened implementation: reuse a mask or omit a refresh and confirm that the chosen distinguisher detects it. Then collect traces for the repaired design, randomise public inputs and masks, and evaluate on data not used to choose probe points. Testing many time samples and many guesses creates multiple comparisons, so a peak must survive a predeclared significance rule and independent replication. FIPS 205 explicitly identifies side-channel and fault protection as implementation considerations beyond the hash-based signature definition. <Cite id="fips205" locator="§3.2 (side-channel and fault attacks)" />

The repair follows the evidence. Refresh masks with fresh entropy at the required boundary, replace the conversion with a reviewed gadget, and examine transition effects if glitches may expose adjacent shares. Re-run the functional vectors and the full leakage campaign; a successful unit test is necessary for correctness but says little about the distribution the attacker observes.

## Formalising leakage and constant time

A leakage model is a family of distributions $\{\mathcal L_s\}$, one for each secret $s$. A useful countermeasure makes the distributions for different secrets close under a stated metric, such as statistical distance or mutual information, after at most $Q$ observations. This is stronger and more precise than saying that two sample means look similar. The model must also state which intermediates the attacker can observe and whether observations can be chosen adaptively.

Pearson correlation measures linear dependence between a prediction and a trace. It can miss nonlinear leakage, and a high value can arise from an inaccurate model that happens to track public workload. A statistically significant peak must survive trace randomisation, a held-out set and correction for the number of tested points and guesses. The four-trace example is arithmetic intuition, not a security test.

Constant-time programming constrains the instruction and address trace. For every pair of secret inputs, execution follows the same sequence of public branches, loop bounds and memory addresses. Secret values may still determine register contents and arithmetic operations. This directly addresses branch and cache-index timing, but it says nothing by itself about power, electromagnetic emanations or fault behaviour. A full-table scan removes the secret index but still processes secret-selected data in registers.

In the $d$-probing model, an adversary observes at most $d$ intermediate wires during one execution. With $d+1$ shares and at least one fresh uniform share, any set of $d$ shares can be independent of the secret. For Boolean sharing, $x=x_0\oplus\cdots\oplus x_d$; conditioning on any $d$ shares leaves the remaining share uniformly distributed. For arithmetic sharing, the same statement holds under addition modulo the relevant ring. <Cite id="nikova-rechberger-rijmen2006" locator="§2–3.3" />

The proof becomes harder for nonlinear operations. Boolean AND, modular multiplication, comparisons and decompression need gadgets whose every intermediate probe set is secure. Strong non-interference requires that extending the observed probe set does not reveal additional secret information. Composability requires that a secure gadget remains secure when placed in a larger circuit. Transition-based leakage models additionally treat glitches between clock cycles. A scheme that is secure against one static probe can fail against two probes at different times if shares are not refreshed.

Masking also consumes randomness and verification effort. Fresh masks must be independent across operations and unpredictable to the attacker. A refresh that reuses a mask can correlate shares. Conversions between Boolean and arithmetic masking are frequent leakage points because they involve nonlinear operations. Hardware glitches can bypass a register boundary and expose multiple shares even when source-level probes were analysed separately.

Fault models should name the fault primitive: a bit flip, a skipped instruction, a corrupted memory word or a repeated computation. A fault may directly break correctness, reveal a secret through differential comparison, or alter control flow so that masking shares become visible. Redundancy helps only if the duplicated computations have sufficiently independent failure modes. Verify-before-release catches many invalid outputs, but physical sensors and protected state machines may still be needed.

The assurance claim is a conjunction. Constant-time source, a masked nonlinear gadget and redundant output checking protect different observables. If any one is absent, the system may remain secure under a narrower model but not under the stated attacker. Document the leakage metric, number of probes, trace budget, fault set and composition assumptions alongside the test results. Without these, a pass/fail label has no stable meaning.
</Lens>

## Constant-time patterns

```c
/* Secret-independent selection, no branch, no secret index. */
static inline uint32_t ct_select(uint32_t mask, uint32_t a, uint32_t b) {
    return (a & mask) | (b & ~mask);
}

/* Full scan: every line is touched, then selected in registers. */
uint8_t value = 0;
for (size_t i = 0; i < TABLE_LEN; i++) {
    uint8_t mask = ct_eq_size(i, secret_index);
    value |= table[i] & mask;
}
```

The compiler may transform these patterns. Use a compiler barrier that does not change semantics, inspect the assembly, and test on the target toolchain.

## Rules that survive contact with optimisers

1. No branches on secret values.
2. No array indices derived from secrets.
3. No variable-time division or modulo on secrets.
4. No early-exit comparisons.
5. No secret-dependent loop bounds.
6. No floating point in the reference path.
7. Zeroise secrets, and keep them out of logs and crash dumps.

<Callout variant="danger" title="Compiler transformations">
`if (secret) x = a; else x = b;` may compile to a branch or a conditional move depending on optimisation level and target. A timing test at `-O2` is not evidence at `-O3` for a different CPU. Validate the actual artifact.
</Callout>

## Validation tools

- **`dudect`** for statistical timing leakage.
- **`valgrind`/ctgrind** style taint analysis for secret-dependent branches and addresses.
- **`ct-verif`** and formal constant-time verifiers for compiled code.
- **Power/EM evaluation** with a leakage assessment methodology (TVLA or equivalent).
- **Fault injection** campaigns on real hardware.

## PQC implementation notes

- **NTT:** unroll and vectorise, but keep the control flow independent of coefficients. Lazy reduction must not introduce secret-dependent correction branches. <Cite id="longa2016" locator="pp. 124–139" />
- **Montgomery/Barrett:** branch-free reduction is essential. <Cite id="montgomery1985" locator="Vol. 44, pp. 519–521" />
- **Decapsulation:** compute the rejection key unconditionally and select it with a mask.
- **Signing:** use constant-time sampling; hedged signing helps but does not replace constant-time code; verify before releasing a signature.
- **Memory:** use locked pages where appropriate, clear buffers, avoid copying secrets into uninitialised padding.

## A release-gate protocol with stated sensitivity

A provider update changes the compiler's handling of a bitwise selection idiom. Functional vectors pass, but the new binary contains a conditional branch on a rejection flag. The old timing report no longer describes the deployed artifact. A release gate must therefore bind reports to an exact build and define what happens when evidence is missing, rather than carrying forward a green badge.

| Gate | Artifact or evidence | Pass criterion | Failure action |
| --- | --- | --- | --- |
| Build identity | Source revision, compiler, flags, provider and target | Matches the evaluated cryptographic bill of materials | Rebuild or repeat affected evaluation |
| Static review | Taint results and generated assembly | No secret-derived branch, address, loop bound or variable-latency call | Fix code or replace the primitive |
| Timing | Fixed-secret, randomised-input distributions | No detected difference above the predeclared sensitivity and trace budget | Isolate, diagnose and retest before release |
| Power and EM | Aligned traces plus weakened positive control | Setup detects the known leak; repaired design meets the stated order and threshold | Review masks, gadgets, probe model and hardware |
| Fault injection | Comparison, sampling and output paths | Faults produce safe abort or specified rejection, never unchecked secret-dependent output | Add detection or redesign the protected path |
| Operational control | Logs, crash dumps, memory wiping and support tooling | No secret exposure and reproducible field-build mapping | Fix handling before deployment |

Statistical timing tests need a planned sample size and a minimum effect of interest. “No significant difference” after 200 measurements may only mean the experiment lacked power. Power campaigns need aligned triggers, stable sampling and enough traces to estimate variance; fault campaigns need to record whether the device aborted, returned a normal rejection value or released an output. A crash is not automatically a secure outcome, and a clean result on one board does not cover every probe location. <Cite id="whitnall-oswald2019" locator="§3.1, §3.3 and §5.2" />

The liboqs reference implementations and KEM/signature test harness provide a starting point for functional and implementation regression, but their results must be tied to the actual release build and hardware. <Cite id="liboqs" locator="Reference implementations and KEM/signature test harness" /> Run a deliberately weakened reference as a positive control to prove the laboratory setup can see the target leak. Keep held-out traces for final confirmation and repeat the affected gates after any compiler, provider, CPU-feature or hardware change.

Report an effect size and uncertainty interval, not only a pass/fail p-value. For timing, compare paired measurements for each public-input class while keeping the secret fixed; for power, report the tested probe order, trace count and correction for multiple time points and guesses. Choose the sample size and exclusion rules before viewing final data, and investigate outliers rather than deleting them to obtain a clean result. A nonsignificant result means the experiment did not detect leakage above its stated sensitivity in that setup. It does not prove that leakage is impossible. <Cite id="whitnall-oswald2019" locator="§5.2 and §7" />

The resulting claim is bounded and reviewable: this artifact, under this attacker model, at this sensitivity.

<Callout variant="danger" title="Validate the deployed artifact">
A constant-time claim at the source level does not survive a different compiler, optimisation level or CPU. Re-run validation after toolchain or hardware changes.
</Callout>

## Patterns that survive optimisation

Use explicit-width unsigned arithmetic and documented masks. Equality can be accumulated with XOR and OR, then converted to a selection mask. Selection uses bitwise operations, not a conditional expression that a compiler may lower to a branch. Avoid calling general-purpose `memcmp` on secret-dependent data. For a full-table scan, keep the loop bound public and select the matching entry in a register after touching every line.

Modular reduction needs the same discipline. A conditional subtraction based on a secret coefficient should become a comparison mask and a bitwise add or subtract. Avoid variable-time division on secret operands. Montgomery and Barrett methods replace division but still require bounded intermediates and branch-free correction. Vector lanes do not change this rule; a conditional lane operation can still be lowered to a branch or create data-dependent timing.

Static analysis should start with taint labels on the secret key, shares, nonce and rejection seed. Flag any branch condition, memory address, loop bound or variable-latency call derived from those labels. Then inspect the generated assembly for the release flags. Source-level tools can miss compiler-introduced checks or library calls. Keep a list of approved primitives and investigate any new intrinsic or provider call in the cryptographic path.

Timing validation needs controlled experiments. Use `dudect` or an equivalent statistical test with fixed secret values, randomised public inputs and enough samples to estimate the distribution. Run on an isolated, frequency-stable target and repeat under realistic load. A nonsignificant result is evidence only for the tested artifact and sensitivity; it is not a universal proof.

Power and electromagnetic validation should use a leakage-assessment process such as TVLA or a task-specific correlation campaign. Fix the trigger, trace window and device configuration. Test first-order and, where relevant, higher-order leakage across probe locations. Include fresh-mask and repeated-mask test modes so the evaluator can confirm that the setup detects a deliberately weakened implementation. <Cite id="schneider-moradi2015" locator="§2–3" />

Fault campaigns should vary voltage, clock and electromagnetic disturbance while recording output and detection behaviour. Inject faults into comparison, sampling, norm checks and hash-address generation. A secure response may abort, return the standard rejection value or repeat a computation, depending on the interface. It must not expose a secret-dependent error or release an unchecked signature.

Operationally, record a cryptographic bill of materials: source revision, compiler, flags, target CPU, provider and hardware revision. Gate deployment on all required reports. Re-run affected tests after any change, including a seemingly harmless library update. Keep a reproducible build so a field report can be matched to the evaluated binary.

Zeroisation is a supporting control, not a side-channel proof. Clear secret buffers on every exit, avoid uninitialised padding in exported structures, and prevent crash dumps from capturing key material. Locked memory pages can reduce swapping but do not hide register or power leakage. Review logs and support tooling with the same suspicion as the cryptographic code.
</Lens>

## Common failure modes

| Failure | Cause | Impact | Prevention |
| --- | --- | --- | --- |
| Early-exit secret comparison | General-purpose comparison or manual break | Timing oracle | Full-length bitwise accumulation |
| Secret-indexed table | Sampling or decompression lookup | Cache and timing leakage | Full scan or audited register selection |
| Conditional modular correction | Branch on a secret coefficient | Timing and control-flow leakage | Comparison mask and branch-free arithmetic |
| Variable-time division | Hardware divider latency depends on operands | Timing leakage | Barrett or Montgomery reduction |
| Mask is reused | Refresh logic is skipped for speed | Shares become correlated | Fresh randomness and refresh tests |
| Masking gadget lacks composability | Individual operations pass, composition leaks | Higher-order probing leakage | Review full circuit and transition effects |
| Fault path returns a distinct error | Error handling exposes detection | Fault and validity oracle | Safe abort or standard rejection interface |
| Validation covers only source | Compiler or provider changes the binary | Unseen branch or library call | Pin and inspect the release artifact |

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Timing distributions differ only under load | Secret-dependent path amplified by contention | Isolate the test, inspect control flow and repeat |
| Taint tool flags a library call | Hidden comparison, division or address derivation | Replace with an audited constant-time primitive |
| TVLA detects leakage after masking | Stale mask, leaky conversion or insufficient order | Review refresh, gadgets and probe model |
| Power result changes between boards | Probe placement, clock or device variation | Standardise setup and increase sample coverage |
| Fault produces a signature or key output | Detection is bypassed or output is unchecked | Add redundancy and verify before release |
| New build fails leakage regression | Compiler or provider transformation | Diff assembly and re-run the full affected test set |

## Design review checklist

- [ ] Secrets, observables, probe counts, trace budget and fault capabilities are explicit.
- [ ] No branch, loop bound, address or variable-latency call depends on a secret.
- [ ] Comparisons process the complete public or secret-dependent input without early exit.
- [ ] Sampling, decompression and table access use reviewed constant-time patterns.
- [ ] Modular reduction has proved bounds and branch-free correction.
- [ ] Masking uses fresh randomness and reviewed nonlinear gadgets and refreshes.
- [ ] Static taint and generated-assembly checks cover the exact release artifact.
- [ ] Timing, power/EM and fault tests each have a stated method and sensitivity.
- [ ] Weakened positive controls confirm that the test setup can detect leakage.
- [ ] Faults cannot expose secret-dependent errors or unchecked signatures.
- [ ] Compiler, provider, CPU and hardware changes trigger revalidation.
- [ ] Secret wiping, logs and crash dumps are included in the operational review.

## Key takeaways

- Side channels attack the implementation, not the mathematical definition.
- Constant-time code prevents timing and cache-index leaks; masking and hiding address power/EM.
- Faults require redundancy and verification, not just encryption.
- Leakage models and validation methods define what a security claim means.
- PQC introduces new secret-dependent code paths that need the same discipline.
