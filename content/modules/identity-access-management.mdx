## Four questions that systems often collapse

Identity and access management becomes confusing when one token is asked to answer four different questions. **Authentication** establishes that a claimant controls an authenticator associated with an identity. **OAuth delegation** grants a client scoped access to a protected resource. **OIDC authentication** adds an identity layer that lets a relying party consume claims about the authenticated user and session. **Authorisation** decides whether that subject may perform a specific action on a specific object now.

The distinctions are operational. A user may authenticate successfully but possess no permission for a report. An OAuth access token may authorise a narrow API scope without telling the client who the user is. An ID token may identify the user to the relying party but must not be used as an API credential. A service identity may hold a valid credential without representing a human at all.

OAuth 2.0 defines an authorization framework in which a client obtains an access token and uses it to request a protected resource. The authorization grant flows are specified separately from resource-server behaviour. <Cite id="rfc6749" locator="§1 and §4" /> OpenID Connect Core adds authentication on top of OAuth, including the authorization request, ID token and validation rules. <Cite id="oidc-core" locator="§3.1 and §3.1.3.3" /> Treating OAuth as a complete login protocol is a common source of confused-deputy and token-confusion bugs.

## Name the actors and the boundary between them

A useful OIDC diagram names four actors:

- the **resource owner**, usually the person whose data or authority is involved;
- the **relying party**, the application that wants an authenticated identity or delegated access;
- the **authorization server**, which authenticates the user, obtains consent and issues tokens;
- the **resource server**, which accepts an access token and enforces API policy.

The browser carries messages but is not a trusted storage boundary for application secrets. The authorization server and relying party may be different security domains with different operators, retention rules and compromise assumptions. The resource server may be a separate service again. A token crossing each boundary needs receiver-specific validation and a clear purpose.

Draw arrows for the authorization request, authorization code, token request, token response and protected-resource request. Label which values are visible in each hop. Then add local session creation at the relying party and object-level policy at the resource server. Those two steps are frequently omitted from diagrams even though they determine whether a successful protocol exchange becomes a secure application session.

## Authentication assurance is contextual

An authentication event has more than a boolean success flag. It includes the authenticator type, whether user verification occurred, how the identity was proofed, when authentication happened and whether step-up authentication is required for the requested action. NIST SP 800-63B-4 addresses authentication and authenticator management, including assurance and lifecycle considerations. <Cite id="nist-sp800-63b-4" locator="§3–5, authenticator assurance and lifecycle" /> A product should choose requirements from its risk model rather than labelling every multifactor-looking login as equivalent.

Recovery is part of authentication design. A weak help-desk process can bypass a strong passkey. A backup code with low entropy or unlimited attempts can become the easiest path into an account. Store recovery material using the protections appropriate to its purpose, rate-limit use, notify the user and require re-enrolment after recovery. Measure recovery success and abuse together.

## Zero trust does not mean identity alone is enough

NIST's Zero Trust Architecture treats access as a dynamic decision using multiple signals rather than assuming everything inside a network perimeter is trusted. <Cite id="sp800-207" locator="§2–3, tenets and architecture" /> Identity is one important signal. Device posture, resource sensitivity, session risk, policy version and requested action may also matter.

For a hosted task manager, a valid employee identity does not imply permission to export every workspace. A contractor's device may be healthy but still lack entitlement to payroll data. A service token may be valid but scoped only to one queue. The practical policy question is: which subject may do which action on which object, under which current conditions? Answer that at the resource, not merely at the front door.

## A scenario with three identities

Imagine a customer workspace that contains employees, external collaborators and automation. A person signs in with a passkey through a workforce identity provider. A collaborator receives a scoped invitation. A background service reads a queue using its own workload identity. The browser application, workforce provider, collaboration service and task API all exchange claims or tokens.

Now suppose the person creates an external sharing link. That action changes access for someone who may never authenticate to the workforce provider. The sharing service must record the grant, its scope and expiry. The API must enforce the grant on each request. Revoking the link must invalidate the grant without disabling the owner's workforce login. One undifferentiated session model cannot safely represent these relationships.

## Write an identity inventory before choosing a protocol

Record human identities, service identities, external collaborators and machine-to-machine workloads separately. For each, document issuer, authenticator, assurance requirement, token audience, scopes, session lifetime, owner, recovery method and revocation path. Include break-glass identities and legacy migrations.

This inventory reveals where federation ends and local authorisation begins. It also prevents scope inflation: a background worker should not inherit every permission its developer possesses, and a read-only reporting client should not receive write scope merely because the issuer supports it. Least privilege starts with an explicit inventory of purpose.

## Identity keys are scoped, and account linking is a security event

Two issuers can legitimately issue the same `sub` value to different people. The JWT specification defines `sub` as identifying the principal in the context of the issuer, not as a globally unique username. <Cite id="rfc7519" locator="§4.1, registered claim names — subject" /> A resource server that stores only `sub` can therefore merge an external collaborator with an internal administrator. Store the issuer and subject together, preserve their original string forms and define which provider is authoritative for each identity namespace.

Email is not a durable substitute. A provider may report an unverified address, a person may change it and a workspace may allow aliases. Automatic linking on a matching email can produce account pre-hijacking: an attacker creates a federated identity with an address they do not yet control, waits for the victim to use that provider and then gains access to the linked account. Linking to an existing local account should require proof of the existing account or an explicit, authenticated account-linking ceremony. Record who approved the link and how the decision can be reversed.

## Why this flow fits browsers and modern clients

The authorization-code flow keeps the authorization response separate from token issuance. The client sends the user to the authorization server, receives a short-lived code through the browser and redeems that code for tokens. <Cite id="rfc6749" locator="§4.1, authorization code grant" /> PKCE adds a proof of possession derived from a high-entropy verifier created by the client. It is especially important for public clients that cannot keep a client secret, and it is also recommended for confidential clients.

A safe implementation follows a precise sequence:

1. The relying party creates a fresh, high-entropy PKCE verifier and derives its S256 challenge.
2. It creates an unpredictable state value and, for OIDC, a nonce bound to this authentication attempt.
3. It redirects the browser to the authorization server with the exact registered redirect URI, client identifier, requested scope and PKCE challenge.
4. The authorization server authenticates the user and obtains any required consent.
5. It returns a one-use authorization code to the registered redirect URI.
6. The relying party exchanges the code over a protected back-channel, presenting the verifier and client authentication where applicable.
7. The authorization server verifies the binding, consumes the code and returns tokens.
8. The relying party validates the tokens and creates a local session with a bounded lifetime.
9. The client uses the access token only at the intended resource server.

## Redirect validation is exact matching, not a convenient pattern

Register complete redirect URIs and compare them exactly. A wildcard or prefix match can send a code to an attacker-controlled path or host. Native applications and loopback callbacks have platform-specific considerations, so use a reviewed library and document the client type rather than copying a web callback rule into every environment.

Reject unexpected query parameters, fragments and path normalisation at registration and validation time. The authorization server should require protected transport for browser and token endpoints. Never include a client secret in front-end JavaScript. A confidential web client can keep a secret server-side, but that secret does not replace redirect validation or PKCE.

## State and nonce protect different bindings

State binds the authorization response to a browser transaction at the relying party. Store the expected value server-side or in a protected, integrity-bound transaction record, compare it on return and consume it once. A missing or repeated state value can indicate login CSRF, in which an attacker causes a victim's browser to complete the attacker's login flow.

Nonce binds an OIDC ID token to the authentication request. The relying party generates it, sends it in the request and requires the returned ID token to contain the same value. It helps detect token replay or substitution even when the signature is valid. State is not a JWT claim, and nonce is not a substitute for state. <Cite id="oidc-core" locator="§3.1.2.1 and §3.1.3.3" />

## Understand code interception before testing the fix

An adversary who observes an authorization code may try to redeem it before the legitimate client. Without PKCE, possession of the code may be enough for a public client. With S256 PKCE, the adversary cannot create the matching verifier from the challenge, so the forged redemption fails. The legitimate client then succeeds if its redirect binding and transaction state are intact.

OAuth 2.0 Security Best Current Practice collects these threats and mitigations, including redirect URI handling, authorization-code threats and token protections. <Cite id="rfc9700" locator="§2–4, threats and mitigations" /> Use a maintained protocol library where possible, but still test its configuration. A library can perform correct cryptography while accepting an unsafe redirect list or omitting nonce validation.

## Tokens have jobs, audiences and lifetimes

An **access token** is presented to a resource server. It may be a JWT or an opaque string. Its audience is the API or resource that accepts it. A **ID token** is delivered to the relying party and contains claims about the authentication event. Its audience is the client. A **refresh token** is used at the authorization server to obtain new access tokens, subject to the grant's rules.

Do not swap these jobs because a value happens to be a signed JWT. An API that accepts an ID token as an access token has confused two audiences and two trust decisions. A relying party that calls an API with its ID token has repeated the mistake in the other direction. Use separate configuration, names and tests for each receiver.

Access tokens should be short enough to bound exposure but long enough for the application's availability needs. Refresh tokens need protected storage, rotation where supported, reuse detection and a revocation path. Rotation can limit the value of a stolen refresh token, but it does not automatically invalidate already issued access tokens. The resource server must have a strategy for those remaining credentials.

A front-end should not store long-lived credentials in broadly readable locations merely for convenience. A server-side session with protected cookie handling is often appropriate for a browser application, but the right design depends on the client type and XSS exposure. If tokens must reach browser code, minimise their lifetime and scope, protect against script injection and define a rotation and revocation strategy.

## Give each transaction value a lifecycle

State, nonce, authorization code and PKCE verifier are often described as four strings to generate. Their security properties come from where each value is created, where it is exposed, how it is checked and when it is destroyed.

| Value | Created and stored by | Crosses the browser as | Must be checked by | Lifecycle failure |
| --- | --- | --- | --- | --- |
| `state` | Relying party, bound to its browser session | Authorization request and response | Relying party callback | Missing, predictable or reusable state permits login CSRF or response substitution |
| `nonce` | Relying party, bound to one authentication attempt | Authorization request; echoed in the ID token | Relying party ID-token validator | A valid token from another attempt can be accepted |
| Authorization code | Authorization server | Redirect response, therefore browser-visible | Authorization server during redemption | Reuse, leakage or a mismatched redirect receiver breaks code binding |
| PKCE verifier | Client, kept out of front-channel URLs | Never sent in the authorization request; only the challenge is sent | Authorization server during redemption | Reuse or a weak verifier weakens proof of possession |

Consider two login tabs. Tab A generates `state-A`; tab B generates `state-B`. If the callback handler merely checks that `state` is present, a response initiated in one tab can complete the other tab's session. Store the expected value in a transaction record keyed to the protected browser session, compare it exactly and consume it once. Bound the record's lifetime. A state value is not a secret that must be hidden from the authorization server, but its unpredictability and one-time use stop an attacker from supplying a chosen transaction.

Code redemption needs a similar discipline. A successful first exchange must make a second exchange fail even when it presents the right verifier. Test this deliberately. Consume state once on callback, but retain the nonce and verifier until exchange and validation complete. On failure, invalidate the entire attempt and return a minimal error rather than silently starting a new login under the old state.

OAuth's security guidance treats redirect handling, code injection and token replay as distinct threats. <Cite id="rfc9700" locator="§2–4, threats and mitigations — authorization code and redirect protections" /> OIDC binds the nonce through its authentication and ID-token validation rules. <Cite id="oidc-core" locator="§3.1.2.1 and §3.1.3.3 — nonce and ID token validation" /> Test these controls as a sequence: a correct signature cannot rescue a stale nonce, and PKCE cannot rescue a callback delivered to the wrong URI.

## A signature proves origin, not suitability

JWT is a compact claims format with encoded header, payload and signature segments. Registered claims include issuer, subject, audience, expiration, not-before and issued-at values. <Cite id="rfc7519" locator="§4.1, registered claim names" /> OIDC adds requirements for using an ID token during authentication. <Cite id="oidc-core" locator="§3.1.3.3, ID token validation" />

A valid signature answers a narrow question: did a holder of the selected issuer key sign these bytes? It does not answer whether the issuer is one this receiver trusts, whether the token was meant for this client, whether it is expired, whether it belongs to this login attempt or whether its subject may access the requested object. Decoding a token in a browser is inspection, not verification.

## Validate the receiver's expectations explicitly

Build a validation profile for each token type and receiver. For an OIDC ID token, the relying party normally checks the signature with an allowed algorithm and issuer key, exact trusted issuer, audience containing its client identifier, expiration and not-before against the current time, and the expected nonce. Depending on the flow, it may also require issuance time, authentication time or an authorised-party claim.

For an API access token, the resource server checks its own trusted issuer, its own audience, lifetime and relevant scope or authority. It must not accept the OIDC client identifier as the API audience unless an explicitly reviewed shared-audience design says so. After token validation, it evaluates resource policy. A subject claim from a signed token is useful, but it does not establish ownership of a report.

## Handle algorithms and keys as policy

Do not accept an algorithm merely because it appears in the token header. Select an allowlist from the issuer's supported configuration and the receiver's security requirements. Reject unsigned tokens and algorithm-confusion attempts. A key identifier helps select a verification key; it does not establish trust by itself.

Authorization servers rotate signing keys. Cache published JSON Web Key Sets with bounded freshness, key identifiers and retry behavior. A key rotation can temporarily produce an unknown key identifier. A safe response may refresh the key set once and retry verification, then fail closed. Do not disable signature checks during an outage, and do not accept a key supplied by the token presenter.

Separate key rollover from issuer migration. A new key for the same issuer may be a routine rotation; a new issuer string is a different trust decision. Record both in telemetry and configuration, with an owner and rollback plan.

## Expiry, replay and revocation are different controls

Expiration limits how long a token can be accepted under normal validation. Nonce binds an ID token to one login transaction. Replay detection for bearer access tokens is harder: anyone who copies a valid token may present it before expiration, and self-contained JWT verification does not remember previous uses. A gateway token-identifier cache can detect some replays, but it is not a universal substitute for short lifetimes, protected storage, revocation or sender-constrained credentials.

Revocation may happen through refresh-token revocation, session termination, account disablement or resource-server introspection. Each has a different propagation delay. Define how long a revoked session may remain usable and whether that delay is acceptable for the resource. Cache introspection results only with a bounded lifetime and clear failure policy.

## Follow the authorisation chain after signature validation

A token can pass every cryptographic check and still fail the application's security question. Consider a reporting client that obtains an access token with `reports:read`. The API verifies the issuer, signature and its own audience successfully. It then returns every report because the handler treats the scope as permission to read all objects. The token establishes a capability ceiling; it does not establish ownership, tenant membership or the sensitivity of a particular export.

Multi-hop delegation adds another boundary. A front end may exchange a user credential for a narrower service token, and that service may call a downstream API. Each receiver must validate the token it actually receives against its own issuer, audience, type and lifetime. A downstream service must not assume that an upstream authorisation decision covered the downstream action. If actor or delegation claims are present, validate their meaning under the issuer's profile rather than inventing a universal `act` rule.

OIDC also distinguishes the client audience from an authorised party. When an ID token has multiple audiences, the authorised-party claim identifies the party the token was issued to; a relying party should check it when present. <Cite id="oidc-core" locator="§3.1.3.3 — ID token validation, audience and authorized party" /> This is a receiver check, not something the browser can establish by decoding claims.

| Credential | Intended receiver | Binding that must succeed | Application decision that remains |
| --- | --- | --- | --- |
| ID token | The relying party named by `aud` | Trusted issuer, signature, audience, time, nonce and authorised party where applicable | Which local account and session assurance apply? |
| User access token | The resource server named by `aud` | Trusted issuer, signature or introspection, audience, time and required scope | May this subject perform this action on this object? |
| Client-credentials token | The intended API | Client identity, audience, time and granted authority | Is the workload entitled to this tenant or operation? |
| Refresh token | The authorization server | Grant binding, client authentication where required, rotation and reuse state | Should the grant be renewed or revoked now? |

Opaque access tokens shift verification rather than removing it. The resource server or its introspection service must authenticate the response, enforce token type and audience expectations, and bound caching. A network failure must not turn unknown token status into acceptance unless a deliberately reviewed, low-risk degraded mode exists.

Keep token acceptance and resource authorisation as separate, observable decisions. Log the receiver profile, token type, issuer, key identifier or introspection outcome, policy version and object result without logging the token. This separation lets an operator distinguish a validation outage from an authorisation bug and prevents “valid token” from being mistaken for “authorised request”.

JWT encodings use base64url, which is an encoding rather than encryption. Anyone who can see a JWT can read its claims. Never put passwords, private keys or unnecessary sensitive attributes in a token. Minimise claims, protect logs and redact authorization headers. Token size also affects headers and intermediaries, so keep custom claims proportionate to a real requirement.

Run the suite against both local validation code and any gateway or sidecar that also makes token decisions. Two components with different issuer or clock configuration can create an outage or a security gap.

## WebAuthn is a credential ceremony, not an OAuth grant

WebAuthn lets a relying party create and later verify public-key credentials. During registration, the authenticator creates a new key pair and returns a credential identifier and public key after a ceremony involving a fresh challenge and relying-party context. During authentication, it signs a new challenge. The server verifies the assertion with the stored public key and its own expected relying-party identifier. <Cite id="webauthn" locator="§5–10, ceremony, credentials and assertions" />

This removes the shared password secret from the authentication exchange and provides origin-bound, phishing-resistant proof under the ceremony's assumptions. It does not grant API scopes, create an OAuth access token or decide which records the user may read. OIDC may carry the result of a passkey authentication performed by an identity provider, while the application's resource server still authorises access.

## Passkeys have deployment and assurance details

A passkey may be device-bound or synchronised through a platform credential provider. Recovery, revocation and device-loss behavior differ. A synchronised credential is not automatically weaker or stronger; evaluate the provider, account recovery, attestation and threat model. Biometric comparison normally happens locally on the user's device. The server receives an assertion, not a fingerprint or face template.

User presence and user verification are different ceremony properties. Configure the required policy explicitly and verify the returned result rather than assuming every authenticator behaves the same way. NIST assurance levels depend on the complete authentication method, authenticator characteristics and deployment, not the marketing term passkey. <Cite id="nist-sp800-63b-4" locator="§3–5, authenticator assurance and lifecycle" /> Require additional factors or proofing where the risk assessment demands them.

Attestation can help assess authenticator properties, but it is not continuous proof that a device remains trustworthy. Decide which attestation roots or metadata your service trusts, how often to update them and what to do when attestation is unavailable. Do not confuse authenticator attestation with the authorization server's signing keys or the resource server's TLS certificate.

## Test WebAuthn failure modes at the ceremony boundary

WebAuthn verification is a collection of context checks, not a single signature call. The server supplies the expected relying-party identifier and a fresh challenge, stores the credential public key for the correct account, and validates the authenticator data and assertion signature. An implementation can verify the signature correctly while accepting the wrong origin context, a reused challenge or an unrelated credential.

| Failure mode | Incorrect acceptance | Required check and test |
| --- | --- | --- |
| Relying-party scope | A credential created for a different host is accepted | Compare the authenticator's RP ID hash with the hash of the expected RP ID; test parent and sibling hostnames |
| Challenge replay | An old assertion is reused to create another session | Store a fresh challenge with a short expiry, consume it once and reject repeats |
| Credential-to-account binding | A valid credential is attached to the wrong local account | Look up the credential by its identifier and verify the stored public key belongs to the authenticated account |
| Ceremony flags | Presence is treated as user verification | Require the configured `UP` and `UV` results and test authenticators that return different combinations |
| Counter policy | Clone detection is assumed from a counter that is not maintained | Define provider-appropriate signature-counter handling; a zero counter can be normal for some synchronised credentials |
| Attestation policy | Unavailable or untrusted attestation silently passes | Make the trust roots, metadata freshness and failure mode explicit for the required assurance level |
| Registration context | A stolen session enrols an attacker's credential | Require appropriate recent authentication or step-up for adding a credential and bind registration to the verified account session |

Consider an attacker with a stolen but still valid portal session. If the registration endpoint accepts a new public key without fresh authentication, the attacker can enrol a passkey they control and later sign in without the victim's password. The signature ceremony may be technically perfect while the enrolment decision is wrong. Registration is a privileged account change, not merely another login.

The WebAuthn ceremony and credential model defines the relying party, challenge, authenticator data and assertion verification that support these checks. <Cite id="webauthn" locator="§5–10 (ceremony, credentials and assertions)" /> A test suite should include wrong RP ID, reused challenge, unknown credential, altered signature, missing user-verification result and registration under a stale session. Test recovery separately: revoking one passkey must not silently remove every authenticator, and enrolling a replacement must not revive a credential the user intended to revoke.

## Authorisation needs an object model

Role-based access control is a useful starting point, but a role name rarely captures tenant, ownership, state and delegated grants. Define resources, actions, subjects, tenants and relationships. Decide whether permission is inherited, explicitly granted, time-bounded or conditional. Use a central policy component or service with versioned rules and deterministic tests.

Evaluate policy close to the resource. A controller can pre-filter a list for usability, but the data layer or resource service must enforce the same boundaries for direct access and background jobs. Avoid checking only a parent object when a child has a different sensitivity. Export, share, delete and administrative impersonation often require stronger checks than ordinary reads.

Policy inputs should come from validated identity and server-side state. Do not let a request assert its own role or tenant. If policy depends on group membership, define propagation delay and revocation expectations. If it depends on a device or risk signal, define stale-data behavior. Missing context should produce a deliberate decision, usually denial for protected resources.

## Operate joiner, mover and leaver lifecycles

Joining an identity involves proofing, authenticator enrolment, group assignment and owner approval. Moving roles requires removing old access as well as adding new access. Leaving requires disabling authentication, revoking sessions, rotating or removing credentials, transferring ownership and verifying that delegated grants no longer work.

Service identities need the same discipline. Rotate workload credentials, store them in appropriate protected systems, scope them to resources and assign an owner. Avoid interactive developer credentials in production. Review unused grants and dormant clients on a schedule.

<Callout variant="warning" title="Recovery is a privileged authentication path">
Treat support-assisted recovery, backup authenticators and emergency access as production authentication mechanisms. Rate-limit them, require strong proofing, notify affected users, audit use and test that old credentials stop working after recovery.
</Callout>

## Test revocation end to end

A successful logout button is not proof of revocation. Define which credentials are invalidated: the local session, refresh token, authorization-server session, access tokens and authenticator. Test each one. A copied access token may remain valid until expiry unless the resource server has a faster revocation signal. Record the maximum residual access window and get explicit risk acceptance where necessary.

For passkeys, removing one credential should not remove every authenticator unless the account is compromised. For a lost device, revoke the specific credential and require recovery or another enrolled authenticator. For a suspected issuer compromise, rotate signing keys, invalidate affected sessions and communicate the trust change. For a departed administrator, remove privileged roles and review tokens or grants issued during the tenure.

## Common failure modes

| Failure mode | Observable symptom | Root cause | Guardrail |
| --- | --- | --- | --- |
| ID token sent to API | API accepts a portal client token | Token purposes and audiences confused | Separate profiles and reject wrong API audience |
| Wildcard callback | Code reaches attacker-controlled URI | Prefix or pattern redirect matching | Register and compare complete URIs exactly |
| Public client without PKCE | Intercepted code redeemed | No proof of verifier possession | S256 PKCE and one-use authorization codes |
| State or nonce omitted | Login CSRF or token substitution | Browser transaction not bound | Fresh state and OIDC nonce with one-time validation |
| Signature-only JWT check | Wrong issuer or client token accepted | Receiver expectations omitted | Validate issuer, audience, time, nonce and algorithm |
| Signature checks disabled during rotation | Invalid tokens accepted | Unsafe outage workaround | Bounded JWKS refresh and fail-closed retry |
| Role-only authorisation | Cross-tenant or cross-patient access | Object relationships absent from policy | Tenant, ownership, state and delegation checks |
| Recovery bypasses passkey | Account taken after support call | Weak proofing and no credential revocation | Privileged recovery workflow with notification and audit |
| Logout leaves tokens usable | Access continues after sign-out | Revocation scope undefined | Specify session, refresh, access and grant invalidation |
| Service identity inherits user roles | Excessive automated access | No workload identity model | Dedicated identity, narrow scopes and ownership |

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Authorization server rejects callback | URI differs by slash, port, path or encoding | Register and compare the exact complete URI |
| Code exchange succeeds but nonce fails | Stale transaction, cached response or token substitution | Bind fresh nonce to one attempt and reject mismatches |
| API returns invalid_token for valid login | ID token used instead of access token | Use the API-audience access token and separate validation |
| All logins fail after key rotation | JWKS cache stale or unknown key handling broken | Refresh once with backoff, then fail closed and alert |
| Intermittent expiry failures | Clock skew or string-based date comparison | Use NumericDate rules and bounded clock synchronisation |
| Replayed token succeeds before expiry | Stateless bearer validation has no memory | Shorten lifetime and add revocation or sender-constrained controls |
| Partner sees unrelated appointments | Policy uses only role or client identifier | Enforce clinic, patient, purpose and delegation boundaries |
| Patient locked out after device loss | Recovery removes every authenticator | Require proofed recovery or another enrolled authenticator |
| Leaver retains delegated access | Grants and refresh tokens not revoked | Run a leaver checklist and verify residual token lifetime |
| Workforce and patient sessions merge | Subject namespaces treated as one identity | Use issuer plus subject and separate local account mapping |

## Design review checklist

- [ ] Human, partner, service and emergency identities have separate owners and credential models.
- [ ] Each OAuth client has exact registered redirect URIs, an appropriate grant type and protected storage.
- [ ] Authorization-code flows use S256 PKCE, fresh state and OIDC nonce where authentication is requested.
- [ ] ID tokens and access tokens have separate receiver-specific validation profiles and audiences.
- [ ] JWT validation checks allowed algorithm, signature, issuer, audience, lifetime and transaction binding.
- [ ] JWKS caching and rotation have bounded freshness, retry, alert and fail-closed behavior.
- [ ] Refresh-token rotation, reuse response, revocation and residual access windows are explicit.
- [ ] Resource policy evaluates subject, action, tenant, object, state and delegation close to the resource.
- [ ] Passkey ceremonies verify challenge, relying-party identifier, credential ownership and user-verification policy.
- [ ] Authenticator attestation and X.509 path validation are configured separately from JWT key trust.
- [ ] Joiner, mover, leaver, recovery and emergency-access procedures revoke old access.
- [ ] Logs and telemetry exclude tokens and unnecessary identity attributes while retaining decision evidence.
- [ ] Negative tests cover wrong issuer, audience, nonce, algorithm, key, lifetime, replay and object ownership.
- [ ] Rollback preserves authentication and does not restore disabled signature or authorisation checks.

## Key takeaways

- Authentication, delegated authorization, federated identity and resource authorization are separate decisions.
- Authorization code with PKCE, exact redirects, state and nonce binds different parts of a browser flow.
- A JWT signature proves origin only; the receiver must validate issuer, audience, time and transaction claims.
- ID tokens belong to relying parties; access tokens belong to resource servers.
- Passkeys provide phishing-resistant authentication evidence but do not replace object-level authorization.
- Key rotation, recovery, revocation and identity lifecycle operations are part of the security boundary.
