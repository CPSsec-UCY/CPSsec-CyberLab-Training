## The central idea

A one-time signature can only sign one message safely. If you use it twice, the secret leaks. Hash-based signatures solve this by building a tree of one-time keys:

- the leaves are one-time public keys,
- each internal node is a hash of its children,
- the root is the public key,
- a signature reveals one leaf key and the path to the root.

A single tree still has a limited number of signatures. SLH-DSA goes further: it uses a **hypertree**, a tree of trees, so one key pair can sign a huge number of messages.

## Why "stateless" is a feature

XMSS and LMS are efficient hash-based signatures, but the signer must remember which one-time keys have been used. Restore a backup, clone a VM, or sign from two machines, and you may reuse a one-time key — catastrophic. SLH-DSA is **stateless**: the signer derives message-specific keys from its secret seeds, the message and a randomizer. There is no counter to lose. <Cite id="fips205" locator="§9 (SLH-DSA key generation, signing and verification)" />

## The cost

SLH-DSA signatures are large — 7,856 bytes for the smallest "s" parameter set, up to 49,856 bytes for the fastest category-5 set. Keys are tiny (32–64 bytes for the public key). You trade bandwidth for extremely conservative assumptions. <Cite id="fips205" locator="§11" /> The construction descends from the SPHINCS+ submission and its CCS paper. <Cite id="sphincs-spec" locator="§3–6" /> <Cite id="sphincs2019" locator="pp. 2129–2146" />

<Callout variant="note" title="When this is the right tool">
Code signing roots, firmware verification, long-lived archives and conservative government profiles may happily accept a 30 KB signature to avoid relying on lattices. Interactive protocols with tight packet budgets usually will not.
</Callout>

## Where SLH-DSA fits

Consider a firmware root key that must verify updates for 20 years and is used only a few times per release. A 30 KB signature is irrelevant compared with the update image, and the conservative hash-only assumption is valuable. The same scheme would be a poor fit for a high-volume TLS handshake on a constrained device.

SLH-DSA is stateless: the signer can be restored from a backup, cloned, or run on two machines without reusing a one-time key. XMSS and LMS are more compact but require the signer to track state. That difference is operational, not cosmetic.

## Threat model and a firmware-root scenario

SLH-DSA targets EUF-CMA security. The attacker may obtain signatures on chosen firmware manifests and attempt to forge a signature for a new manifest under the public root. It may collect a very large number of signatures within the standard's stated signing limit, and it may use quantum algorithms. The defender must keep the secret seeds confidential, derive the message randomizer correctly, implement every domain-separated hash and release a signature that verifies against the pinned root.

A bootloader trusts a 32-byte SLH-DSA-128s public root for twenty years. An offline signing service produces a 7,856-byte signature for each release. The attacker can modify update files and signatures in transit but cannot read the signing service. A separate operational attacker may clone the service, restore an old backup or corrupt its random source. Statelessness removes the one-time-key counter, but it does not remove the long-lived private key or the need to protect randomness and faults.

Defender goals include conservative cryptographic assumptions, canonical verification and reliable large-object handling. The bootloader needs enough contiguous memory or a streaming verifier for the signature. The signing service needs protected seed storage and enough workspace for authentication paths. The release pipeline must authenticate the complete manifest and ensure that no layer truncates the signature to fit a legacy field.

Misconceptions often start with the phrase hash-only. It does not mean security follows from collision resistance alone. WOTS+ relies on second-preimage resistance of its chain function, FORS relies on hiding and few-time properties, and the full bound accounts for hash queries and signature queries. Nor does stateless mean randomisation is irrelevant: the message randomizer is part of the construction's security and fault analysis.

Bandwidth is a security parameter in practice. A 49,856-byte signature can exceed a protocol's record, flash partition or database column. Silently truncating it causes denial of service; accepting an alternative parser's malformed value can create inconsistency. Choose the parameter set with the verifier's memory and transport constraints in view. A small public key does not make the signature small, and fast signing does not imply fast verification.

Availability is distinct from forgery resistance. Hash-only implementations still suffer from faulty randomness, corrupted seed material and side channels. A signature that fails verification is a correctness event; a fault that reveals seed information is a security event. The service should verify before release, monitor verification failure rates and retain enough independent build information to diagnose an incompatible parameter set.

### Stateless does not mean state-free

Two signing workers are cloned from the same approved image. Neither needs a one-time-key counter, so both can restore an old snapshot without the XMSS reuse failure. They still depend on state that must be governed: the correct parameter-set identifier, the secret seed and public seed, root consistency, approved software, randomness health and a signing-volume policy. Statelessness removes one fragile invariant; it does not remove key custody.

| Operational state | Why it still matters | Failure if ignored |
| --- | --- | --- |
| Parameter-set identifier | Determines hash family, dimensions and signature encoding | Valid key material is interpreted under the wrong algorithm |
| SK seed and SK.prf seed | Generate message-specific WOTS+/FORS material and the randomizer | Broad copying turns one root compromise into a long-lived compromise |
| Public seed and root | Bind derived keys to the trusted public key | A worker may sign for a different trust anchor |
| Randomness source | Drives the message randomizer | Repeated or correlated randomizers weaken the construction's assumptions |
| Software and configuration version | Determine addresses, derivation and encoding | A rollback restores incompatible or vulnerable signing logic |
| Signing-volume policy | Keeps use within the standard's bound | A key exceeds the quantified signing limit |

FIPS 205 treats input destruction, public-key validation and side-channel or fault protection as implementation considerations beyond the abstract signature algorithm. <Cite id="fips205" locator="§3.2 (implementation considerations)" /> Protect seed import and memory, verify root regeneration where possession assurance is required, and stop a worker if internal verification fails. Cloning can improve availability, but every clone increases the number of places that hold the same crown-jewel seed. Access control and audit must reflect that concentration of risk.

## Three layers

<Figure caption="The SLH-DSA stack: a hypertree of XMSS trees, WOTS+ one-time keys, FORS for the message digest, and a public key that is just a root.">
  <SlhHypertree />
</Figure>

1. **WOTS+** signs a hash digest as a sequence of hash-chain values. It is a one-time signature: signing two different digests with the same key reveals enough chain values to forge.
2. **FORS** (Forest of Random Subsets) signs a digest using a few-time signature scheme: several small trees, one leaf revealed per tree.
3. **Hypertree** uses XMSS-style layers. Each layer signs the roots of the trees below it with WOTS+. The top root is the public key.

## The signing flow

1. Derive the randomizer with `SK.prf` from the signing input.
2. Hash the message with the randomizer to obtain a digest.
3. Use FORS to sign the digest.
4. Use a WOTS+ key in the bottom hypertree layer to sign the FORS public key.
5. Include the authentication path up the hypertree, signing each tree root with the layer above.

Verification reverses the process and checks hashes up to the root. <Cite id="fips205" locator="§7" />

## Parameters

The standard defines 12 parameter sets: SHA-2 and SHAKE variants, each at categories 1, 3 and 5, in "small" (s) and "fast" (f) flavours. The additional-signature track and the SPHINCS+ design history are documented in the NIST status report. <Cite id="nist-ir8545" locator="§4" />

| SLH-DSA-128s | 16 | 63 | 7 | 32 B | 7,856 B |
| SLH-DSA-128f | 16 | 66 | 22 | 32 B | 17,088 B |

## Why WOTS+ keys cannot be reused

A WOTS+ signature reveals one hash-chain value per digit. A second signature on a different digest may reveal a later chain value, letting an attacker compute the first signature's remaining chain and forge. This is not a theoretical nicety; stateful hash-based deployments have failed precisely here.

XMSS and LMS are standardised and efficient, but the signer must guarantee that every one-time key is used at most once. Backups, failover and disaster recovery must all preserve that invariant. <Cite id="rfc8391" locator="§3–4" />

## WOTS+ by example

A WOTS+ key is a set of hash chains. To sign a base-$w$ digit, the signer reveals the chain value at that digit's position. The verifier applies the remaining hash steps to recover the chain endpoint. Revealing two different values for the same chain would let an attacker compute later values and forge.

FORS signs a digest with a small forest of trees: one leaf is revealed per tree, and the authentication path lets the verifier recompute each root. The roots are then signed by the bottom XMSS layer.

## Signing flow

1. Derive the randomizer with `SK.prf` from the signing input.
2. Hash the message and randomizer into a digest.
3. Produce a FORS signature over the digest.
4. Sign the FORS public key with a WOTS+ key.
5. Include the authentication path up the hypertree, signing each tree root with the layer above.

Verification reverses the process and checks the final root against the public key. <Cite id="fips205" locator="§7–9" />

## Hash chains and authentication paths by hand

WOTS+ uses base-$w$ digits of a digest. For a chain of length $w-1$, signing digit $d_i$ reveals the value after $d_i$ hashes; verification applies the remaining $w-1-d_i$ hashes and compares the endpoint. Address and domain separation are prepended so that the same secret value used at two positions does not produce the same chain. For every FIPS 205 parameter set, $\lg w=4$ and $w=16$. With $n=16$ bytes, $\mathrm{len}_1=\lceil128/4\rceil=32$. The checksum adds $\mathrm{len}_2=3$ chains, giving $\mathrm{len}=35$ chains in total. Each chain can require up to 15 hash calls. <Cite id="fips205" locator="§5 (WOTS+ parameters, equations 5.1–5.4)" />

FORS splits a digest into $k$ chunks, each selecting one leaf in a tree of height $a$. A signature contains the selected secret value and its sibling path in each tree. The verifier recomputes that tree's root, hashes the roots into the FORS public key, and then follows the hypertree authentication path. Selecting one leaf per tree limits what each signature reveals, but many signatures gradually reveal more leaves; the few-time security bound accounts for this.

### Account for the signature, byte by byte

The large signature is not an opaque blob. Its size follows from four contributions: the randomizer, the FORS secret values and sibling paths, one WOTS+ signature per hypertree layer, and the hypertree authentication siblings. For a parameter set with $n$ bytes, $k$ FORS trees of height $a$, $d$ layers and total height $h$,

$$
|\mathrm{SIG}| = n + k(a+1)n + d(2n+3)n + hn.
$$

The WOTS+ factor uses $\mathrm{len}=2n+3$ because every FIPS 205 set has $\lg w=4$. The formula explains the measured sizes in Table 2 rather than merely memorising them. <Cite id="fips205" locator="§5 (WOTS+), §7 (hypertree), §8 (FORS), and Table 2 (parameter sets)" />

| Set | Randomizer | FORS values and paths | WOTS+ signatures | Hypertree siblings | Total |
| --- | ---: | ---: | ---: | ---: | ---: |
| 128s | 16 B | 14 × 13 × 16 = 2,912 B | 7 × 35 × 16 = 3,920 B | 63 × 16 = 1,008 B | 7,856 B |
| 128f | 16 B | 33 × 7 × 16 = 3,696 B | 22 × 35 × 16 = 12,320 B | 66 × 16 = 1,056 B | 17,088 B |
| 256s | 32 B | 22 × 15 × 32 = 10,560 B | 8 × 67 × 32 = 17,152 B | 64 × 32 = 2,048 B | 29,792 B |

The “fast” set does not make every component smaller. It uses shorter FORS trees, which reduces each path, but increases the number of FORS trees. It also uses many more hypertree layers, each requiring another WOTS+ signature. Shorter XMSS trees reduce per-layer chain and path work; the larger layer count still costs bandwidth. The “small” set does the opposite. This is why changing from 128f to 128s saves signature space but increases signing work, not because the hash function itself becomes slower.

The same arithmetic supports memory budgeting. A signer can stream or discard completed FORS paths, but it must retain the roots needed to construct the FORS public value and enough workspace for each WOTS+ chain and hypertree sibling. A verifier can process one layer at a time only if it preserves the root needed by the next layer. Fixed-size buffers derived from the parameter set prevent a malformed signature from driving unbounded allocation.

The hypertree parameters show the size/work tradeoff. The 128s set has height 63 and 7 layers, so each tree has height 9. The 128f set has height 66 and 22 layers, so each tree has height 3. Shorter trees reduce WOTS+ and authentication-path work per layer, but there are more layers to sign. The total height still governs the number of available leaves; it is not chosen independently of the signing bound.

For SHAKE-128s, the public key contains two 16-byte values: the independently generated public seed and the root. A verifier first parses the signature's randomizer and message-dependent values, then recomputes the digest and FORS roots using the public seed. It does not need the private key, but it must reproduce the address construction exactly. A one-position error in layer, tree or leaf indexing produces a different hash and a failed signature.

<Lens level={3} title="Hash assumptions, few-time security and tight bounds">

## WOTS+ as a one-time signature

WOTS+ signs a base-$w$ representation of an $n$-byte digest. Each digit selects a position along a hash chain. The public key is the endpoint of every chain; a signature reveals intermediate values. Security reduces to the second-preimage resistance of the chain function, with careful domain separation through addresses. <Cite id="wots2013" locator="pp. 173–188" />

## FORS as a few-time signature

FORS signs $k$ chunks of the message digest. For each chunk, the signer reveals one secret leaf in a tree of height $a$; the verifier recomputes the root from the leaf and its authentication path. An attacker who obtains many FORS signatures on related digests can gradually learn more leaves, which is why the parameter sets are chosen for a bounded number of signatures. <Cite id="fips205" locator="§8" />

## Hypertree correctness

The hypertree is a sequence of XMSS trees. A signature at the bottom layer includes a WOTS+ signature on the FORS public key. Each higher layer signs the root of the tree below. Verification recomputes each root and finally compares with the public key.

<Callout variant="lab" title="Security bound sketch">
The forgery probability is bounded by the probability of breaking the hash functions plus the probability of a FORS/WOTS+ one-time key collision across the allowed number of signatures. The standard's analysis is parameterised by the number of hash queries and the number of signatures; the 2024 standard claims EUF-CMA security for up to $2^{64}$ signatures per key pair under its assumptions. <Cite id="fips205" locator="§11" />
</Callout>

## Quantum margins

Hash-based signatures are attractive post-quantum because the assumptions are minimal. Grover still applies:

- preimage resistance drops from $2^n$ to $2^{n/2}$,
- collision resistance drops to about $2^{n/3}$ with quantum collision-finding.

The parameter sets choose $n = 16, 24, 32$ bytes to meet categories 1, 3 and 5 with these reductions in mind. There is no algebraic structure to attack, but there is also no free lunch: the signature size grows to pay for the conservative proof.

## What the proof does not cover

It does not cover implementation faults, state reuse (for stateful cousins), randomness failures, or side-channel leakage. Those are engineering problems, not hash-function problems.


## Security from hashes alone

WOTS+ reduces to second-preimage resistance of the chain function with domain-separated addresses. FORS is a few-time signature; the parameter sets bound how many signatures an attacker can collect before the probability of a useful collision becomes significant. The hypertree extends a small number of one-time keys into many signatures.

The security bound accounts for hash queries, signature queries and the probability of a FORS or WOTS+ collision. FIPS 205 claims EUF-CMA security up to $2^{64}$ signatures for the standard parameter sets. <Cite id="fips205" locator="§11" />

## Quantum margins

Grover halves preimage security and quantum collision search reduces collision security further. The parameter sets use $n=16,24,32$ bytes for categories 1, 3 and 5. The conservative assumption is the selling point, but the signature size pays for it.

<Callout variant="lab" title="Few-time is not many-time">
FORS and WOTS+ are not general-purpose many-time signatures. The hypertree and parameter choices keep the number of revealed one-time keys within the security bound. Reusing a WOTS+ key across two different digests is a break.
</Callout>

## Security bounds and verification invariants

### The checksum closes a shortcut, not every attack

For a 128-bit digest encoded in base 16, there are 32 message digits. Suppose all are zero. The WOTS+ checksum is

$$
\sum_{i=1}^{32}(w-1-d_i)=32\times15=480.
$$

In base 16, 480 is `1E0`, so the three checksum digits are 1, 14 and 0. A signature reveals the starting chain values for 32 zero message digits and those three checksum digits. Verification advances each value by the remaining number of hashes and recomputes the WOTS+ public value. <Cite id="fips205" locator="§5 (WOTS+ checksum and chain functions)" />

Now change one message digit from 0 to 1 while leaving the signature unchanged. The checksum falls from 480 to 465, which is `1D1`: the checksum digits become 1, 13 and 1. The old checksum-chain values no longer match the new digest's required endpoints, so the forgery fails even before the message-chain mismatch is considered. An attacker cannot independently shorten arbitrary chains and still satisfy the checksum. This is the concrete role of the three checksum chains.

The FORS bound is different. Within one reused FORS tree, revealing selected leaves creates a birthday-style subset-collision problem. For a deliberately simplified model with $Q\ll2^{a/2}$ selections among $2^a$ leaves, the chance of any repeated leaf across $k$ trees is approximately

$$
1-\exp\left(-\frac{kQ(Q-1)}{2^{a+1}}\right).
$$

With $a=12$, $k=14$ and $Q=10$, that expression is about 14.3%. This is intuition for why “few-time” matters, not the FIPS 205 forgery bound: SLH-DSA derives message-specific FORS keys, and the full analysis also includes hash queries, hypertree selection and target-subset effects. <Cite id="fips205" locator="§8 (FORS) and §11 (security bounds and parameter sets)" />

WOTS+ has another failure pattern. Its second-preimage argument assumes that an attacker cannot find a different digest whose base-$w$ digits permit a compatible signature from the revealed chain values. Address separation keeps chains at different layers, trees, key pairs and positions in distinct hash domains. Omitting an address component collapses those domains and invalidates the reduction even if every individual hash call is correct. <Cite id="wots2013" locator="pp. 173–188" />


WOTS+ has a different failure pattern. Its base-$w$ digit sequences are designed so that a second-preimage attack must find a new digest with a compatible signature. The checksum chains prevent an attacker from simply choosing arbitrary digits that keep the signature shorter. Address separation ensures that chains at different positions, layers and trees are independent hash domains. Omitting an address component collapses those domains and invalidates the argument. <Cite id="wots2013" locator="pp. 173–188" />

Hypertree correctness follows by induction. The bottom layer's XMSS signature authenticates the FORS public key under a leaf of its tree. The next layer authenticates that tree's root, and so on. At layer $\ell$, the verifier recomputes the signed root using the supplied WOTS+ signature and authentication path, then uses it as the target root for layer $\ell-1$. After the top layer, equality with the public root establishes that the same sequence of one-time keys authenticated the original digest.

Statelessness changes key selection, not this verification chain. The signer derives a message-specific seed and chooses one-time keys pseudorandomly within the tree. Reusing the exact same message with the same randomizer can repeat a signature without revealing two different digest signatures. For different messages, the security argument bounds accidental or adversarial key-selection collisions over the allowed signing quantity; pseudorandom derivation is not an unconditional uniqueness guarantee. A broken randomizer in randomized mode can increase correlation and is therefore treated as a security failure, not a performance inconvenience.

The assumptions are deliberately narrow. The approved hash functions must provide the required preimage, second-preimage and pseudorandomness properties. Address separation, key derivation and tree traversal must match the standard. Generic quantum search reduces preimage security, while quantum collision finding has a different cost from classical birthday search; parameter sizes are selected with those reductions in mind. Hash-based does not mean that implementation faults, seed disclosure or side channels disappear. <Cite id="fips205" locator="§11" />

Verification must reject malformed structures before doing expensive work where possible. Check the exact signature length, randomizer length, FORS indices, WOTS+ digit ranges and hypertree path lengths. Recompute every root and compare the final root without early acceptance of an intermediate match. Do not normalise an out-of-range index modulo the tree size. Treat a signature for one parameter set as invalid under another, even if both use the same public-key length.

Output privacy is usually less central for signatures than for MPC, but metadata still matters. Signing time can reveal the parameter set or workload, and a repeated signature can reveal repeated inputs. Bind release identifiers and timestamps through the message being signed. The signature itself is public by design; the secret seeds, chain intermediates that have not been selected, and signing workspace remain confidential.
</Lens>

<Lens level={4} title="Hash calls, memory and operational failure modes">

## What dominates the cost

SLH-DSA is a hash-call engine. Signing performs thousands to millions of hash evaluations depending on the parameter set; verification is much cheaper but still hash-heavy. There is no NTT and no modular arithmetic in the hot path.

- **SHA-2 variants** benefit from SHA-NI and mature hardware support.
- **SHAKE variants** use Keccak, which is fast in software and increasingly accelerated. <Cite id="fips202" locator="§3" />
- **Parallelism** is possible across independent FORS trees and hypertree nodes, but the dependency chain limits some speed-ups.

## Memory and code size

The signer needs to hold authentication paths and intermediate nodes. The "s" parameter sets minimise signature size but do more work; the "f" sets reduce work by using more hypertree layers. On constrained devices, code size and stack usage can matter more than raw speed.

## Faults and randomness

- **Randomness:** FIPS 205 defines randomized and deterministic signing interfaces. Randomized signing supplies fresh approved random input to derive the message randomizer; deterministic signing uses the prescribed zero input and can repeat a signature for the same message. Do not describe a failed or reused RNG in randomized mode as harmless, and do not mistake deterministic repetition for fresh entropy.
- **Fault injection:** a corrupted hash computation can produce an invalid or exploitable signature. Redundant computation and verify-before-release are standard defences. <Cite id="boneh1997" locator="pp. 37–51" />
- **Side channels:** hash functions are usually easier to make constant-time than lattice arithmetic, but address computation and secret-dependent branching still matter.

### Compare failures by what they break

A fault during address generation, a broken randomizer and a truncated transport record can all produce “signature failed.” Their security consequences and tests are not the same.

| Failure | Local symptom | Security consequence | Discriminating test |
| --- | --- | --- | --- |
| Address field is stale or swapped | Every affected path hashes to the wrong node | Usually invalid output; cross-domain reuse could undermine separation if systematic | Fixed address vectors and layer-by-layer root comparison |
| Randomizer repeats | Same message can produce the same signature; different messages may become correlated | Randomisation assumptions weaken | RNG health tests, repeated-randomizer fault injection and entropy review |
| Seed workspace is exposed | Logs, crash dump or side trace contain seed-derived values | Long-term signing key compromise | Memory wiping, log inspection, taint and power evaluation |
| FORS index is malformed | Out-of-range leaf or path reaches hashing | Parser ambiguity or resource exhaustion | Reject before allocation; mutate every index region |
| Faulted chain or path is released | Internal verification fails or output is unchecked | Invalid signature or fault-dependent leakage | Inject faults and require abort or normal rejection |
| Transport truncates a path | Length or partition check fails | Availability loss; custom parsers may accept ambiguous bytes | Exact-size, fragmented and region-truncation tests |

FIPS 205 explicitly identifies side-channel and fault protection as implementation considerations and specifies address fields that separate layer, tree, type, key pair and position. <Cite id="fips205" locator="§3.2 (side-channel and fault attacks) and §4.2 (addresses)" /> Hash-only security does not make these concerns disappear. Signing time can depend on WOTS+ digits and FORS indices; a secret-indexed table can leak through the cache; a fault that skips a hash or copies the wrong address can invalidate the authentication path.

For the cloned-worker scenario, inject a repeated randomizer in randomized mode while keeping the seed intact and observe both outputs. Repeating a signature for the identical message is possible by design when the randomizer repeats, but the service should treat unexpected repetition as a security-relevant fault. Then corrupt one hypertree layer's address state and verify that internal verification catches it before release. Finally, truncate one WOTS+ value and require deterministic rejection without an out-of-bounds read. These tests target distinct failure classes rather than treating every error as generic “RNG trouble.”

## Deployment patterns

- **Firmware and code signing:** verify once, at boot or install time; large signatures are acceptable.
- **Long-lived roots:** small public keys and conservative assumptions simplify trust-anchor management.
- **Protocols:** measure the handshake and record sizes; a 30 KB signature may fragment badly.
- **Test vectors and interoperability:** use the standard's vectors and an independent implementation. <Cite id="liboqs" locator="Reference implementations and KEM/signature test harness (SLH-DSA known-answer tests)" />

<Callout variant="note" title="Hybrid signatures">
In a hybrid signature scheme, both a classical and a PQC signature must verify. This protects against a break in either component, but doubles the signature size and verification cost. Decide whether the protocol can afford it.
</Callout>

## Implementation patterns and operations

Structure the implementation around a hash-address helper rather than scattered index arithmetic. One function should encode the layer, tree, type, keypair and chain or leaf position according to the parameter set. Unit-test that helper with fixed addresses before testing the full signature. Most interoperability failures in hash-based signatures come from a correctly implemented hash receiving the wrong domain or position bytes.

Use fixed-size workspaces for FORS trees, WOTS+ chains and hypertree authentication paths. The small parameter sets are attractive for constrained devices partly because their intermediate values are short, not only because signatures are smaller. Avoid recursion for tree traversal when stack depth is uncertain; use explicit index arrays and bounded loops. Streaming verification can process a large signature in chunks, but it must authenticate the total length and retain the computed roots needed for the next layer.

Parallelise only independent work. Different FORS trees can be evaluated concurrently, and WOTS+ chains for distinct digits are independent once addresses are fixed. Hypertree layers are sequential because each signs the root needed by the layer above. Measure hash throughput, address-generation overhead and memory traffic; adding threads to a dependency chain can reduce performance.

Protect all private-key components and the randomizer workflow. FIPS 205 key generation produces three fresh $n$-byte values: `SK.seed`, `SK.prf` and `PK.seed`. The public root is computed from `SK.seed` and `PK.seed`; `SK.prf` is used to derive the message randomizer. The serialized private key also contains copies of the public seed and root, but the public seed is not derived from the secret seed. Keep every private-key component out of process dumps and logs, and verify root regeneration when private-key possession assurance is required. <Cite id="fips205" locator="§3.1 (randomness, key checks) and §9 (SLH-DSA algorithms)" /> A cloned stateless signer is not automatically a key-compromise event, but an uncontrolled clone still doubles exposure of the same long-lived private key.

Use approved randomness and the standard's signing interface. Verify the exact serialized signature before releasing it when faults are in scope. Recompute the final root or invoke an independent verifier in the signing pipeline; this catches corrupted paths and address state. Redundancy should not reuse the same faulty address helper without scrutiny. Monitor internal verification failures and stop the service if they rise unexpectedly.

Transport deserves its own test plan. Encode signatures with a length field large enough for the selected set. Test update bundles near the largest signature size, fragmented network records, flash-wear limits and database column sizes. The bootloader should reject a truncated signature before allocating unbounded memory. If a protocol uses a hybrid signature, both components must be present, canonical and independently verified according to the protocol rule.

Run standard known-answer vectors for all selected sets, then differential-test with an independent implementation. Fuzz the verifier's FORS indices, chain values and path lengths. Mutate every signature region and require rejection unless the mutation produces a different valid signature, which is not expected for these serialized structures. Benchmark signing and verification separately on the target CPU, including cold-cache and constrained-memory cases.

During operation, rotate compromised seeds through the trust-anchor process and retain the old public root only for a defined legacy-verification window. Statelessness simplifies failover, but it does not make snapshot rollback harmless: a restored signer must still have the correct software, random source and seed. Keep the parameter-set identifier with every artifact so an engineer can distinguish a large but valid signature from a malformed one.
</Lens>

## Common failure modes

| Failure | Cause | Impact | Prevention |
| --- | --- | --- | --- |
| Signature is truncated | Legacy field or partition assumes classical sizes | Verification failure | Size the full artifact and reject truncation |
| Wrong parameter set is used | Small and fast sets share a family name | Different signature length and hash behaviour | Store and validate the explicit set identifier |
| Address bytes are misordered | Layer, tree or type fields are swapped | Every path hashes to the wrong node | Centralise and test address construction |
| FORS index is normalised | Parser reduces an out-of-range value modulo tree size | Malformed input may reach the wrong leaf | Reject before hashing |
| Randomizer source is broken | Randomized mode reuses or loses random input | Randomisation assumptions fail | Approved RBG and fresh input; label deterministic mode explicitly |
| Secret seed is copied broadly | Cloned workers share unprotected storage | Long-term root compromise | Protected key import and isolated workers |
| Faulted path is released | No internal verification | Invalid signature or information leak | Verify exact serialized output |
| Hybrid rule is misapplied | Only one signature is checked | Weaker than intended combined security | Define and test both-required semantics |

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Signature exceeds a fixed metadata field | Parameter set or length calculation is wrong | Measure exact bytes and redesign storage |
| Every FORS path fails | Public seed, digest or address construction differs | Compare fixed addresses and digest bytes |
| WOTS verifies in one library but not another | Chain order or digit/checksum encoding differs | Check base-$w$ encoding and standard vectors |
| Only top hypertree layer fails | Root ordering or layer count is wrong | Verify each intermediate root independently |
| Signing is unexpectedly slow | Small set chosen without workload analysis | Compare hash counts and target hardware limits |
| Internal verification intermittently fails | Randomness, memory corruption or address state fault | Stop release and isolate seed, RNG and workspace |

## Design review checklist

- [ ] The parameter set, hash family and security category are explicit in every artifact.
- [ ] Public-key, signature and metadata sizes fit the verifier's measured budget.
- [ ] FORS indices, chain values and path lengths are checked before hashing.
- [ ] Address construction is centralised and covered by fixed test vectors.
- [ ] WOTS+ digit and checksum encoding matches the selected set.
- [ ] Hypertree layer count, tree height and root order are verified independently.
- [ ] Secret seeds and randomizer material are protected across cloning and rollback.
- [ ] Internal verification and fault injection run before signature release.
- [ ] Transport and flash paths preserve every signature byte.
- [ ] Known-answer, differential and region-mutation tests pass on target hardware.
- [ ] Signing, verification, peak RAM and boot-time margins are benchmarked.

## Key takeaways

- SLH-DSA builds signatures from hash functions with minimal algebraic assumptions.
- WOTS+ and FORS are few-time/one-time primitives; the hypertree makes the scheme stateless and scalable.
- Signatures are large because they contain chain values and authentication paths.
- The "s" and "f" parameter sets trade size against signing work.
- Hash-only assumptions are conservative, but implementation and operational risks remain.
