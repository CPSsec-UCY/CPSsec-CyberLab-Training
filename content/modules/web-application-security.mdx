## Start with the request, not the vulnerability name

A web application receives bytes and turns them into decisions. A route, query parameter, JSON field, cookie, header or uploaded filename may influence a database query, an HTML page, a server-side network request or a file read. The central security question is not simply whether an input looks dangerous. It is **where did this value come from, what meaning has the application assigned to it, and what authority will the next component give it?**

HTTP defines method and response semantics, but it does not make application data trustworthy. GET is defined as safe and idempotent: a conforming client uses it to retrieve a representation rather than request a state change. That property does not make a GET endpoint public, and it does not prevent a poorly designed endpoint from causing side effects. HEAD and OPTIONS also have specific semantics. <Cite id="rfc9110" locator="§9.1–9.3" /> Application security begins by preserving those meanings while treating every supplied value as untrusted.

OWASP's Top 10 is useful as a risk-family map, especially for broken access control, injection and authentication failures. It is not a complete inventory of every weakness, nor does a category label explain why a particular request is dangerous. The CWE Top 25 adds a weakness vocabulary for engineering work and trend discussions. <Cite id="owasp-top-10" locator="Risk categories and guidance" /> <Cite id="cwe-top-25" locator="Ranked software weakness list" /> Use both to organise review, then return to the concrete data flow.

## Draw the boundary before drawing the fix

A trust boundary is a point where data or authority changes meaning. The browser is not a trusted client: a user can edit a request, bypass JavaScript validation or write a non-browser client. The edge is not a trusted validator: a gateway may normalise a path differently from the application. A background job is not automatically trusted: it can process an object that an untrusted user created. A database value is not automatically safe: stored XSS begins when untrusted content is persisted and later rendered.

For a multi-tenant reporting service, a practical model contains at least six zones:

- the user's browser and any injected content inside its origin;
- the CDN, load balancer and application framework;
- the application's authentication and authorisation layer;
- business services and asynchronous workers;
- databases, object stores and internal services;
- outbound HTTP clients and external identity providers.

Crossing a boundary requires an explicit decision. The application should derive the tenant from a verified server-side context, check permission on the object, and then construct a query. It should not copy a tenant identifier from the request into a privileged operation merely because it arrived on an HTTPS connection. TLS protects transport; it does not certify the user's intentions.

## Authentication, validation and authorisation answer different questions

Authentication asks who is making a request. Authorisation asks whether that principal may perform this action on this resource under current conditions. Validation asks whether a value fits the application's accepted representation and business constraints. These checks overlap in implementation but fail differently. A perfectly authenticated administrator can still request an object outside the intended scope. A valid date can be used in an unsafe SQL string. A syntactically valid URL can point at an internal service.

A denial must be explicit and server-side. Hiding a button is a usability feature, not an access control. Checking a role name without considering tenant or object ownership can create a cross-tenant flaw. Caching an earlier successful authorisation decision without a version or expiry can preserve access after permissions change. Prefer a default-deny policy with a small, reviewable set of allowed actions.

Applications that accept federated sign-in callbacks add another boundary. Exact redirect URI validation, transaction binding and authorization-code protection matter because an attacker may redirect a browser or capture a code. OAuth's security best-current-practice guidance treats redirect URI validation and code interception as protocol threats rather than ordinary form-validation problems. <Cite id="rfc9700" locator="§2–4, redirect URI and authorization-code protections" /> Keep that protocol work separate from the application's resource-level policy: a valid federated identity still needs permissions here.

## Threat model one concrete journey

Consider a report search page used by support teams. A user supplies a tenant filter, searches report titles, previews an uploaded document and downloads an attachment. A privileged worker renders titles back into a dashboard. A preview service fetches a user-supplied remote document. Each step creates a different adversary opportunity.

An external attacker can submit unusual encodings, object identifiers and URLs. A malicious tenant can store content that a support analyst later views. An insider with limited privileges can alter request parameters to reach another tenant's data. A compromised worker can abuse its network position. The defender wants to preserve confidentiality, integrity and availability without turning every unusual but legitimate document into an outage.

The most useful review follows one value end to end. Record where it enters, every transformation, every stored copy, every sink and every response. This exposes fixes that merely move the problem: trimming a value before validation but using the original later, encoding once and then decoding again, or normalising a path in one component while a worker opens the unnormalised form.

## A boundary-first review record

For each important route, write a compact record: caller, credential, input sources, parsed representation, subject, tenant, object, action, policy decision, sinks, outputs and audit event. Mark every point where a value is decoded, normalised, stored or re-used. The record makes gaps visible. If no one can say which subject and object the authoriser saw, the decision is not reviewable.

Do not turn this into documentation theatre. The record should drive tests. A negative test for object ownership, a query-binding test and an outbound-destination test correspond directly to rows in the review. When a design changes, update the flow and the tests together.

## Model the authority changes between components

HTTPS usually authenticates a transport hop, not the meaning of every value forwarded through it. A gateway that strips `/api`, a cache that omits a tenant header from its key and a worker that reparses an archived URL can each preserve valid bytes while changing the authority attached to them. These are boundary failures even when no parser throws an error.

Consider a report link that passes through a CDN, a reverse proxy, the application and an asynchronous renderer. A useful review records what each component believes it is handling:

| Boundary | Convenient assumption | Concrete failure | Required invariant and test |
| --- | --- | --- | --- |
| CDN to application | A private-looking route is never cached | A response authorised for one tenant is reused for another | Cache keys must represent every authorisation-relevant input; test two tenants through the deployed cache |
| Proxy to router | Both components decode the path identically | The proxy resolves `%252F` once while the application decodes twice | Define the decoding contract; send encoded and doubly encoded paths through the whole chain |
| API to worker | The API already made the security decision | A queued job runs after permission or object state changes | Re-evaluate authority at execution or carry a bounded, revocable grant |
| Worker to storage | A stored filename still names the same object | A symlink or replacement changes containment between validation and open | Resolve and open safely in one component; test replacement and symlink cases |

The important question is not which component is “trusted”. It is which invariant survives the hand-off. A control demonstrated only inside the application is not proven for a request that reached the sink through a cache, proxy or queue. Deployment-level tests should assert the final observable effect: the correct tenant's representation, the intended object and no unauthorised side effect.

## Injection is a grammar problem

SQL injection occurs when untrusted data becomes part of a command's grammar. A string may look like a single value to the application but contain tokens that change the database's parse. The fix is not to remove a few suspicious characters. It is to keep values separate from syntax by using parameterised queries or prepared statements through a maintained driver.

Dynamic table names, sort directions and JSON paths cannot be bound as ordinary values in many databases. They need a closed mapping from an application token to a reviewed identifier. Never place a user-provided identifier directly into SQL, even if another value is parameterised. ORMs reduce boilerplate but raw-query escape hatches, unsafe query-builder methods and hand-written fragments can reintroduce the flaw.

## Cross-site scripting is an output-context problem

XSS occurs when untrusted content reaches a browser context where it can be interpreted as executable markup or script. Stored XSS persists the content; reflected XSS places request data into a response; DOM-based XSS performs the unsafe operation in client-side code. The same stored value can be safe in a plain-text response and dangerous when inserted into HTML, an attribute, a URL or JavaScript.

HTML text encoding is the baseline for ordinary text. Attribute, URL, CSS and JavaScript contexts have different grammars, so one generic escaping function is not a universal solution. Prefer framework escaping and safe DOM APIs. Avoid constructing HTML from strings. If the product requires rich HTML, use a maintained allowlist-based sanitiser and define allowed elements, attributes and URL schemes. Content Security Policy can reduce impact but does not repair an injection sink.

The browser's origin matters. Script executing in the application's origin may read data available to that page, act with the user's session and call same-origin endpoints. HttpOnly cookies can limit direct token reading but do not stop actions made with the cookie. Secure cookie attributes and SameSite policies are useful session controls; they are not alternatives to output encoding.

## Server-side request forgery changes who can reach a destination

SSRF occurs when an attacker influences a server-side network request. The server may reach loopback, private networks, link-local metadata endpoints or internal services unavailable to the browser. URL filters that inspect only a prefix are fragile. User information, alternate host representations, unexpected ports, redirects, DNS changes and URL-parser differences can all matter.

Start with the strongest design: accept an identifier for a known resource rather than an arbitrary URL. If arbitrary destinations are a genuine requirement, parse the URL with a well-defined library, canonicalise it, and allowlist the exact scheme, host and port. Reject credentials and ambiguous forms. Validate the resolved destination against the egress policy, disable redirects or revalidate every hop, and restrict the worker's network access. DNS rebinding requires connecting to a validated address or using an egress control that does not rely on one early lookup.

## Path traversal is a containment problem

Path traversal occurs when untrusted path data escapes the directory or object namespace the application intended to expose. Concatenating a base directory and a filename is not containment proof. Parent-directory segments, encoded separators, platform-specific roots, symlinks and races between a check and an open can all break the assumption.

Prefer opaque object identifiers mapped to server-side paths. Decode input once according to the interface contract, canonicalise using platform-aware routines, resolve it beneath a fixed root and verify containment on the resulting path. Reject absolute paths and unexpected separators. Where symlinks or concurrent replacement are possible, use directory-relative, no-follow filesystem operations or a storage layer with atomic semantics. Finally, authorise the resolved object rather than only the supplied identifier.

## Read an exploit as a chain of transitions

A payload is only one link. The useful analysis names the transition it forces and the invariant that must hold. The same report title can be inert in a database row, become executable in an analyst's dashboard and become a misleading link in an email. Defences fail when they protect a different link from the one the attacker uses.

| Family | Transition the attacker seeks | Defence that can look sufficient | Stronger verification |
| --- | --- | --- | --- |
| SQL injection | Data becomes query grammar | Reject a list of SQL keywords or quotes | Assert the final query structure and parameter list against the real driver |
| Stored XSS | Persisted data becomes browser markup or script | Sanitise when the title is first stored | Render in each output context and inspect the resulting DOM; re-check after transformations |
| SSRF | An attacker-chosen name becomes a server-side socket | Match the URL text against a prefix allowlist | Instrument the transport and prove rejected resolved addresses and redirects never connect |
| Path traversal | A relative name becomes an object outside the approved namespace | Reject `..` before canonicalisation | Test the resolved object, symlinks, platform roots and replacement races at the open boundary |

Second-order cases make this distinction sharper. An attacker may store `&lt;img src=x onerror=...&gt;` in a report title, relying on a later component to decode entities before rendering. A downloader may pass a safe-looking URL that redirects to a loopback address. A filename may contain no parent segment but resolve through a symlink. In each case the dangerous representation is created downstream, so an input-only test can pass while the sink remains vulnerable.

A practical exploit hypothesis therefore states the entry point, transformations, privilege gained and evidence expected. For example: “A tenant stores an HTML entity-encoded title; the dashboard decodes it and inserts the result into HTML; script executes in the support origin.” That claim suggests tests at storage, transformation and rendering. A generic assertion that “XSS was tested” does not identify which transition was actually blocked.

## Canonicalise once and preserve provenance

A value should have a documented internal representation. If a query parameter is decoded by the framework, downstream code should not decode it again unless the contract explicitly requires that transformation. If a filename is normalised, use the normalised value for containment, storage and authorisation. Carrying both a raw and an interpreted form invites a mismatch between the component that validates and the component that acts.

Keep provenance alongside sensitive values. A filename from an upload, a URL from a tenant configuration and a path from an internal worker may share a string type but have different trust levels. Types can help, but comments and naming are not enforcement. Construct separate request objects or commands with narrow fields rather than passing an entire untrusted dictionary into a privileged service.

Business validation remains necessary. Length limits, character sets, allowed file types, numeric ranges and object-state transitions reduce attack surface and protect availability. They supplement sink controls. A maximum length on a URL does not make the destination trustworthy; rejecting angle brackets in a report title does not justify skipping HTML output encoding.

## Defence placement by sink

For SQL, keep the query structure in code and values in bind parameters. Review raw SQL, dynamic ordering and tenant filters. For HTML, use context-aware encoding or safe rendering APIs at the final output point. For outbound requests, enforce destination policy on the parsed and resolved target, then revalidate redirects. For files, enforce canonical containment and object authorisation before opening the resolved resource.

A web application firewall can block known attack patterns, enforce coarse request limits and add visibility. It sees a different parser from the application and cannot reliably understand object-level business rules. Treat it as a compensating layer. Logging a suspicious payload after a vulnerable query executes is detection, not prevention.

## Authorise the resolved object, then keep the decision fresh

Centralise policy at the service or data-access boundary, not in scattered controller snippets. Inputs should include a verified subject, the action, the resolved object, tenant context and relevant attributes such as state or risk. Return a default denial when policy is unavailable. Avoid trusting a client-supplied role, tenant or ownership flag.

Cache policy decisions only with explicit keys and bounded lifetimes. Include the policy version, subject, object, action and relevant attributes. Invalidate on entitlement, ownership or object-state changes. A cache key that omits tenant can leak data; a cache entry that survives revocation can preserve stale authority. For high-impact operations, re-evaluate close to execution.

Prevent state changes through safe methods. Use the appropriate non-safe method and anti-CSRF protection where browser ambient credentials are involved. SameSite cookies reduce some cross-site cases but are not a complete design. Sensitive operations may require recent authentication or step-up verification, with the freshness requirement recorded in policy.

## Test the sink, not only the validator

Unit tests should prove that dangerous-looking data stays data. For SQL, assert the generated query structure and parameter list, then use an integration test against the real driver. For HTML, render representative values and inspect the DOM rather than searching only for substrings. For SSRF, instrument the connection layer and assert that rejected destinations never open a socket. For files, test canonical containment with encoded separators, absolute paths and symlinks where supported.

Build a negative matrix for each route. Change one condition at a time: another tenant's object identifier, missing role, expired session, malformed encoding, unexpected method, stale policy version or a redirect to a forbidden destination. Verify both the response and the absence of a sink call. A 403 response is not sufficient evidence if the database query or outbound fetch already happened.

Regression tests must include benign edge cases. Apostrophes in names, internationalised text and legitimate nested paths should not be rejected merely because a toy detector matched. Track blocked-request reasons by route and control version. Repeated false positives can pressure operators to disable a control, so tuning needs evidence and an owner.

## Put state-changing operations inside a transaction boundary

Not every web attack forges syntax. Some abuse the gap between checking a state and committing a new one. Authorisation may be correct for the state the server saw moments earlier while the write applies to a different state by the time it reaches the database.

Consider a report-ownership transfer. Two requests arrive concurrently from the current owner: one transfers the report to a collaborator, the other to an external archive service. Both controllers read the same owner and pass authorisation. Without a version check, both writes succeed, two notifications are sent and the last commit silently wins. The fix is not a second role check. The update must be conditional on the expected ownership and state, such as an optimistic version, and the side effects must follow the committed result. An idempotency key can prevent retries from repeating an action, but it does not resolve two distinct concurrent requests.

| Primitive | Missing invariant | Structural control | Decisive test |
| --- | --- | --- | --- |
| Mass assignment | Only approved fields may change | Map the request to an explicit command with no privilege-bearing fields | Submit `role=admin` or `tenant_id=other` and inspect the persisted object |
| Concurrent state change | Check and write refer to the same version | Conditional update, transaction and unique constraints where appropriate | Race two legal-looking operations and assert only the intended transition commits |
| Replayed side effect | One business action is applied once | Idempotency key scoped to the operation and authenticated actor | Retry the same request after a lost response and verify one external effect |
| Stale workflow | A later step cannot exceed an earlier grant | Revalidate object state and grant close to execution | Queue a step, revoke access, then process it and confirm denial |

Request-shape validation is still useful, but it should define the accepted command rather than merely reject suspicious characters. For example, a profile update should not bind directly to a database entity that also contains `is_admin`, `tenant_id` and `email_verified`. A narrow command object makes accidental privilege changes harder and gives tests a precise contract.

Design error handling around the transaction too. If a database commit succeeds but a notification fails, retrying the whole request may duplicate the notification. Use an outbox or another durable hand-off, and make the consumer idempotent. Security tests should cover the failure window, not only the happy path: commit succeeds, response is lost and the client retries.

## Availability is part of the threat model

Injection and traversal can disclose data, but defensive controls can also create denial of service. A URL fetch without timeouts occupies a worker. A decompression bomb exhausts memory. A filesystem walk over attacker-controlled depth consumes CPU. An expensive authorisation lookup can amplify traffic. Bound concurrency, payload sizes, response sizes, redirects, execution time and recursion.

Fail closed at security gates, but design safe error behavior. A temporary policy-service outage should not silently become allow. If availability requirements demand a degraded mode, define exactly which low-risk operations remain possible, for how long and with what audit trail. Emergency exceptions should be narrow, approved and visible.

## Turn standards into review evidence

OWASP ASVS organises verifiable security requirements and levels. Select a target level from the application's risk and obligations, then map important routes and data flows to requirements. Architecture, authentication, access control, validation and encoding, data protection, and files and resources are especially relevant to this module. <Cite id="owasp-asvs" locator="V1, V2, V4, V5, V8 and V12 verification requirements" /> A checkbox without a test, configuration review or code path is not evidence.

A useful verification package contains the route inventory, threat model, policy definition, automated test results, manual negative tests and deployment settings. Record framework and library versions because escaping and path semantics can change. Re-run the package after dependency upgrades, parser migrations, CDN changes and new background workers.

## Observe decisions without creating a second leak

Security telemetry should answer which control made a decision, for which route and policy version, and whether execution reached the sink. Record request identifiers, subject identifiers where lawful, object class, reason code, control outcome and latency. Avoid logging raw payloads, session cookies, access tokens, full document bodies or secrets by default. Parameter values may contain personal data even when they are not credentials.

Monitor authorisation denials separately from malformed requests. A spike can indicate an attack, a broken client or a policy rollout error. Monitor outbound fetch destinations, redirect counts and timeouts. Monitor template-rendering failures and sanitizer rejections. Correlate application events with gateway and database evidence, while preserving access controls and retention limits for the logs themselves.

## Require prevention evidence as well as exposure evidence

A detection that says an attack was blocked does not prove the sink was protected. A gateway might log a blocked `SELECT` while the application still executes a differently tokenised query. An alert might describe a sanitizer rejection while the original unsanitised value is rendered elsewhere. Incident evidence must connect the control decision to what the sensitive component actually did.

| Suspected failure | Prevention evidence | Exposure evidence | Recovery gate |
| --- | --- | --- | --- |
| SQL injection | Query builder records a fixed structure and bound parameters | Database audit shows the executed statement and affected rows | Regression test fails on the vulnerable query and passes on the fix |
| Stored XSS | Renderer identifies the encoding context and sanitizer policy | Persisted content search, response capture and affected viewer sessions | Each rendering context produces inert output in a DOM test |
| SSRF | Transport log shows destination rejected before connection | Outbound connection and data-service access logs | Forbidden address and redirect fixtures never open a socket |
| Path traversal | File operation uses the resolved, contained object identifier | Storage or filesystem audit shows which objects were opened | Encoded path, absolute path and symlink fixtures stay inside the root |

Correlate these sources with a request identifier where possible, but do not assume one identifier crosses every boundary. A preview request may become a queue message and then an outbound fetch. Carry a correlation field through the application and worker, and record the object identifier rather than only a display filename. If a component cannot emit a sink event, treat that as a telemetry gap and add a testable side effect instead of claiming the control worked.

During response, preserve the deployed code version, configuration and policy version alongside the event window. A clean log after a fix is weaker evidence than a before-and-after reproduction. State the residual uncertainty plainly: sampling may miss a low-volume read, retention may have expired or an asynchronous worker may use a different code path. Recovery should combine the regression test, production canary and targeted log review; no single signal proves the entire route is safe.

HTTP status codes provide a shared vocabulary. A malformed request, an authentication failure and an authorisation denial are not interchangeable. RFC 9110 defines the relevant status-code semantics, including client-error and server-error classes. <Cite id="rfc9110" locator="§15.3–15.5" /> Use consistent, minimal errors and a correlation identifier; do not expose stack traces, SQL fragments, internal paths or whether a hidden object exists.

## Respond to a suspected sink failure

When telemetry suggests a real vulnerability, first bound exposure. Identify affected routes, tenants, time window, deployed versions and sink calls. Preserve relevant request metadata and code/configuration versions without collecting unnecessary sensitive bodies. Disable the vulnerable feature or apply a narrow feature flag if that is safer than a broad emergency rule.

Containment depends on the sink. For SQL injection, remove the unsafe query construction and review database audit evidence. For stored XSS, disable the rendering path and search persisted content. For SSRF, restrict egress and review outbound connection logs. For traversal, freeze the affected storage mount or route and verify which objects were readable. Rotate credentials only when evidence indicates exposure; do not treat rotation as a substitute for fixing execution.

Recovery requires a regression test that fails on the vulnerable version and passes on the fixed version. Re-enable gradually, watch control outcomes and document residual risk. Post-incident review should update the route inventory, dependency constraints, tests and monitoring. The goal is not merely a patch; it is removal of the condition that allowed untrusted data to acquire authority.

## A practical rollout sequence

1. Inventory important routes, input sources, sinks and owners.
2. Rank findings by exploitability, data sensitivity, exposure and detectability, not by CWE number alone.
3. Fix structural issues at the sink and add default-deny object authorisation.
4. Add negative integration tests and benign boundary fixtures before broad deployment.
5. Canary the change with route-level error, latency and control-outcome metrics.
6. Keep compensating controls until evidence shows the structural fix is effective.
7. Rehearse rollback, incident containment and communication with affected service owners.

## Common failure modes

| Failure mode | Observable symptom | Root cause | Guardrail |
| --- | --- | --- | --- |
| Tenant ID trusted from request | Cross-tenant rows or objects returned | Identity is not mapped to object scope | Derive tenant server-side and authorise the resolved object |
| SQL fragments assembled from input | Query shape changes with special values | Data concatenated into command grammar | Bind values and allowlist dynamic identifiers |
| Generic escaping at every output | One context is safe while another executes | HTML, attribute, URL and JS grammars differ | Name the context and test the final sink |
| URL prefix filtering | Internal destination reached after redirect | String checks do not bind resolved connection | Exact destination policy, egress controls and redirect revalidation |
| Path prefix check without resolution | Parent segment or symlink escapes root | Check and open use different paths | Canonical containment and safe file operations |
| Hidden UI used as permission | Direct request succeeds | Authorisation exists only in client | Default-deny server-side object policy |
| Policy cache omits tenant or version | Stale or cross-tenant decision | Incomplete cache key and no invalidation | Include all decision inputs and bound freshness |
| Defensive limits create outage | Workers stall on fetches or huge files | Unbounded time, size, recursion or concurrency | Explicit budgets and fail-closed, observable errors |

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Prepared query still returns other tenants | Tenant value supplied by client or policy uses wrong key | Derive tenant from verified context and test object ownership |
| Benign apostrophe breaks search | Value concatenated into SQL | Bind the value and test the actual driver |
| Encoded title still executes | Wrong output context or later decoding | Inspect rendered DOM and encode at the final context |
| Preview works but redirect reaches metadata service | Redirect destination was not revalidated | Disable redirects or validate every hop and restrict egress |
| File test passes locally but fails in production | Platform separator, symlink or worker path differs | Test canonical resolution and open semantics in deployment |
| Legitimate requests receive 403 after rollout | Policy key, role mapping or cache version mismatch | Trace subject, action, object and policy version server-side |
| Gateway blocks attack but database logs query | Prevention occurs after sink execution | Add structural control in application and keep gateway as compensation |
| Error page reveals internal path | Detailed exception returned to client | Return minimal status plus correlation ID and retain safe server logs |

## Design review checklist

- [ ] Every important route has a request-to-sink flow with owner, subject, tenant, action and object.
- [ ] Untrusted data is decoded and canonicalised once, and the same representation reaches validation, authorisation and execution.
- [ ] SQL values are bound; dynamic identifiers come from a closed allowlist.
- [ ] Output encoding matches the final HTML, attribute, URL, CSS or JavaScript context.
- [ ] Outbound fetches use approved destinations, resolved-address policy and redirect revalidation.
- [ ] File operations enforce canonical containment and authorise the resolved object.
- [ ] Authorisation is default-deny, server-side and tested for cross-tenant and cross-object access.
- [ ] Session, CSRF, cookie and recent-authentication controls match the application's browser model.
- [ ] Negative tests assert that forbidden operations never reach the sink.
- [ ] Benign fixtures cover apostrophes, Unicode, safe nested paths and approved destinations.
- [ ] Timeouts, size limits, concurrency bounds and safe failure modes protect availability.
- [ ] Logs and errors exclude secrets and unnecessary personal data while retaining decision evidence.
- [ ] ASVS target requirements have linked code, configuration or test evidence.
- [ ] Rollback disables unsafe capability rather than restoring vulnerable execution.

## Key takeaways

- A request is untrusted data crossing boundaries; the sink determines which defence matters.
- Authentication, validation and object-level authorisation solve different problems.
- Parameterised queries, contextual encoding, destination allowlists and canonical containment are structural controls.
- Gateways and validation reduce risk but cannot replace safe construction at the sink.
- Negative integration tests, benign fixtures and decision telemetry make security claims reviewable.
- Availability limits and incident containment belong in the design, not only in operations.
