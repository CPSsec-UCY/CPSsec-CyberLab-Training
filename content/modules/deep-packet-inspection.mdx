## What DPI is

Deep packet inspection looks beyond IP and port headers into protocol fields, payloads and application behaviour. A firewall can allow port 443; a DPI sensor can ask whether the traffic is really TLS, whether the certificate looks suspicious, or whether a file download contains a known malicious pattern.

DPI powers intrusion detection, application control, data-loss prevention, traffic shaping and network forensics. It also creates privacy and performance obligations.

## What encryption changes

TLS 1.3 encrypts application data. A passive sensor still sees endpoints, ports, packet sizes, timing and often the server name, but not the HTTP request or file contents. <Cite id="rfc8446" locator="§5" /> The old payload-signature model is no longer sufficient by itself.

<Callout variant="warning" title="Visibility is not control">
A passive IDS alerts; an inline IPS can block. Inline placement turns false positives into outages, so it needs stronger testing and an explicit failure policy.
</Callout>

## The defender's shift

When payloads disappear, defenders move to flow behaviour, DNS and TLS metadata, endpoint telemetry, identity logs and network segmentation. DPI remains useful, but it is one sensor in a portfolio.

## What a sensor actually sees

A passive sensor on a mirrored port sees packet headers: source and destination addresses, ports, protocol, TCP flags, sequence numbers and timing. If the application is plaintext HTTP, it can also see the request line, headers and body. If the application is TLS 1.3, it sees a handshake and then encrypted records; the payload is opaque.

That difference changes the detection strategy. A plaintext signature can look for `GET /admin`; an encrypted sensor must reason about the flow, the TLS metadata, the endpoint and the identity. It can still detect a compromised host calling a suspicious destination, but it may not know what was sent.

### Threat model and incentives

Start with the defender's questions. Is the objective to stop malware before execution, detect command-and-control after execution, prevent regulated data leaving the network, or reconstruct an incident? A hospital infusion-pump network, a public web tier and a research subnet need different placement and retention rules. The monitored assets include availability, patient safety, confidential records and the sensor's own parser memory. A false positive that disconnects a clinical device is not merely annoying; it can interrupt care.

The active attacker wants to complete an objective without producing an interpretable alert. Encryption, fragmentation and protocol tunnelling increase the defender's uncertainty, while timing jitter and benign-looking destinations increase investigation cost. The attacker cares about time-to-detect and can rotate infrastructure cheaply. The defender cannot inspect every payload indefinitely, so its incentive is to collect high-value metadata, prioritise by asset risk and automate evidence gathering. A passive observer may infer behaviour without attacking; interception raises the privacy and legal risk for the defender itself.

Several misconceptions distort design. A firewall is not a DPI sensor: port-and-protocol access control does not reconstruct application behaviour. A flow record is not a packet capture: it cannot support arbitrary content signatures. TLS 1.3 does not hide every useful field: addresses, ports, record sizes, timing and often SNI remain visible. Conversely, metadata does not prove malicious content: a large encrypted upload can be a backup or exfiltration. Finally, a detection that fires correctly in a replay lab may fail in production if the parser sees different tunnel, fragmentation or routing conditions.

Write the visibility contract as a table: observable field, collection point, permitted use, retention and sensitivity. State where the design must use endpoint or identity telemetry instead. This prevents the team from promising payload inspection on an encrypted path and clarifies whether TLS interception is even an acceptable control.

## The pipeline

1. **Capture:** a tap, SPAN port, eBPF hook or capture library.
2. **Decode:** parse link, IP and transport headers; validate lengths and fragmentation.
3. **Flow:** group packets into conversations, track TCP state, reassemble streams.
4. **Detect:** signatures, protocol parsers, anomaly models and threat intelligence.
5. **Action:** alert, log, enrich, throttle, reset or block.

- **Syslog** (RFC 5424) remains a common event transport across network devices. <Cite id="rfc5424" locator="§6" />

## Tuning

A signature that is never tuned becomes noise. Start from an asset inventory, know which services are expected where, and measure alert precision and response cost. NIST SP 800-94 frames the deployment and tuning problem for IDPS. <Cite id="sp800-94" locator="§2–4" />



## The pipeline in more detail

**Capture.** A tap, SPAN port, eBPF hook or packet-capture library copies frames. Loss at capture is a silent blind spot; monitor drop counters.

**Decode.** Parse link, IP and transport headers. Handle VLANs, tunnels, fragmentation and malformed packets. A parser bug can crash the sensor or create an evasion.

**Flow and stream reconstruction.** Group packets into conversations, track TCP state and reassemble application streams. Stateful inspection must handle retransmissions, out-of-order packets and asymmetric routing.

**Detect.** Apply signatures, protocol parsers, anomaly models and threat intelligence. Rules should name the protocol, direction, field and expected behaviour, not just a byte string.

**Action.** Alert, enrich, throttle, reset or block. Inline blocking changes the availability risk and requires a fail-open/fail-closed decision.

## Common evasions

- Fragmenting a payload across IP fragments or TCP segments.
- Encoding or compressing content that the parser does not normalise.
- Tunnelling one protocol inside another.
- Using encryption or domain fronting to hide the destination.
- Sending the malicious action after a benign-looking handshake.

Detection engineering is an arms race; test evasions, not only known samples.

## A packet walk-through

A plaintext HTTP request to `/admin` reveals the method, path, headers and body. A signature can match the path and the user agent. A TLS 1.3 connection to the same server reveals a handshake and encrypted records; the sensor may see the SNI, certificate and flow shape, but not `/admin`.

If the endpoint is compromised, EDR telemetry may show the process and command line even when the network payload is opaque. If the endpoint is not instrumented, the defender must rely on flow behaviour, DNS and authentication logs. No single sensor tells the whole story.

### Reconstruct a conversation, not a packet

A stateful sensor joins packets by addresses, ports, protocol and TCP sequence space. It must tolerate retransmissions without applying a signature twice, handle out-of-order segments without losing context and avoid confusing a new connection that reuses a port with an old one. Consider a TLS connection over IPv4 with an Ethernet MTU of 1,500 bytes. After 20-byte IP and 20-byte TCP headers, the usual maximum segment payload is 1,460 bytes, before options reduce it further.

<Lens level={3} title="Detection is classification under base rates">

A signature is a classifier. Its operational value depends on attack prevalence, false-positive rate and investigation cost. With a base rate $\pi$, true-positive rate $p$ and false-positive rate $q$:

$$
\Pr(\text{attack} \mid \text{alert}) = \frac{\pi p}{\pi p + (1-\pi)q}.
$$

When attacks are rare, even a small $q$ can dominate the queue. Early signature systems often failed not because they missed attacks, but because analysts could not handle the alerts.

<Callout variant="lab" title="Signatures versus anomalies">
Signatures explain why they fired; anomaly models need a baseline and a cost model. Both are evadable. Coverage should be mapped to attacker techniques, not only to file hashes.
</Callout>

Flow analysis provides metadata features — bytes, packets, duration, periodicity — that survive encryption. It can reveal beaconing, scans and exfiltration patterns, but often not intent.

Without decryption, DPI can use:

- TLS metadata and certificate properties,

These are probabilistic. They support hunting and triage; they rarely prove content-level malice on their own.



## Detection as a decision problem

A signature fires when a pattern matches. Its operational value depends on prevalence, false positives and the cost of investigation. With base rate $\pi$, true-positive rate $p$ and false-positive rate $q$:

$$
\Pr(\text{attack} \mid \text{alert}) = \frac{\pi p}{\pi p + (1-\pi)q}.
$$

When attacks are rare, a small $q$ can dominate the queue. A high-accuracy rule can still be operationally useless if it fires on every benign deployment.

## Encrypted traffic

With TLS 1.3, payload signatures cannot see the plaintext. Defenders use:

- flow features: bytes, packets, duration, directionality;
- TLS metadata: SNI where visible, certificate properties, ALPN;
- timing and periodicity for beaconing;
- DNS and proxy logs;
- endpoint telemetry.

These features support hunting and triage, but they rarely prove content-level malice. Be explicit about uncertainty. <Cite id="rfc8446" locator="§5" />

<Callout variant="lab" title="Normalise before you match">
A signature that works on one parser can fail on another because of encoding, case, chunking or normalisation. Document the parser and the normalisation assumptions with the rule.

### Formal detection model

Let $X$ be an event, $Y\in\{0,1\}$ indicate an attack and $D$ indicate an alert. Sensitivity is $p=\Pr(D=1\mid Y=1)$; false-positive rate is $q=\Pr(D=1\mid Y=0)$; specificity is $1-q$. Bayes' rule gives precision as before. The expected number of false alerts over a period is

$$
E[F] = N(1-\pi)q,
$$

where $N$ is the number of evaluated events and $\pi$ is attack prevalence. If a sensor evaluates ten million flows per day with $q=0.001$, that is about 10,000 false alerts per day before correlation. Grouping, suppression and tuning are therefore part of the mathematical model, not cosmetic SIEM changes.

A likelihood-ratio detector scores $L(x)=p(x\mid Y=1)/p(x\mid Y=0)$ and alerts above a threshold. Raising it reduces false alerts and true alerts, producing an ROC trade-off. Choose the threshold from the costs of missed attacks, investigations and blocked legitimate traffic. Accuracy is unsuitable because benign events dominate; laboratory precision does not transfer automatically to a rarer population.

The Bayesian calculation assumes representative samples, stable prevalence and meaningful conditional probabilities. Correlated alerts violate independence: one compromised host may produce many detections of one incident. Endpoint compromise changes observations, and attackers can shift traffic distributions. Recompute metrics by asset class and time window, separating event-level from incident-level precision.

### Correctness of parsing and limits of encrypted evidence

For signature detection to be sound, the reconstructed byte string presented to the rule must be equivalent to the application's interpretation under the protocol version being inspected. Otherwise fragmentation, character encoding or decompression can make two different payloads look identical to the sensor. Treat normalisation as a specification with tests. Bound decompression ratios, recursion and buffer sizes; a parser that allocates unbounded memory creates a denial-of-service path independent of the attack signature.

TLS 1.3 protects record payload confidentiality and integrity under the negotiated keys. <Cite id="rfc8446" locator="§5" /> A passive observer cannot verify a claim about plaintext content from ciphertext alone. Metadata-based detection is therefore a probabilistic inference over features such as timing, size and destination, not a proof of content. Two applications can intentionally produce identical flow shapes; a benign software updater can mimic beaconing; a CDN can host many destinations behind one address. Report confidence and supporting evidence rather than upgrading correlation into certainty.

Flow features need their own units and assumptions. Periodicity can be estimated from inter-arrival gaps, but network queuing adds jitter. Volume anomalies require a baseline for the asset and time of day. Directionality helps distinguish uploads from downloads, but NAT and proxies alter endpoints. The design should specify the feature window, minimum packet count, treatment of retransmissions and missing samples. Without those choices, the same detection produces inconsistent results across sensor software.

Evasion analysis compares the attacker's possible transformations with the detector's normalisation. If the parser understands gzip, the attacker can still exploit unsupported compression, nested archives or decompression errors. If a rule matches a header split across TCP segments, stream reassembly closes that gap but introduces state-exhaustion risk. Encryption removes the gap only by removing visibility. A defensible detection portfolio combines payload inspection where lawful and available, protocol validation, endpoint telemetry and identity-aware correlation so that one bypass does not erase every signal.
</Callout>

## Performance

- **eBPF/XDP** and kernel bypass move processing close to the NIC.
- **Flow tables** and hardware offload reduce per-packet cost.
- **Full packet capture** is expensive; many teams retain flows and capture packets around alerts.

## Inline hazards

1. False positives drop legitimate traffic.
2. Asymmetric routing breaks stateful inspection.
3. Fragmentation and tunnelling can evade parsers.
4. Sensor failure must fail open or closed by explicit policy.
5. TLS interception creates a high-value key and trust target.

<Callout variant="danger" title="TLS decryption proxies are crown jewels">
A proxy that terminates TLS holds keys, sees plaintext and must be trusted by clients. It needs isolation, strong access control, logging and a legal/privacy basis. It can break certificate pinning and create new attack surface.
</Callout>

## Deployment checklist

- Define the questions the sensor must answer and the data it must not retain.
- Place capture points where traffic is representative.
- Normalise time, identity and schema before correlation.
- Benchmark worst-case traffic, not averages.
- Test fail-open versus fail-closed behaviour.
- Validate coverage against emulated attacker behaviour.
- Document retention and privacy controls.

## Performance and deployment

- **Kernel bypass** (DPDK, PF_RING) and **eBPF/XDP** move processing close to the NIC.
- **Flow tables** and hardware offload reduce per-packet cost.
- **Sampling** reduces volume but can miss short-lived events.
- **Full packet capture** is expensive in storage, privacy and review time; retain flows and capture around alerts.

## Inline versus passive

An inline IPS can block, but a false positive becomes an outage. A passive IDS cannot block but is safer to deploy and easier to justify legally. Many organisations run passive detection first, then add targeted inline enforcement after tuning.

## Privacy and legal constraints

Packet capture can contain credentials, personal data and regulated content. Define lawful basis, retention, access control, encryption and deletion. TLS interception is a high-value target: it holds keys, sees plaintext and must be hardened and authorised.

## Deployment checklist

1. Define the questions the sensor must answer and the response it may take.
2. Place sensors where traffic is representative and not asymmetric.
3. Normalise timestamps, identities and schema.
4. Benchmark worst-case traffic and capture loss.
5. Test fail-open/fail-closed and rollback.
6. Measure alert precision and response cost.
7. Document retention and privacy controls.

## Common pitfalls

- Deploying a sensor without measuring capture loss.
- Writing signatures against a parser without normalising encodings.
- Treating an encrypted flow as invisible instead of using metadata and endpoint telemetry.
- Forgetting retention, privacy and access control for captured payload.
- Enabling inline blocking before measuring false positives.
- Assuming a signature still covers a protocol after a version upgrade.

### Deployment patterns and capacity planning

A passive tap cannot interrupt production traffic. Mirror a representative link, but verify both directions and avoid oversubscribing the sensor. An eBPF host sensor sees endpoint flows a network tap may miss, but consumes host resources and inherits the host's integrity assumptions. An inline IPS can block in real time, yet turns parser bugs, stale rules and hardware failure into availability incidents.

Plan capacity from packets per second and bytes per second, not link utilisation alone. Small packets consume more per-packet work; fragmented traffic, TLS handshakes and rule count increase cost. If a 10 Gb/s link carries 64-byte frames, it presents about 14.88 million frames per second before overhead. A sensor rated for a certain packet rate may saturate on small-packet traffic even when its byte throughput appears adequate. Benchmark the rule set, flow-table size, capture filters and logging destination together.

Use hardware offload and kernel bypass where measured, but keep a functional reference path for debugging. Flow-table timeout and maximum-flow settings affect memory: too low creates churn and missed state; too high permits resource exhaustion. If full packet capture is required, capture around alerts or store a bounded rolling window rather than every payload indefinitely. Protect captures as sensitive data with encryption, access logging and deletion schedules.

### Observability and testing

Monitor NIC and kernel drops, capture-ring overruns, parser errors, reassembly failures, flow-table utilisation, detection latency, rule evaluation time and output-queue backpressure. Compare packet counters at the tap, sensor and collector; a sensor can report healthy while losing traffic upstream. Include sensor software version, ruleset hash and last successful heartbeat in every alert. Log action outcomes separately: an inline block attempt is not proof that traffic stopped.

Test with replayed benign traffic, known-malicious samples and attacker-controlled evasions. Vary MTU, fragmentation, TCP options, out-of-order delivery, retransmissions, tunnels, compression and protocol versions. For an inline deployment, test fail-open and fail-closed with real failover hardware and confirm that recovery does not flap. Measure the false-positive cost on critical assets before enabling automatic blocking.

1. Define the detection question and acceptable response for each network zone.
2. Verify capture coverage in both directions and measure loss under peak small-packet load.
3. Document protocol versions, tunnel types and normalisation assumptions for every rule.
4. Set bounded reassembly, decompression and flow-table resources.
5. Establish the base rate and measure precision by asset class.
6. Correlate network events with identity and endpoint evidence using synchronised time.
7. Define retention, access, encryption and deletion for payload captures.
8. Benchmark worst-case packet rate, rule set and log throughput.
9. Rehearse inline failure, bypass and rollback without disrupting critical services.
10. Retest coverage after protocol, proxy, TLS or routing changes.

## Common failure modes

| Failure mode | Observable symptom | Root cause | Guardrail |
| --- | --- | --- | --- |
| Silent capture loss | Fewer events than interface counters suggest | SPAN oversubscription or full capture ring | Compare counters at every hop and alert on drops |
| Stream mismatch | Rule fires inconsistently on equivalent traffic | Parser normalisation differs from application | Version parsers and test encodings and fragmentation |
| Alert flood | Most alerts are benign deployments | Rare base rate and broad rule scope | Measure precision, group events and narrow exceptions |
| Inline outage | Legitimate clinical or business traffic drops | Untested false positives or fail policy | Passive tuning and approved containment workflow |
| Reassembly exhaustion | Sensor memory spikes on crafted fragments | Unbounded state and decompression | Cap buffers, ratios, flow counts and timeouts |
| Encryption overclaim | Team believes payload is inspected | TLS termination or visibility not documented | Publish a per-zone visibility contract |

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Interface looks idle | Wrong SPAN direction or VLAN filter | Validate capture with controlled packets on both directions |
| Rule misses a known sample | Pattern spans segments or uses an unexpected encoding | Replay through stream reassembly and inspect normalised bytes |
| Sensor CPU pegs under small packets | Per-packet rule and flow overhead | Profile hot rules, adjust capture filters and right-size capacity |
| Endpoint and network times disagree | Unsynchronised clocks or proxy rewrites | Record event and ingestion time; fix NTP and document proxy boundaries |
| Inline deployment blocks backups | Broad signature matches an expected data transfer | Add asset-scoped exception with owner, expiry and monitoring |
| TLS flows lack expected metadata | Encrypted ClientHello or proxy termination | Inspect negotiation support and correlate at proxy or endpoint |

## Design review checklist

- [ ] Each network zone has a documented visibility and response contract.
- [ ] Capture loss, parser failures and output backpressure are measurable end to end.
- [ ] Rules identify protocol version, direction, fields and normalisation assumptions.
- [ ] Reassembly, decompression and flow-table resources are bounded.
- [ ] Base rate, precision and investigation cost are measured by asset class.
- [ ] Encrypted detection is described as inference with explicit uncertainty.
- [ ] Inline fail-open or fail-closed behaviour is approved and rehearsed.
- [ ] Payload retention, access and deletion satisfy privacy and legal requirements.
- [ ] Evasion tests cover fragmentation, tunnelling, encoding and jitter.

## Key takeaways

- DPI provides visibility, not omniscience; encryption changes what is observable.

- Capture, decode, flow and detection each have distinct failure modes.
- Detection quality is a function of base rates and response cost, not just accuracy.
- Inline blocking trades availability risk for control.
- Privacy and legal constraints are part of the architecture.
