## The familiar picture

When you open a secure website, your browser and the server agree on keys, authenticate the server, and start encrypting. TLS 1.3 does this in one round trip for a new connection. <Cite id="rfc8446" locator="§2" />

Two separate jobs are happening:

- **Key exchange:** agree on a fresh shared secret that an eavesdropper cannot compute.
- **Authentication:** prove the server is who its certificate says it is.

Post-quantum cryptography changes both. The key exchange can use a hybrid of X25519 and ML-KEM. The authentication can use ML-DSA or SLH-DSA certificates.

## Why the packet gets bigger

A classical X25519 key share is 32 bytes. An ML-KEM-768 encapsulation key is 1,184 bytes and its ciphertext is 1,088 bytes. A hybrid client hello can therefore carry more than a kilobyte of key material before any certificate appears. <Cite id="fips203" locator="Table 3" />

<Callout variant="warning" title="The suitcase problem">
The maths is not the hard part in deployment. The hard part is every assumption that a ClientHello fits in one TCP segment, a certificate chain fits in a buffer, or an HSM accepts a 3 KB signature. Test the whole path.
</Callout>

## Why hybrid is the safe first step

A hybrid group remains secure if either X25519 or ML-KEM is secure. That protects against a surprise in the new component without betting the connection on a single assumption. It also gives the ecosystem time to find implementation bugs while traffic is already protected against harvest-now attacks. <Cite id="hybrid-design" locator="§3–4" />

## What users should notice

Ideally: nothing. In practice: slightly slower first connections, larger handshakes, and occasional failures in old middleboxes or constrained devices. Those failures are exactly what a staged rollout is for.

## What happens in the first second

A browser opens a TLS connection and sends a ClientHello with supported versions, cipher suites, groups and key shares. The server selects parameters and returns its own key share, certificate chain and signature. Both sides derive traffic keys and the browser verifies the certificate path before sending the HTTP request.

For a PQ hybrid, the ClientHello may carry both a 32-byte X25519 share and a 1,184-byte ML-KEM encapsulation key. The server returns an X25519 share and a 1,088-byte ML-KEM ciphertext. The resulting shared secret is a combination of both, so the connection remains secure if either component is secure.

### Threat model: migration under active observation

A well-resourced observer can record encrypted traffic now and recover session keys later if quantum capabilities emerge. Harvest-now, decrypt-later makes key-exchange migration urgent. The same observer may exploit downgrade, certificate or interception weaknesses today. Recorded signatures create a different exposure: future forgery threatens long-lived firmware and documents.

A bank introducing hybrid TLS faces pressure from attackers seeking classical fallback, from older clients and from vendors optimising for compatibility. Silent fallbacks and under-sized buffers weaken the security argument despite passing routine compatibility tests.

Three misconceptions are dangerous. **Hybrid is not a vote for the weaker algorithm**: the combiner aims to retain security if either component survives. **A PQ certificate is not automatically trustworthy**: X.509 path and identity validation still apply. **Standards compliance is not deployability**: middleboxes, HSMs and firmware carry legacy limits. Most failures occur in devices and processes that assumed classical sizes, not in the mathematics.

Separate time horizons: protect ephemeral session keys against future decryption, CA and firmware signing keys against future forgery, and trust stores and upgrades against present compromise.
</Lens>

## Key exchange details

- The client advertises groups in `supported_groups` and sends one or more `key_share` entries. <Cite id="rfc8446" locator="§4.2.1" />
- For X25519MLKEM768, the client sends an X25519 public value (32 B) and an ML-KEM-768 encapsulation key (1,184 B).
- The server selects the group and returns an X25519 public value plus an ML-KEM ciphertext (1,088 B).
- Both sides derive a classical shared secret (X25519 is specified in RFC 7748 <Cite id="rfc7748" locator="§5" />) and a PQ shared secret, concatenate them, and feed the result into the TLS key schedule.

## Authentication details

- The server sends a certificate chain and a `CertificateVerify` signature over the transcript.
- With ML-DSA-65, the signature is 3,309 bytes. <Cite id="fips204" locator="§4" /> With SLH-DSA-128s, it is 7,856 bytes; an SLH-DSA chain would be larger still. <Cite id="fips205" locator="§11" /> Classical ECDSA remains in the same X.509 framework. <Cite id="fips186-5" locator="§6" />
- X.509 parsing, name constraints, revocation and path building are unchanged in principle, but size and algorithm identifiers change. <Cite id="rfc5280" locator="§4.1–4.2" />

## HPKE and other protocols

HPKE exposes a KEM interface directly and is used for sealed messages, encrypted metadata and hybrid public-key encryption. An ML-KEM-based HPKE ciphersuite replaces the classical KEM but keeps the same API shape. <Cite id="rfc9180" locator="§4–5" />

## Certificate chain sizing

For a rough planning model:

- ML-DSA-65 public key: 1,952 B; signature: 3,309 B.
- A three-certificate chain with one ML-DSA signature per certificate can add roughly 10 KB before extensions.
- Classical ECDSA P-256 signatures are around 64 B; the delta is two orders of magnitude.

Compression, shorter chains and cross-signing strategies can help, but they do not change the order of magnitude.

<Callout variant="note" title="Crypto agility is a protocol feature">
Algorithm identifiers, certificate extensions and negotiated groups must be able to change without a new protocol version. NIST IR 8547 treats agility as a central migration requirement. <Cite id="nist-ir8547" locator="§4" />
</Callout>



## Flights and state

TLS 1.3 has a tightly specified key schedule and transcript. The handshake transcript binds the ClientHello, ServerHello, certificates, CertificateVerify and Finished messages. If an attacker modifies a group, signature algorithm or certificate, the transcript changes and the Finished MAC fails.

The client and server maintain separate traffic secrets for each direction. Record sequence numbers prevent reordering and replay within a connection. A new connection derives fresh secrets, giving forward secrecy.

## Certificates and algorithms

A modern chain may use different signature algorithms at different levels: a root with a long-lived classical or PQC signature, an intermediate signed with ML-DSA, and a leaf using another approved scheme. The verifier must support each algorithm and enforce path constraints.

Certificate size is a protocol constraint. ML-DSA-65 has a 3,309-byte signature and a 1,952-byte public key; an SLH-DSA chain is much larger. <Cite id="fips204" locator="§4" /> Buffer limits, fragmentation and middlebox behaviour must be tested with realistic chains.

### Walk the negotiated flight

The client offers versions, cipher suites, signature algorithms, groups and key shares. X25519MLKEM768 carries both public values. The server selects one group; a mismatch is a protocol error, not permission to try another group in the same flight. It then sends EncryptedExtensions, the certificate chain, CertificateVerify and Finished. The client verifies before releasing application data.

CertificateVerify signs a context string and transcript hash, authenticating the negotiation as well as the certificate. Finished prevents undetected handshake modification. Application traffic uses separate write secrets. PQ key exchange protects against a passive quantum adversary only if group negotiation, KDF and transcript binding are correct.

<Lens level={3} title="Key schedule, combiners and the authentication chain">

## The TLS 1.3 key schedule

TLS 1.3 uses HKDF with SHA-256 or SHA-384. The early secret, handshake secret and master secret are derived by `HKDF-Extract` and `HKDF-Expand-Label`. The transcript hash binds the handshake messages, including the key shares and certificates. <Cite id="rfc8446" locator="§4.4" />

For a hybrid group, the input keying material is a concatenation of the component shared secrets. The hybrid design draft specifies how the group is encoded and how the combined secret is formed, including domain separation. <Cite id="hybrid-design" locator="§3–4" />

<Callout variant="lab" title="Security argument sketch">
If the KDF behaves as a random oracle and the concatenated secrets contain at least one unknown-to-the-adversary component, the derived traffic keys are indistinguishable from random. The proof must account for the transcript, the authentication signatures and the possibility that one component is broken. Hybrid combiners are designed so that the failure of one component does not compromise the output.
</Callout>

## Authentication

`CertificateVerify` signs a context string and the transcript hash with the server's private key. The verifier checks the certificate chain, the key usage, the signature algorithm and the signature over the transcript. PQC signatures plug into the same structure, but the algorithm identifier and signature length change.

## X.509 and trust anchors

A certificate binds a subject to a public key and is signed by an issuer. The chain terminates at a trust anchor in the client's store. PQC migration affects:

- the signature algorithm of each certificate,
- the public-key algorithm and key size,
- the size of the encoded certificate,
- the algorithms a CA is willing to issue,
- the algorithms a client is willing to accept.

There is no single switch. Trust stores, CA/browser policy, and cross-signing must be coordinated. <Cite id="rfc5280" locator="§4" />

## Revocation and transparency

CRLs and OCSP responses grow with certificate size and signature size. Certificate Transparency logs must accept PQC certificates. A migration that ignores revocation and transparency creates a second, slower outage later.



## The key schedule and hybrid security

TLS 1.3 derives handshake and application secrets with HKDF. The hybrid group supplies input keying material containing both the classical and PQ shared secrets. The hybrid design must define the encoding, ordering and domain separation so both peers derive the same value and an attacker cannot splice components across groups.

A reduction for a hybrid combiner typically argues that if the derived key is distinguishable, then either the KDF is broken or at least one component secret is distinguishable. This is why the protocol must not silently fall back or accept a mismatched group.

## Certificate validation in depth

Validation checks the signature chain, validity dates, name constraints, key usage, basic constraints, revocation policy and trust anchor. A PQ certificate is not automatically trusted because it uses a PQ algorithm; the same path-building rules apply. Mis-issued or cross-signed certificates remain a risk, and revocation data must be available and fresh. <Cite id="rfc5280" locator="§4" />

<Callout variant="lab" title="Transcript binding">
If the handshake transcript or algorithm identifiers are not bound into the Finished MAC and CertificateVerify signature, an attacker may be able to downgrade or splice messages. Protocols must bind every negotiated parameter that affects security.
</Callout>

### Key schedule and transcript binding

TLS 1.3 defines the handshake secret using HKDF-Extract over an early-secret derivation and the negotiated shared secret. In simplified notation,

$$
\text{EarlySecret}=\operatorname{Extract}(0,\text{PSK}),\qquad
\text{HandshakeSecret}=\operatorname{Extract}(\text{DerivedSecret},\text{IKM}),
$$

where IKM is the key-exchange output and a zero PSK means no early data. Labelled HKDF expansions derive master and directional traffic secrets, preventing purpose collisions. <Cite id="rfc8446" locator="§4.4" /> Exact context strings and ordering are normative; this notation only explains the structure.

The transcript hash commits to ClientHello, ServerHello, key shares, certificates, CertificateVerify and Finished. Record sequence numbers distinguish records within a connection. Fresh ephemeral secrets provide forward secrecy: compromising a long-term authentication key does not automatically reveal past session keys.

### Hybrid security argument

Let $Z_c$ and $Z_p$ be classical and post-quantum shared secrets. The group maps them into IKM with specified encoding and domain separation. If at least one component remains unknown to the adversary, the combiner should leave derived keys indistinguishable from random; a reduction attacks either the KDF or a component secret. <Cite id="hybrid-design" locator="§3–4" />

This requires correct negotiation, valid key shares, transcript binding and no silent fallback. It does not protect compromised endpoints, stolen server keys or accepted classical-only downgrades, nor does it make both components equally strong.

ML-KEM uses implicit rejection to avoid a decapsulation oracle. Timing differences, logged rejection codes or retries with weaker groups can still undermine the system-level property.

### Certificate-path correctness

A verifier builds a path to a trust anchor, checking signatures, validity, name constraints, key usage, policy and revocation. <Cite id="rfc5280" locator="§4" /> PQ changes sizes and identifiers, not these semantics. A cryptographically valid chain can still authenticate the wrong identity.

For $m$ transmitted ML-DSA-65 certificates, keys and signatures alone contribute $m(1,952+3,309)$ bytes. The root usually stays in the trust store, so a three-certificate hierarchy normally sends two. Include extensions, names, CertificateVerify, Finished and record headers in capacity plans; size revocation and transparency pipelines separately.
</Lens>

<Lens level={4} title="Buffers, middleboxes, HSMs and firmware">

## The deployment gauntlet

PQC in TLS fails in the same places classical TLS fails, only sooner:

- **TCP segmentation and MTU:** a 4–10 KB handshake spans multiple segments. Some middleboxes assume one segment.
- **Record fragmentation:** TLS records have a plaintext limit of $2^{14}$ bytes; handshake messages can span records, but implementations must reassemble correctly. <Cite id="rfc8446" locator="§5.1" />
- **Buffer limits:** 2 KB ClientHello buffers, 4 KB certificate buffers and fixed-size HSM command buffers are common.
- **Parsers:** length fields and extensions must be checked; a larger certificate is a larger attack surface.
- **Hardware:** HSMs and secure elements need firmware support for ML-KEM and ML-DSA, plus enough command-buffer space.
- **Firmware and boot:** code-signing keys live for years. Plan the trust-anchor migration before the hardware refresh.

## Hybrid pitfalls

- Do not concatenate secrets without a specified combiner and domain separation.
- Do not silently fall back to a classical-only group if the PQ component fails; that can be a downgrade.
- Do not assume both components have the same security level or the same failure behaviour.
- Test with real clients, not only your own implementation.

<Callout variant="danger" title="Downgrade and oracle hazards">
A server that reveals whether a PQ key share was malformed, or that falls back on any error, can create an oracle or a downgrade path. Follow the protocol specification and test negative cases.
</Callout>

## Operational checklist

1. Inventory TLS terminators, load balancers, CDNs and embedded clients.
2. Measure handshake sizes and fragmentation on the real path.
3. Enable hybrid groups in monitor mode; collect failure telemetry.
4. Update certificate profiles and CA tooling for PQC signatures.
5. Test HSM command sizes and key import/export paths.
6. Add crypto-agility tests to CI: swap algorithms, reject unknowns, verify negatives.
7. Plan the long-lived signing keys separately from ephemeral key exchange.

## Interoperability

Use standard test vectors and independent implementations. `liboqs` and the Open Quantum Safe provider ecosystem are useful for experimentation, but production deployment needs audited protocol stacks and hardware. <Cite id="liboqs" /> <Cite id="fips204" locator="§3.6" />

## Deployment and performance

- **Buffer sizing:** handshake messages and certificates can span multiple records and TCP segments.
- **Middleboxes:** some assume classical handshake sizes or specific extensions.
- **HSMs:** firmware must support the algorithm, key sizes and command-buffer sizes.
- **Firmware and boot:** signing keys outlive devices; plan rotation and recovery.
- **Crypto agility:** negotiate algorithms without requiring a new protocol version.

## Testing checklist

1. Measure handshake size and fragmentation on the real path.
2. Test with old clients, middleboxes and constrained devices.
3. Verify negative cases: bad signatures, unknown groups, expired certificates.
4. Check downgrade resistance and failure behaviour.
5. Test HSM key generation, import/export and signing performance.
6. Exercise root and intermediate rotation.
7. Monitor handshake failure rates by client and network.

<Callout variant="danger" title="Interception changes the trust model">
A TLS proxy that decrypts traffic holds keys and sees plaintext. It must be isolated, authorised, monitored and included in incident response. It can also break certificate pinning and create a new single point of compromise.
</Callout>

### Staged deployment and performance

Inventory TLS terminators, gateways, proxies, service meshes, mobile applications, terminals and update clients. Hybrid key exchange can precede PQC certificate authentication because ephemeral keys and long-lived CA operations have different urgency and support profiles.

Start in monitor mode: offer hybrid groups, record negotiation and failures by client, network and edge, and retain justified classical support. Canary only after size and failure baselines exist. Measure CPU, p99 latency, retransmissions, aborts and certificate-fetch time; microbenchmarks do not predict end-to-end behaviour.

Budget both directions. Larger ClientHellos consume constrained uplink; certificate flights consume downlink and parsing memory. Record plaintext and ciphertext lengths, group, signature algorithm, chain length and record count to attribute regressions.

### Testing and operational observability

Test independent implementations across groups, chains, TLS versions, middleboxes, MTUs and proxy modes. Use known-answer vectors plus protocol negatives: unknown groups, malformed shares, bad signatures, expired certificates and missing intermediates. None may trigger fallback.

Instrument failures by stage: ClientHello rejection, no shared group, path failure, signature failure, reassembly timeout or Finished mismatch. Aggregate by release, client family and network without retaining sensitive handshake contents. Alert on negotiation, chain-size and fallback shifts.

Operate PKI as a lifecycle. Inventory certificate owners, algorithms, expiry, issuance and revocation dependencies. Test CA failover, HSM firmware, root rotation and emergency revocation. Long-lived code-signing migration must cover spares, field updates and offline recovery.

1. Inventory TLS terminators and embedded clients with their supported algorithms and buffer limits.
2. Define time horizons for session confidentiality and long-lived signature forgery.
3. Measure realistic ClientHello, certificate chain and server-flight sizes across the actual path.
4. Deploy hybrid groups in monitor mode and baseline failures by client and network.
5. Test HSM generation, signing, command sizes, backup and recovery with the target algorithms.
6. Verify certificate path building, name constraints, revocation and transparency ingestion.
7. Test malformed messages, downgrade attempts and fail-closed behaviour.
8. Benchmark CPU, memory, latency and retransmissions under peak connection churn.
9. Rehearse CA, root, intermediate and firmware trust-anchor migration.
10. Monitor negotiated algorithms, chain sizes, fallbacks and failure stages after rollout.

## Common failure modes

| Failure mode | Observable symptom | Root cause | Guardrail |
| --- | --- | --- | --- |
| ClientHello dropped | Specific networks cannot connect | Fixed-size middlebox buffer | Measure full hello and test real MTU and proxy paths |
| Certificate buffer overflow | Handshake fails after ServerHello | Chain and signature sizes exceed limit | Send shorter valid chains and upgrade constrained devices |
| Silent downgrade | Hybrid negotiation rate collapses | Retry with classical-only group | Reject unsupported policy and alert on fallback shifts |
| HSM command rejection | Signing fails for long signatures | Firmware or command buffer lacks support | Test exact algorithm, size, backup and restore paths |
| PKI inconsistency | Clients reject otherwise valid chain | Missing algorithm support or constraint handling | Validate full path, name constraints and revocation |
| Trust-anchor outage | Firmware devices stop updating | Offline root retired too early | Inventory long-lived devices and rehearse rotation |

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Failure only on one partner network | Middlebox size or extension handling | Capture the failure stage and test with reduced MTU and exact chain |
| Server logs decapsulation errors | Malformed share, wrong group or oracle-like retry | Validate encoding, reject cleanly and remove weak fallback |
| Certificate works in library but fails in browser | Path-building, name or algorithm-policy mismatch | Compare hostname, constraints, AIA and trust-store policy |
| HSM accepts keys but not signatures | Command buffer or firmware limit | Test fragmentation support and update or replace the appliance |
| Handshake latency spikes after PQ rollout | Large flight, CA fetch or CPU saturation | Measure stage latency, chain size, CPU and retransmissions |
| Old devices fail after root rotation | New trust anchor absent or incompatible | Restore prior trust distribution and stage device updates |

## Design review checklist

- [ ] Session-confidentiality and long-lived-signature migration plans have separate owners and timelines.
- [ ] Hybrid negotiation cannot silently fall back on size errors or malformed shares.
- [ ] Full ClientHello and server-flight sizes include extensions, chain, Finished and record overhead.
- [ ] Every middlebox, proxy and client is tested through the real path and reduced MTU.
- [ ] HSM firmware supports target algorithms and exact command and signature sizes.
- [ ] Certificate path building, name constraints, revocation and transparency are verified end to end.
- [ ] Trust-anchor rotation includes offline custody, recovery shares and field-device inventory.
- [ ] Negative tests cover unknown groups, bad signatures, expired and missing certificates.
- [ ] Rollback preserves security and does not open a downgrade window.

## Key takeaways

- TLS performs key exchange and authentication; PQC changes both sizes and algorithms.

- Hybrid groups protect traffic while the PQC ecosystem matures.
- Certificate path validation and revocation remain essential.
- The transcript binds the handshake; downgrade resistance is a protocol property.
- Deployment failures often come from buffers, middleboxes and hardware, not the maths.
